TRD-06: One-Sided Operations

Hints — Limen RDMA Transport Project
Level 1 = nudge  |  Level 2 = stronger push  |  Try Level 1 for 15+ minutes before escalating

Level 1 points at the right place. Level 2 names the mechanism.

The failure character of this rung is plausible wrongness. Most defects here produce a program that runs, completes, and reports success while having done something subtly different from what you intended — a write to the wrong address that happened to be registered, a notification scheme that works today and not under load. The defence is printing all four address-and-key fields from section 3 and checking whose each is, every time something behaves oddly.

H1 — Consume the Handshake Descriptor (R1)

Level 1

The values already arrive — TRD-05 R7 exchanged them and printed them. The work is validation, and it is worth more than it looks: these three numbers crossed a network and were byte-order converted, and a mistake in either step produces a remote access error in R2 that implicates access flags rather than the conversion.

Check three things before posting anything. Two are obviously invalid values. The third is a bounds relationship between what you intend to write and what the peer advertised, and nothing in the API will check it for you.

Level 2
if (peer.addr == 0 || peer.rkey == 0) {
    std::fprintf(stderr,
        "peer descriptor invalid: addr=0x%016" PRIx64 " rkey=0x%08x\n"
        "  the handshake did not deliver a usable region "
        "(check the byte-order conversion in TRD-05 R7)\n",
        peer.addr, peer.rkey);
    return 3;
}
if (msg_size > peer.length) {
    std::fprintf(stderr, "message size %zu exceeds the peer's advertised %u bytes\n",
                 msg_size, peer.length);
    return 3;
}

Verify the round trip once, by hand, before trusting it: print the peer’s ConnInfo on the client and the server’s own region address and key on the server, and confirm they match. Four numbers, thirty seconds, and it eliminates the most confusing possible cause of an R2 failure.

H2 — RDMA_WRITE (R2)

Level 1

Start from TRD-03’s post_send. Change the opcode and populate the union that was zeroed and unused there.

The scatter-gather entry is unchanged — it still describes your buffer with your local key. Only the two new fields describe the peer. If you find yourself putting a remote key into the scatter-gather entry, reread section 3’s table.

Zero the work request structure before filling it, as always. The union has other members and stack contents in them produce failures that appear intermittently.

Level 2
static int post_write(ibv_qp *qp, ibv_mr *mr, void *buf, size_t len,
                      uint64_t remote_addr, uint32_t rkey, uint64_t id)
{
    ibv_sge sge{};
    sge.addr   = (uintptr_t)buf;        /* YOUR buffer  */
    sge.length = (uint32_t)len;
    sge.lkey   = mr->lkey;              /* YOUR key     */

    ibv_send_wr wr{};
    wr.wr_id               = id;
    wr.sg_list             = &sge;
    wr.num_sge             = 1;
    wr.opcode              = IBV_WR_RDMA_WRITE;
    wr.send_flags          = IBV_SEND_SIGNALED;
    wr.wr.rdma.remote_addr = remote_addr;   /* THEIR address */
    wr.wr.rdma.rkey        = rkey;          /* THEIR key     */

    ibv_send_wr *bad = nullptr;
    return ibv_post_send(qp, &wr, &bad);
}

Write into the peer’s region at the base address for iteration 0, or at an offset if you want each iteration in its own slot. Either is fine; document which, because the server’s verification has to agree.

Fill with TRD-03 R7’s iteration-encoded pattern so the server can distinguish “the right data arrived” from “some data arrived.”

H3 — Prove the Receiver Was Passive (R3)

Level 1

This requirement is mostly about what the server does not do. Its loop posts nothing and polls nothing during the transfer.

Which raises the practical question the requirement is really about: if the server is not polling, how does it know when to stop waiting and verify? There is no notification — that is the point. You need something outside the RDMA path.

You already have exactly that thing from TRD-05, still open, and used for one byte in TRD-03.

Level 2

The server waits on the connection manager’s DISCONNECTED event, or on a single trailing two-sided SEND from the client after the writes finish. Either is honest, and both keep the completion queue empty during the transfer itself.

/* server, mode=write */
std::printf("onesided: passive (mode=write) — posting no receives, "
            "polling no completions\n");

/* ... wait for the client to signal completion out of band ... */

int reaped = 0;
ibv_wc wc;
while (ibv_poll_cq(cq, 1, &wc) > 0) ++reaped;   /* drain: must be 0 */
std::printf("remote-completions: %d\n", reaped);

size_t bad = verify_pattern(rx_buf, msg_size, iterations - 1);
std::printf("verify: buffer contents %s expected pattern for %u iterations\n",
            bad ? "DO NOT match" : "match", iterations);

Drain the completion queue after the transfer and assert the count is zero. That is stronger than not polling: it proves nothing was there to poll.

Worth pausing on when it works. The server’s process did not execute a single instruction on behalf of a hundred transfers, its completion queue is empty, and its memory contains data it was never told about. That is the property this ladder has been building toward for six rungs.

H4 — RDMA_READ (R4)

Level 1

Structurally identical to H2 with one opcode changed. The conceptual reversal is the thing to hold onto: the scatter-gather list is now a destination.

That reversal has a consequence for your own memory region’s access flags. Work out which flag your local region needs before running it, rather than after reading the error.

Your completion means something stronger here than on a write: the data is present in your buffer and readable. There is no separate notification problem for reads — which is worth noticing, because it is why reads are sometimes preferred despite costing a round trip.

Level 2
wr.opcode              = IBV_WR_RDMA_READ;
wr.wr.rdma.remote_addr = peer.addr;     /* fetch FROM here */
wr.wr.rdma.rkey        = peer.rkey;
/* sge now describes where the data LANDS */

Your local region needs IBV_ACCESS_LOCAL_WRITE, because your own adapter writes into it. It already has that flag if you followed TRD-03 H1; if you registered a send-only buffer without it, the read fails with IBV_WC_LOC_PROT_ERR.

For the server side, write a known pattern into its own buffer before the client connects, so there is something distinctive to retrieve. Verify on the client against that same pattern.

The server is passive here too. Report remote-completions: 0 exactly as in R3.

H5 — The Separate Flag Write (R5)

Level 1

Two posts per iteration, in order: payload, then flag. The ordering guarantee that makes this correct is between the two requests, not within either of them — section 6 of the Prior Knowledge document is precise about the distinction and R5 asks you to restate it.

Decide where the flag lives. It must not overlap the payload, and both sides must agree on the offset without further negotiation, since the handshake is already over.

On the server, the polling loop reads a location the adapter is writing concurrently. Think about what the compiler is entitled to assume about a variable it cannot see being modified, and what that means for a naive while loop.

Level 2
/* Convention: the flag is the last 8 bytes of the advertised region. */
const uint64_t flag_off  = peer.length - sizeof(uint64_t);
const uint64_t flag_addr = peer.addr + flag_off;

/* per iteration, in this order */
post_write(qp, tx_mr, tx_buf, msg_size, peer.addr, peer.rkey, WRID_PAYLOAD);
uint64_t token = iteration + 1;              /* never 0 */
std::memcpy(flag_buf, &token, sizeof token);
post_write(qp, tx_mr, flag_buf, sizeof token, flag_addr, peer.rkey, WRID_FLAG);

Server side:

auto *flag = reinterpret_cast<volatile uint64_t *>(
                 static_cast<char *>(rx_buf) + flag_off);

for (unsigned i = 1; i <= iterations; ++i) {
    while (*flag != i) { /* spin */ }        /* volatile: reread every time */
    std::atomic_thread_fence(std::memory_order_acquire);
    verify_pattern(rx_buf, msg_size, i - 1);
}

volatile stops the compiler hoisting the load out of the loop — without it the loop may read once and spin forever on a stale value. The acquire fence orders your subsequent payload reads after the flag read; the adapter’s write ordering is guaranteed, but your own CPU’s load ordering is not.

Start the token at 1 so a zeroed buffer is never mistaken for iteration 0 having arrived.

For the notes, the explanation R5 wants: write-class work requests within one send queue are totally ordered, so the flag write — a separate message posted after the payload write — cannot be placed before the payload write completes. Observing the flag therefore implies the payload is entirely present.

H6 — Write With Immediate (R6)

Level 1

One opcode change from H2, plus a field. The field is four bytes and travels in network byte order like everything else that crosses machines.

The server side is not new work — it is TRD-03’s receive-and-poll loop, unchanged, because this opcode consumes a receive and produces a completion exactly as a SEND does. If you deleted that code when writing R3’s passive server, you need it back for this mode.

The completion’s opcode will not be the one you posted. Look at what the receiving side actually reports and handle it explicitly.

Level 2
wr.opcode   = IBV_WR_RDMA_WRITE_WITH_IMM;
wr.imm_data = htobe32(iteration);

Server, having posted receives beforehand exactly as in TRD-03:

ibv_wc wc;
if (wait_completion(cq, &wc, 10) == 1 && wc.status == IBV_WC_SUCCESS) {
    if (wc.opcode == IBV_WC_RECV_RDMA_WITH_IMM) {
        uint32_t iter = be32toh(wc.imm_data);
        verify_pattern(rx_buf, msg_size, iter);
        post_recv(...);                      /* replenish, as in TRD-03 R6 */
        ++remote_completions;
    }
}

The receiving opcode is IBV_WC_RECV_RDMA_WITH_IMM, not IBV_WC_RDMA_WRITE. Note also that byte_len on this completion reports the bytes written by the RDMA operation, which is useful and is not true of a plain write, because a plain write produces no remote completion at all.

Post receives before the client starts, and replenish before the peer can send again — TRD-03 R6’s ordering rule applies unchanged. Getting it wrong here costs 655 ms per retry rather than 0.64 ms, because the connection manager fixed the timer.

H7 — Demonstrate That Last-Byte Polling Is Wrong (R7)

Level 1

Implement it as written — the server polls the final byte of the payload region and treats a change as arrival. Same volatile consideration as H5.

Then run it twice, at a small size and at the largest your region allows, and record both outcomes honestly. Expect it to pass. The requirement is not to make it fail; it is to understand why a passing test proves nothing.

To make the failure more likely if you want to try: use the largest size you can, run many iterations, and load the machine. You may still not see it, and that is the lesson rather than an obstacle to it.

Level 2
auto *last = reinterpret_cast<volatile unsigned char *>(
                 static_cast<char *>(rx_buf) + msg_size - 1);
unsigned char want = expected_last_byte(iteration);
while (*last != want) { /* spin */ }
size_t bad = verify_pattern(rx_buf, msg_size, iteration);   /* may be non-zero */

Record something of this shape in docs/onesided-notes.md:

mode=lastbyte, size=64:      100 iterations, 0 mismatches
mode=lastbyte, size=1048576: 100 iterations, 0 mismatches

Both passed. This does not make the technique correct. Byte placement
order within a single RDMA write is not guaranteed — RC guarantees
ordering between messages, not within one. A large write may be
segmented and nothing requires the final segment to land last. My test
did not provoke the reordering; on a hardware adapter with real
segmentation, under load, it eventually will, and the symptom is a
reader observing a torn buffer with no error reported anywhere.

The general habit is the thing to take: a test that passes establishes that you did not provoke the failure, which is different from establishing that the failure cannot occur. Whether that difference matters depends on whether the correctness argument comes from the specification or from the observation — and here it comes from neither, because the specification says the opposite.

H8 — Access Control Failure (R8)

Level 1

Corrupting the key is one line. The requirement is the diagnostic, because the error you get back names nothing.

Reuse TRD-03’s restricted error printing — only four completion fields are valid on a failure — and TRD-03’s queue-pair state readback, which will show the connection is finished.

The message should name both access gates, because the error cannot distinguish them and a reader hitting this for real needs to check both.

Level 2
uint32_t rkey = peer.rkey;
if (opt_bad_rkey) {
    rkey ^= 0xdeadbeefu;
    std::printf("bad-rkey: using 0x%08x instead of 0x%08x\n", rkey, peer.rkey);
}

On the failure, alongside TRD-03 R5’s four-field error line:

fprintf(stderr,
  "  remote_addr=0x%016" PRIx64 " rkey=0x%08x length=%zu\n"
  "  REM_ACCESS_ERR does not say which gate refused. Check both:\n"
  "    1. the peer's qp_access_flags (set at INIT, or via rdma_conn_param)\n"
  "    2. the peer's memory region flags (set at ibv_reg_mr)\n",
  remote_addr, rkey, msg_size);

Expect IBV_WC_REM_ACCESS_ERR. The queue pair will be in the error state afterwards — TRD-03 section 9 — so exit rather than attempting another operation.

H9 — Bounded Outstanding Reads (R9)

Level 1

If you post one read at a time and wait for each completion, you cannot exceed the limit and the requirement is satisfied by reporting it. That is a legitimate implementation.

The value comes from two places depending on which path established the connection, and you set both at some point — one in TRD-02, one in TRD-05. They are the same constraint under different names.

Note which of the two device attributes bounds the initiating side; there are two and they are not interchangeable.

Level 2
uint32_t depth = std::min<uint32_t>(1, da.max_qp_init_rd_atom);
std::printf("onesided: mode=%s iterations=%u size=%zu max_outstanding_reads=%u\n",
            mode_name, iterations, msg_size, depth);

max_qp_init_rd_atom bounds reads you initiate; max_qp_rd_atom bounds reads you serve. Through the connection manager these are initiator_depth and responder_resources in rdma_conn_param, which TRD-05 H8 populated.

To confirm the limit is real, temporarily post two reads without reaping between them and watch the transport error. Then remove it — TRD-07 pipelines against this bound deliberately and it is worth having seen what exceeding it does first.

H10 — Teardown, Regressions, Leaks (R10)

Level 1

Teardown needs no new work. The RAII layer already owns every resource this rung uses, which is the return on TRD-04 becoming visible — a new program with new operations and no cleanup code at all.

Both regression suites should pass without being touched, because this rung adds a program rather than changing one. If either fails, look for something shared that you modified — a header, the connection setup you factored out, the pattern helpers.

Level 2
./scripts/trd-03-tests.sh --dev rxe0 --gid 3 --peer 10.0.0.1 --ssh you@10.0.0.1
./scripts/trd-05-tests.sh --dev rxe0 --gid 3 --peer 10.0.0.1 --ssh you@10.0.0.1
valgrind --leak-check=full ./build/limen_onesided -d rxe0 --mode write -n 20 10.0.0.1
valgrind --leak-check=full ./build/limen_onesided -d rxe0 --mode read  -n 20 10.0.0.1
valgrind --leak-check=full ./build/limen_onesided -d rxe0 --bad-rkey -n 5 10.0.0.1

The third is the one worth watching: it exits through an error path with a queue pair in the error state, and that path is the least exercised.

Debugging This TRD

QuestionInstrument
REM_ACCESS_ERR and the flags look rightPrint all four fields from section 3 and check whose each is. A local key in the rkey field is the most common cause and looks entirely normal in source.
Did the write actually land?Have the server dump the first sixteen bytes of its buffer after the run. Bytes present with no completion anywhere is the demonstration working.
Server spins forever on the flagMissing volatile — the compiler hoisted the load. Check the disassembly if unsure.
Immediate mode hangsNo receive posted. It consumes one. 655 ms per retry now, so it looks like a hang rather than a stall.
Read returns zerosServer never wrote its buffer, or you read from the wrong offset. Have the server print what it staged.
Wrong data, no errorAddress arithmetic. Print remote_addr per iteration and check it against the advertised base and length.
Is anything on the wire?sudo tcpdump -i <iface> -n udp port 4791 -c 20 — the same capture as TRD-00 R4, now showing one-sided traffic.
Does the reference still work?ib_write_bw -d rxe0 and ib_read_bw -d rxe0. Same discipline as every rung: establish the fabric before debugging yourself.
The most useful check on this rung

Print the four address-and-key fields — local address, local key, remote address, remote key — on every posted operation while developing. Nearly every defect here is one of them holding a value that belongs to the other machine, and that mistake is invisible in source because both are just integers.

The Tool Boundary

This rung rewards suspicion of success. An operation that completes with IBV_WC_SUCCESS proves the adapter accepted it, not that it did what you meant — a write to a wrong-but-registered address succeeds. Verify contents, not completions.

An AI assistant is appropriate for reviewing code once it works, clarifying a concept a document left unclear, and grading comprehension answers. It is not appropriate for writing or debugging the implementation.
