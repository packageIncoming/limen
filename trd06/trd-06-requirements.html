TRD-06: One-Sided Operations

Requirements — Limen RDMA Transport Project
Depends on: TRD-05  |  Difficulty: Medium  |  Estimated: 3–4 sessions

Objective

Build limen_onesided: a two-node program that writes directly into a peer’s memory and reads directly out of it, using the address and remote key exchanged by TRD-05’s handshake. It must demonstrate that the peer’s software is not involved, implement two correct completion-detection mechanisms, and demonstrate that the obvious third one is broken.

What This Is Not

No atomics. Compare-and-swap and fetch-and-add complete the one-sided family and are not needed here.

No changes to connection establishment. TRD-05’s connection manager path is reused unchanged, and its ConnInfo already carries everything this rung needs.

No measurement. One-sided operations should be dramatically cheaper than two-sided ones on real hardware and are not on the software provider. TRD-08 is where that becomes visible; drawing performance conclusions from this rung is drawing them from the wrong fabric.

No flow control beyond what TRD-03 already had. R6 reintroduces the receiver-not-ready condition and handles it the same way: post enough receives.

Technical Requirements

R1 — Consume the Handshake Descriptor

Use the ConnInfo delivered by TRD-05’s handshake — the peer’s buffer address, remote key, and length — as the target of every one-sided operation in this rung.

Before posting anything, validate it: a zero address, a zero key, or a length shorter than the message size is a fatal configuration error, reported and exiting 3. Those values crossed a network and were byte-order converted; a silent failure here surfaces as a remote access error that implicates the wrong thing.

Print the peer: line as TRD-05 did. It is now load-bearing rather than informational.

Stuck? → Hints H1

R2 — RDMA_WRITE

Post an IBV_WR_RDMA_WRITE naming your local buffer through a scatter-gather entry and the peer’s address and key through wr.rdma. Signal it, reap the completion, and report it.

Bound the target: the write must not exceed the peer’s advertised length. Nothing in the API checks this for you, and exceeding it produces a remote access error rather than a bounds message.

Fill the payload with the iteration-encoded pattern from TRD-03 R7, so the server can verify content rather than merely presence.

Stuck? → Hints H2

R3 — Prove the Receiver Was Passive

In --mode write the server must post no receive work requests and poll no completions during the transfer. It announces this, waits for the client to finish, then verifies its buffer contents.

Both sides print remote-completions: 0. The server’s zero is the requirement: its completion queue was empty throughout while its memory was being written.

This is the rung’s central demonstration. Two-sided transfer required the receiver to post, poll, and process. Here the receiver’s software executed nothing on behalf of the transfer and was never informed it occurred — and its memory changed anyway.

Stuck? → Hints H3

R4 — RDMA_READ

In --mode read, post an IBV_WR_RDMA_READ that fetches the peer’s buffer into your local one. Verify the retrieved contents against a pattern the server wrote locally before the transfer.

Note the reversal: the scatter-gather list is now where data is deposited. Your local region requires IBV_ACCESS_LOCAL_WRITE, since your own adapter writes into it. Your completion means the data has arrived and is readable.

The server remains passive here too, and reports it.

Stuck? → Hints H4

R5 — Correct Notification: the Separate Flag Write

In --mode flag, post two requests per iteration: the payload write, then a second small RDMA_WRITE to a distinct flag location carrying the iteration number. The server polls the flag, and on seeing it verifies the payload.

The flag must live in a region of the peer’s buffer that does not overlap the payload. Advertise its offset as a fixed convention — the last eight bytes of the advertised region is sufficient — and document it.

This is correct because write-class work requests within a send queue are totally ordered against one another,[5] so the flag cannot land before the payload it follows. Record in docs/onesided-notes.md why that guarantee makes the pattern safe, in your own words.

Stuck? → Hints H5

R6 — Correct Notification: Write With Immediate

In --mode imm, post IBV_WR_RDMA_WRITE_WITH_IMM carrying the iteration number as immediate data. The server polls its completion queue and finds an IBV_WC_RECV_RDMA_WITH_IMM carrying that value.

This opcode consumes a receive work request on the peer.[2][3] The server must post receives before the client begins, and replenish them, exactly as in TRD-03. Failing to do so produces a receiver-not-ready condition — and TRD-05 R8 recorded that the connection manager fixed the minimum RNR timer at 655 ms, so the resulting stall is far longer than it was in TRD-03.

Both sides now report non-zero remote-completions. Contrast that with R3 and record the comparison: this mode is a two-sided operation wearing a one-sided opcode.

Stuck? → Hints H6

R7 — Demonstrate That Last-Byte Polling Is Wrong

In --mode lastbyte, the server polls the final byte of the payload region and treats a change as arrival, then verifies the whole buffer. The client writes with no flag and no immediate.

Run it at a small message size and at the largest size your region allows, and record both results in docs/onesided-notes.md.

It may well pass. On a short message that fits a single packet, and on an idle software fabric, the bytes will usually arrive in order. That is precisely the danger, and reporting it honestly is the requirement: record what you observed, then record why the pattern is unsound regardless. Byte placement order within a single message is not guaranteed,[1] so a passing test here demonstrates only that you did not provoke the failure.

Write two to four sentences on why a technique that passes your test is nonetheless wrong to ship, and what the failure would look like when it eventually occurs.

Stuck? → Hints H7

R8 — Access Control Failure

With --bad-rkey, corrupt the peer’s remote key before posting. The operation must fail with IBV_WC_REM_ACCESS_ERR, reported through TRD-03 R5’s restricted error path and TRD-03 R10’s queue-pair state check.

The error does not distinguish between the two access gates — queue-pair flags and memory-region flags — so the diagnostic must print what it can: the key used, the remote address, the length, and a reminder of both gates from section 4 of the Prior Knowledge document.

Exit 5. The queue pair will be in the error state and the connection is finished; do not attempt recovery.

Stuck? → Hints H8

R9 — Bounded Outstanding Reads

Do not post more concurrent RDMA_READ operations than the negotiated depth permits. That depth is max_rd_atomic, set at the RTS transition in TRD-02 or supplied as initiator_depth through the connection manager in TRD-05, and bounded by max_qp_init_rd_atom from the device attributes recorded in TRD-00 R7.

Print the effective limit alongside the mode line. If your implementation posts one read at a time, say so and state the limit anyway — knowing the constraint exists is the requirement, and TRD-07 will pipeline against it.

Stuck? → Hints H9

R10 — Teardown, Regressions, Leaks

Teardown is TRD-05’s, unchanged — the RAII layer already covers every resource this rung uses.

Regressions: the TRD-03 suite must pass against limen_pingpong, and the TRD-05 suite must pass against it too. This rung adds a program rather than modifying one, so both should pass untouched; if either fails, something shared was changed that should not have been.

Leak checks: zero bytes definitely lost on the write path, the read path, and the --bad-rkey failure path.

Stuck? → Hints H10

Deliverables

  • src/limen_onesided.cpp, reusing the connection setup from TRD-05 rather than duplicating it.
  • An updated CMakeLists.txt building all four programs.
  • scripts/trd-06-tests.sh, executable, passing.
  • docs/onesided-notes.md recording: the R5 explanation of why flag ordering is safe; the R7 results at both sizes with the explanation of why the technique is unsound regardless; and a short comparison of the three notification mechanisms naming which you would choose for a transport and why.
  • Written answers to the comprehension questions.

What Comes Next

TRD-07 makes these operations efficient: inline data for small payloads, unsignaled completions with periodic signalling, completion-queue moderation, and event-driven reaping. Every one of those trades something, and the trades are clearest on one-sided operations because there is no remote processing to hide behind.

The outstanding-read limit reported in R9 becomes a pipelining bound there, and the three notification mechanisms compared in this rung’s notes become a measured comparison in TRD-08.
