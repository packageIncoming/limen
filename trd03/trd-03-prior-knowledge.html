TRD-03: Two-Sided Transfer

Prior Knowledge — Limen RDMA Transport Project
Depends on: TRD-02  |  Difficulty: Medium-High  |  Estimated: 3–5 sessions

1   Where This Fits

TRD-02 left you with a connected queue pair in RTS on both nodes, verified by readback and carrying no traffic. The registered buffer from TRD-01 has been dragged through two rungs unused.

This rung moves bytes. You will post receive requests, post send requests, poll a completion queue, interpret what comes out of it, and run a ping-pong loop that verifies its own payload. At the end you will have a working RDMA transfer and a program that can tell you why a transfer failed.

You will also, deliberately, break it. The receiver-not-ready condition is the defining behavioural fact of two-sided RDMA, and section 8 requires you to provoke it on purpose — because meeting it by accident, in a program you believe is correct, is how people conclude the fabric is broken.

This is the first rung where a mistake made earlier surfaces. Crossed sequence numbers from TRD-02 produce their symptom here, not there.

2   The Posting Model

Nothing in verbs sends. You describe work and hand the description to the adapter; the adapter performs it and later reports that it finished. Posting and completion are separate events, and everything about the API's shape follows from that separation.

Figure 1 — The post-and-complete cycle. Steps 3 and 4 are separated by an unbounded interval.

The consequence stated in the caption is the rule that governs every buffer in an RDMA program: a buffer named in a posted work request may not be read, written, or freed until a completion for that request has been retrieved.[1] The adapter may be reading it at any moment in between, and neither the compiler nor the operating system knows that.

3   Describing a Buffer: the Scatter-Gather Entry

struct ibv_sge {
    uint64_t addr;    /* virtual address                      */
    uint32_t length;  /* bytes                                */
    uint32_t lkey;    /* local key from the memory region     */
};

Three fields, and the third is where TRD-01 pays off. The local key is the value ibv_reg_mr() returned, and it is how the adapter verifies that this address belongs to a registered region in the right protection domain. An address without a matching key is refused.

A work request carries an array of these, which is what "scatter-gather" names: a send gathers from several buffers into one message; a receive scatters one message into several buffers. The array length is bounded by the max_send_sge and max_recv_sge values the provider granted in TRD-02 — the granted values, not the ones you requested.

Limen uses a single entry throughout this rung. Multiple entries change nothing conceptually and are worth knowing exist.

4   Posting a Receive

struct ibv_recv_wr {
    uint64_t             wr_id;    /* your identifier, returned in the completion */
    struct ibv_recv_wr  *next;     /* linked list, or NULL                        */
    struct ibv_sge      *sg_list;
    int                  num_sge;
};

int ibv_post_recv(struct ibv_qp *qp, struct ibv_recv_wr *wr,
                  struct ibv_recv_wr **bad_wr);

A posted receive is a promise of a landing place. It says: when a message arrives, put it here. It names no peer and no expected size — any incoming send consumes the next posted receive, in order.

wr_id is an opaque 64-bit value the adapter does not interpret. It comes back in the completion and it is the only link between a completion and the request that caused it. Use it to identify which buffer, which slot, or which operation — anything you need to know when the completion arrives, because the completion tells you nothing else about the request.

Requests may be chained through next and posted in one call. Posting stops at the first request that fails immediately, and the failing one is returned through bad_wr.[1]

The receive must exist before the send arrives

Not before the send is posted — before it arrives. There is no buffering. If a message arrives at a queue pair with no posted receive, it cannot be delivered, and the consequences are section 8.

Size mismatch

A posted receive larger than the incoming message is fine; byte_len in the completion reports what actually arrived. A posted receive smaller than the incoming message fails on both sides: the receiver gets IBV_WC_LOC_LEN_ERR and the sender gets IBV_WC_REM_INV_REQ_ERR.[4] Since the receiver cannot know the size in advance, the standard answer is to post receives at the maximum message size the protocol allows.

5   Posting a Send

struct ibv_send_wr {
    uint64_t             wr_id;
    struct ibv_send_wr  *next;
    struct ibv_sge      *sg_list;
    int                  num_sge;
    enum ibv_wr_opcode   opcode;
    unsigned int         send_flags;
    /* ... opcode-specific unions: rdma, atomic, ud ... */
};

int ibv_post_send(struct ibv_qp *qp, struct ibv_send_wr *wr,
                  struct ibv_send_wr **bad_wr);

Two fields beyond the receive form. The opcode is IBV_WR_SEND here; IBV_WR_RDMA_WRITE and IBV_WR_RDMA_READ arrive in TRD-06 and use the same structure with its union populated.

Send flags

FlagEffect
IBV_SEND_SIGNALEDGenerate a completion for this request. Relevant only when the queue pair was created with sq_sig_all = 0.[1]
IBV_SEND_INLINECopy the payload into the work request itself rather than having the adapter fetch it. The local key is not checked, and the buffer is reusable immediately. Bounded by max_inline_data. TRD-07.
IBV_SEND_FENCEDo not begin this request until all prior requests on this queue have completed. Valid only on reliable-connected queue pairs.
IBV_SEND_SOLICITEDMark the message so the receiver's completion raises a solicited event. Relevant to event-driven reaping in TRD-07.
TRD-02 zeroed the initialization structure before creating the queue pair, which set sq_sig_all to 0. Sends therefore produce no completion unless you set IBV_SEND_SIGNALED. An unsignalled send that succeeds is invisible — the transfer happens, no completion appears, and a loop waiting for one waits forever. This is not a bug in the fabric; it is the consequence of a field you set two rungs ago. TRD-07 exploits it deliberately; here, signal every send.

Receives are always signalled

There is no unsignalled receive. Every consumed receive request produces a completion, because a completion is the only mechanism by which you learn that data arrived. The asymmetry with sends is not an inconsistency — a send's completion tells you something you could in principle infer, while a receive's completion is the arrival notification itself.

6   Polling for Completions

int ibv_poll_cq(struct ibv_cq *cq, int num_entries, struct ibv_wc *wc);

Fills up to num_entries completions into your array and returns the number it found. Zero means the queue was empty — not an error, and by far the most common return. A negative value is a failure.[2]

Two consequences worth internalising. First, polling is non-blocking, so waiting for a completion means looping. Second, each polled completion is removed from the queue permanently and cannot be returned to it.[2] If you poll a completion and then discard it because it was not the one you wanted, it is gone.

struct ibv_wc {
    uint64_t              wr_id;       /* the identifier you chose          */
    enum ibv_wc_status    status;      /* IBV_WC_SUCCESS or a failure       */
    enum ibv_wc_opcode    opcode;      /* IBV_WC_SEND, IBV_WC_RECV, ...     */
    uint32_t              vendor_err;  /* provider-specific detail          */
    uint32_t              byte_len;    /* bytes transferred                 */
    union { __be32 imm_data; uint32_t invalidated_rkey; };
    uint32_t              qp_num;
    uint32_t              src_qp;      /* UD only                           */
    int                   wc_flags;
    uint16_t              pkey_index;
    uint16_t              slid;
    uint8_t               sl;
    uint8_t               dlid_path_bits;
};
On an error completion, most of this structure is garbage

When status is anything other than IBV_WC_SUCCESS, only four fields are valid: wr_id, status, qp_num, and vendor_err.[2] opcode and byte_len in particular are undefined, and printing them in an error path produces confident nonsense — a byte count of zero for a transfer that partly happened, or an opcode naming an operation you never posted. Check status first and branch; never format the whole structure uniformly.

byte_len is meaningful on a receive completion, where it reports how much arrived. On a send completion it carries nothing useful: the request named the length and the completion adds no information.

Completion status

ibv_wc_status_str() converts a status to a printable string, which saves writing a table. The ones this rung can produce:

StatusMeaning
IBV_WC_SUCCESSThe only non-error value. Zero.
IBV_WC_RNR_RETRY_EXC_ERRThe receiver had no posted receive and the retry budget ran out.[5] Section 8.
IBV_WC_RETRY_EXC_ERRThe peer did not acknowledge within the timeout, repeatedly. After a first successful message this usually means the peer is gone; as the first failure it frequently means crossed sequence numbers from TRD-02.
IBV_WC_LOC_LEN_ERRThe posted receive was too small for the incoming message.[4]
IBV_WC_REM_INV_REQ_ERRThe responder rejected the message. The sender's counterpart to the receiver's length error.
IBV_WC_LOC_PROT_ERRA local protection violation — usually a wrong local key, or an address outside the registered region.
IBV_WC_WR_FLUSH_ERRThis request was outstanding when the queue pair entered the error state.[6] A consequence, not a cause. Section 9.

7   The Ping-Pong

Both sides post their receives before either sends. The client sends first. Each side then loops: reap a receive completion, verify the payload, post a fresh receive, send a reply.

Figure 2 — One round. The replacement receive is posted before the reply is sent.

The ordering inside the loop is the part worth stating explicitly: post the replacement receive before sending the reply. Sending first opens a window in which the peer's answer can arrive at a queue pair with no receive posted — and on a fast link that window is wide enough to hit. The rule generalises: replenish receives before doing anything that could cause the peer to send.

Posting several receives up front rather than one is the same defence with more slack. A depth of N means the peer may run N messages ahead of your replenishment before the condition can occur.

8   Receiver Not Ready

When a message arrives at a queue pair with no posted receive, the responder returns an RNR negative acknowledgement — receiver not ready. The sender waits min_rnr_timer and tries again, up to rnr_retry times. Both values were set at the RTR transition in TRD-02.

TRD-02 had you set rnr_retry = 7. The value 7 means retry indefinitely.[5] A send to a peer with no posted receive therefore never fails — it retries forever, and your program hangs in the polling loop with no completion, no error, and no diagnostic. This is the single most confusing failure available in RDMA, and it is a configuration choice rather than a fault.

Setting rnr_retry to a finite value converts the hang into an IBV_WC_RNR_RETRY_EXC_ERR completion, which is a far better failure: it names itself. The tradeoff is real in both directions. Infinite retry is correct for a protocol where the peer is expected to replenish receives and a transient shortage should be absorbed. Finite retry is correct for a protocol where a shortage means something is wrong and you want to be told.

Neither value is a substitute for the actual answer, which is flow control you design. The peer must not be permitted to send more messages than you have receives posted, and nothing in RDMA enforces that. Credit schemes are the usual mechanism: each side tracks how many receives the peer has outstanding and refuses to exceed it, replenishing the count in message headers. Limen does not build one — the ping-pong is self-limiting because each side sends only in response — but every real transport does, and the reason is exactly this.

The general point

RDMA gives you ordered, reliable delivery of individual messages and nothing else. Flow control, framing, message boundaries above the transfer, and knowing when a buffer is safe to reuse are all yours. This is the price of removing the kernel: everything the kernel was doing on your behalf, you now do or do without.

9   What an Error Completion Does to the Queue Pair

On a reliable-connected queue pair, a completion with an error status is not a per-request failure. The queue pair transitions to the error state and cannot be used again.[3] Recovery requires transitioning back through RESET and repeating the entire bringup on both sides — the whole of TRD-02, including a fresh parameter exchange.

Every work request outstanding when that happens is completed with IBV_WC_WR_FLUSH_ERR.[6] So one real failure produces a burst of completions, of which exactly one names the cause and the rest are debris. The first non-success status is the diagnosis; every flush error after it is noise. A program that reports the last error it saw reports the noise.

The completion queue itself survives and stays usable.[3] Only the queue pair dies. If several queue pairs share one completion queue, the others are unaffected.

Querying the queue pair with ibv_query_qp() after an error completion confirms IBV_QPS_ERR. R9 requires that check, because it is the difference between "the transfer failed" and "the connection is gone," and those call for different responses.

10   Buffer Ownership

Between posting and reaping, the buffer belongs to the adapter.[1] Reading it may return a partially transmitted state; writing it may transmit data you did not intend; freeing it hands the adapter a pointer into freed memory.

Nothing enforces this. There is no borrow checker, no lock, and no diagnostic — the compiler sees an ordinary buffer and the operating system sees pinned pages. Violations produce corrupted payloads that appear intermittently and only under load, which is the worst available failure profile.

Three practical rules for this rung:

  • Use separate buffers for sending and receiving, or separate regions of one buffer. Sharing one buffer for both directions works in a strict ping-pong and breaks the moment anything overlaps.
  • Do not refill a send buffer for iteration n+1 until the completion for iteration n has been reaped.
  • IBV_SEND_INLINE is the exception — the payload is copied into the work request, so the buffer is free immediately.[1] That is TRD-07.

This is also the second half of the argument for TRD-04. Ownership that the type system does not express is ownership you enforce by remembering, and this program now has enough moving parts that remembering is not sufficient.

12   What Is Deliberately Left Out

No flow control. The ping-pong is self-limiting because each side sends only in reply, which is exactly the property a real protocol does not have. Credit-based flow control is named in section 8 and not built.

No pipelining. One message is outstanding at a time, so the link sits idle during every round trip. TRD-07 addresses this and TRD-08 measures what it was costing.

One scatter-gather entry per request, one buffer, no pooling. Everything is signalled, so every send costs a completion — deliberately, since TRD-07 is where unsignalled sends stop being a trap and become a technique.

Nothing here is one-sided. Both peers are running, both post, both poll. The remote key printed in TRD-01 remains unused until TRD-06, which is the rung where the remote CPU stops participating.

13   Further Reading

Read before starting:

  • ibv_post_send(3)[1] — the flag table, the opcode list, and the buffer-reuse rule stated normatively. The most important page for this rung.
  • ibv_poll_cq(3)[2] — the return convention and, critically, the list of which completion fields are valid when the status is not success.

Read while implementing:

  • ibv_post_recv(3)[1] — short; the receive form of the same model.
  • rc_pingpong.c, the posting and polling loop[7] — the fourth read of this file. It is a correct implementation of exactly this rung, including the receive replenishment ordering from section 7.

Reference as needed:

  • RDMAmojo on ibv_post_send[5] and ibv_poll_cq[3] — the comment threads on both pages are unusually valuable, because they are people hitting exactly the failures in section 11 and being told what they mean.
  • InfiniBand Architecture Specification, Volume 1, ch. 9–11[8] — normative on completion semantics and error handling. For settling questions, not for learning.
