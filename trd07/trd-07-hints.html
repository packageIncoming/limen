TRD-07: Completion Efficiency

Hints — Limen RDMA Transport Project
Level 1 = nudge  |  Level 2 = stronger push  |  Try Level 1 for 15+ minutes before escalating

Level 1 points at the right place. Level 2 names the mechanism.

Build in this order: R1 first, so every subsequent change is visible in the config line; then R2 through R5, which are independent and easy; then R6 through R8 together, because the event path is one mechanism and implementing it piecewise produces a hang you cannot attribute. Do not start with R6.

H1 — Report the Effective Configuration (R1)

Level 1

Write this first. Every other requirement adds a field to it, and having the line print before you implement the thing it describes means you always know what is actually in force.

The distinction the requirement cares about is requested versus effective. Three of the five settings can differ from what you asked for — one is granted by the provider, one is clamped against a device limit, one may be refused entirely. Print what is true, not what was typed.

A small configuration struct populated once after the queue pair exists, then printed, keeps this from being scattered.

Level 2
struct EffectiveConfig {
    bool     inline_on;
    uint32_t inline_max;        /* GRANTED, from init.cap after create_qp */
    unsigned signal_every;
    unsigned pipeline;          /* clamped to granted max_send_wr        */
    const char *reap;           /* "poll" or "event"                     */
    const char *moderation;     /* "off", "unavailable", or "16:8"       */
};

std::printf("config: inline=%s(max=%u) signal_every=%u pipeline=%u "
            "reap=%s moderation=%s\n",
            cfg.inline_on ? "on" : "off", cfg.inline_max,
            cfg.signal_every, cfg.pipeline, cfg.reap, cfg.moderation);

--report-config exits before connecting, so populate what you can without a peer — which means creating the context, protection domain, and queue pair, but not the connection. That is enough for the granted inline limit and the clamped depth.

H2 — Inline Data (R2)

Level 1

Two places. The capability is requested in the same structure TRD-02 used to size the queues, before creation; the flag is set per send.

The trap is assuming you got what you asked for. Some providers grant more, some grant zero unless the field is set, and some grant zero regardless. Read it back from the structure the creation call wrote into — the same write-back behaviour TRD-02 R2 made you report.

The fallback matters. A payload larger than the granted limit must send normally rather than fail, and the requirement says report it once rather than every iteration.

Level 2
init.cap.max_inline_data = 256;              /* request, before create_qp  */
/* ... ibv_create_qp ... */
cfg.inline_max = init.cap.max_inline_data;  /* GRANTED, may differ        */
bool use_inline = opt_inline && len <= cfg.inline_max;
wr.send_flags = (signal ? IBV_SEND_SIGNALED : 0)
              | (use_inline ? IBV_SEND_INLINE : 0);

if (opt_inline && !use_inline && !warned_inline) {
    std::fprintf(stderr, "inline requested but payload %zu exceeds granted %u "
                         "— falling back to normal sends\n", len, cfg.inline_max);
    warned_inline = true;
}

Note what inline does to R4: the buffer is free the instant ibv_post_send returns, because the payload was copied into the descriptor.[1] Your reuse tracking should skip the covered-sequence check entirely for inline sends, and getting that wrong costs you nothing in correctness but forfeits the benefit.

H3 — Periodic Signalling (R3)

Level 1

One modulus, one flag. The mechanical part takes five minutes.

Two details are not mechanical. The last send of a run must be signalled regardless of where it falls in the period, or the run ends with work outstanding that nothing will ever report. And the period must be validated against the send queue depth at parse time — the warning in R3 explains why, and discovering it at runtime means an ENOMEM from a call whose every prior invocation succeeded.

Level 2
bool signal = (i % cfg.signal_every == 0) || (i == iterations - 1);

Validation, after the queue pair exists so the granted depth is known:

if (cfg.signal_every >= granted_max_send_wr) {
    std::fprintf(stderr,
        "signal-every %u must be less than the send queue depth %u\n"
        "  completions are what free send queue entries; a longer period\n"
        "  fills the queue and ibv_post_send returns ENOMEM\n",
        cfg.signal_every, granted_max_send_wr);
    return 1;
}

A period of at most a quarter of the depth is a comfortable rule. At 16 over 1000 iterations expect about 63 send completions, and reporting that count is how the suite confirms the flag did anything.

H4 — Buffer Reuse Under Periodic Signalling (R4)

Level 1

This is where the correctness risk lives. With signalling suppressed you know less than before, and the question is what a completion still tells you.

The property to lean on is in §4 of the Prior Knowledge document: send-queue requests complete in order. Work out what a completion for request k establishes about requests before k, and the tracking falls out as a single integer.

Buffers: you need at least as many as the signalling period, because that is how many can be uncovered at once. A fixed array indexed by sequence number modulo its size is sufficient and is what the requirement asks for.

Level 2
uint64_t posted  = 0;     /* next sequence number to post          */
uint64_t covered = 0;     /* highest sequence a completion covers   */
const size_t NSLOT = cfg.signal_every * 2;   /* headroom            */

/* before posting sequence `posted`, ensure its slot is free */
while (posted >= covered + NSLOT) {
    ibv_wc wc;
    if (ibv_poll_cq(cq, 1, &wc) > 0) {
        if (wc.status != IBV_WC_SUCCESS) { /* R10 error path */ }
        covered = wc.wr_id;      /* wr_id carries the sequence number */
    }
}
void *buf = slot(posted % NSLOT);
/* ... fill and post with wr_id = posted ... */
++posted;

Encode the sequence number directly in wr_id. That is what makes covered = wc.wr_id correct in one line, and it is the payoff for the identifier scheme TRD-03 H2 made you design deliberately.

For inline sends, skip the wait entirely — the buffer is already free:

if (!use_inline) { /* the while loop above */ }

Verify at several periods before trusting it. A reuse bug produces corruption only when the ring wraps before a completion arrives, which needs both a long run and a high rate. Run a thousand iterations at period 16 and depth 8 and confirm mismatches=0; a bug here that survives testing is the same profile as TRD-06’s last-byte trap.

H5 — Pipelining (R5)

Level 1

If R4 is correct, this is nearly free — the covered-sequence tracking already permits several outstanding requests. Pipelining is choosing to let it.

Two bounds, and they are not the same number. One you have known since TRD-02; the other you met in TRD-06 §5 and it is far smaller. Clamp and report both if the program supports both operation types.

Level 2
cfg.pipeline = std::min<unsigned>(opt_pipeline, granted_max_send_wr);
unsigned read_depth = std::min<unsigned>(cfg.pipeline, negotiated_max_rd_atomic);

Then bound the posting loop by outstanding count rather than by slot availability:

while (posted - covered >= cfg.pipeline) { /* reap one */ }

Writes and sends pipeline to the send-queue depth — potentially hundreds. Reads are capped at the negotiated atomic depth, often 16 and 1 in this ladder’s configuration. Using the write bound for reads produces a transport error and a dead queue pair, and the error names neither limit.

H6 — Event-Driven Reaping (R6)

Level 1

Read §6 of the Prior Knowledge document completely before writing anything, then read the worked example in ibv_get_cq_event(3)[3] line by line. That example is the shape; §6 is an annotation explaining why each line is where it is.

Four rules, and each corrects a distinct failure. Getting three of four right produces a program that works for a while and then stops, which is the hardest possible thing to debug. Write all four before running it once.

The channel is passed to the completion-queue creation call, in the parameter TRD-02 filled with a null pointer. That means the channel must exist before the completion queue, and must outlive it — a declaration-order question your TRD-04 layer already knows how to answer.

Level 2
comp_ch_ = ibv_create_comp_channel(ctx.get());
cq_      = ibv_create_cq(ctx.get(), depth, nullptr, comp_ch_, 0);
ibv_req_notify_cq(cq_, 0);        /* arm BEFORE anything can complete */

The loop, with R8’s guard already in place because adding it later means writing the bug first:

static int reap_event(ibv_cq *cq, ibv_comp_channel *ch,
                      ibv_wc *wc, int n, Stats &st, int timeout_sec)
{
    int got = ibv_poll_cq(cq, n, wc);
    if (got != 0) return got;                    /* fast path */

    if (ibv_req_notify_cq(cq, 0)) return -1;     /* arm */

    got = ibv_poll_cq(cq, n, wc);                /* THE RACE-CLOSING POLL */
    if (got != 0) { ++st.race_polls_hit; return got; }

    pollfd p{ ch->fd, POLLIN, 0 };
    if (poll(&p, 1, timeout_sec * 1000) <= 0) return -2;   /* exit 8 */

    ibv_cq *ev_cq; void *ev_ctx;
    if (ibv_get_cq_event(ch, &ev_cq, &ev_ctx)) return -1;
    ++st.events_received;
    ++st.unacked;

    if (ibv_req_notify_cq(cq, 0)) return -1;     /* RE-ARM: it is disarmed */

    got = ibv_poll_cq(cq, n, wc);                /* DRAIN */
    if (got == 0) ++st.empty_events;             /* legal, not an error */
    return got;
}

Make the channel descriptor non-blocking if you want poll to be the only thing that blocks; otherwise ibv_get_cq_event blocks and the timeout has no effect. Setting O_NONBLOCK on ch->fd and gating the call behind poll gives you the timeout R6 requires.

The caller must keep draining after this returns — one call may yield several completions and more may remain. Loop until it returns zero before waiting again.

H7 — Batched Acknowledgement (R7)

Level 1

A counter and a threshold. The interesting part is teardown: whatever is outstanding must be acknowledged before the completion queue is destroyed, or destruction blocks.

That failure has a shape you have seen. TRD-05 §6 rule 2 described the same thing for connection-manager events, and the fix is the same — make the acknowledgement happen on every exit path rather than at the end of the happy one.

Level 2
if (st.unacked >= 64) {
    ibv_ack_cq_events(cq, st.unacked);
    st.events_acked += st.unacked;
    st.unacked = 0;
}

And before destroying the completion queue:

if (st.unacked) {
    ibv_ack_cq_events(cq, st.unacked);
    st.events_acked += st.unacked;
    st.unacked = 0;
}

Putting that flush in the destructor of whatever owns the completion queue gets it on every path including exceptions, which is the TRD-04 pattern applied to a resource TRD-04 did not know about.

A threshold of 64 is arbitrary and fine. The point is that the call takes a mutex and is expensive on the data path,[2][3] so amortising it matters; the exact number does not until TRD-08 measures it.

H8 — Close the Arming Race, and Prove You Did (R8)

Level 1

The guard is one extra poll and it is already in H6’s code, deliberately — adding it afterwards means writing the bug first and then trying to reproduce it, which you will not manage on this fabric.

The counter is the requirement. Increment it when the post-arming poll returns something, and report it. Think about what a non-zero value proves and what a zero value proves before writing the notes, because they are not symmetric.

For the broken variant, remove exactly one thing and leave everything else identical, so the difference is attributable.

Level 2
if (!opt_broken_arming) {
    got = ibv_poll_cq(cq, n, wc);
    if (got != 0) { ++st.race_polls_hit; return got; }
}

Run the broken version at high concurrency and see what happens:

./build/limen_pingpong -d rxe0 --reap event --pipeline 32 \
    --signal-every 1 -n 100000 --broken-arming 10.0.0.1

For the notes, something of this shape — and write what you actually saw:

race_polls_hit = 4 over 100,000 iterations at pipeline depth 32.

Non-zero means the race occurred four times and the guard caught it
four times. Each of those would have been a permanent hang without it.

--broken-arming did NOT hang in 100,000 iterations. That does not
show the guard is unnecessary. The window is a few instructions wide
and soft-RoCE's kernel-thread completion path makes it narrower than
hardware would; race_polls_hit being non-zero on the guarded run is
direct evidence the window is real on this fabric. The unguarded
version is one scheduling accident away from blocking forever.

If race_polls_hit is zero across a long run, record that instead and say what it establishes: that the window was not hit here, which is not that it cannot be. That is the same distinction TRD-06 R7 made about last-byte polling, and meeting it twice in two rungs is the point.

H9 — Moderation, Gracefully (R9)

Level 1

One call with a small structure. The whole requirement is what you do when it fails, and the answer is not “exit.”

Distinguish three states in the config line rather than two: off because it was not requested, unavailable because the provider refused, and active with the values in force. Collapsing the middle one into either of the others loses information a reader needs.

Level 2
if (opt_moderate) {
    ibv_modify_cq_attr attr{};
    attr.attr_mask         = IBV_CQ_ATTR_MODERATE;
    attr.moderate.cq_count  = (uint16_t)mod_count;
    attr.moderate.cq_period = (uint16_t)mod_usec;   /* microseconds */

    int rc = ibv_modify_cq(cq, &attr);
    if (rc == 0) {
        std::snprintf(modbuf, sizeof modbuf, "%u:%u", mod_count, mod_usec);
        cfg.moderation = modbuf;
    } else {
        cfg.moderation = "unavailable";
        std::fprintf(stderr, "note: cq moderation not supported by this "
                             "provider (%s) — continuing\n", std::strerror(rc));
    }
}

Expect it to be unavailable on the software provider. That is the expected result and reporting it correctly satisfies the requirement in full.

If your headers lack ibv_modify_cq, guard it with a feature test and report unavailable the same way — that is also a correct outcome.

H10 — Matrix, Regressions, Leaks (R10)

Level 1

Run the matrix yourself before running the suite. Sixteen cells at a few seconds each, and every failure localises to one option combination.

Defaults are the part people break. Every option must default to exactly TRD-06’s behaviour, so the two earlier suites pass untouched. If either fails, a default changed.

Teardown gains one resource with an ordering constraint that is not obvious from creation order — work out which of the completion queue and the channel must go first, and why.

Level 2
for inl in "" "--inline"; do
  for sig in 1 16; do
    for pipe in 1 8; do
      for reap in poll event; do
        ./build/limen_pingpong -d rxe0 -n 500 $inl \
            --signal-every $sig --pipeline $pipe --reap $reap 10.0.0.1 \
          | grep -q 'mismatches=0' || echo "FAILED: $inl sig=$sig pipe=$pipe $reap"
      done
    done
  done
done

The completion queue references the channel, so the queue is destroyed first and the channel after — which means the channel is declared before the queue, since TRD-04 destroys members in reverse declaration order.

class CompletionChannel { /* five special members, noexcept dtor, as TRD-04 */ };

class Endpoint {
    Context           ctx_;
    EventChannel      cm_ch_;
    ProtectionDomain  pd_;
    CompletionChannel comp_ch_;   /* destroyed AFTER cq_ */
    CompletionQueue   cq_;        /* destroyed before comp_ch_ */
    /* ... */
};

Leak-check the poll path, the event path, and a deliberate timeout — the third exits through R6’s error return and is the least exercised path in the program.

One event then silenceNot re-armed. A notification disarms the queue.
Completions present, no eventsNot drained — leftovers do not notify, only new arrivals do.

The most useful habit on this rung

Change one option at a time and rerun the correctness check. Five independent switches produce thirty-two combinations, and a bug found after changing three of them costs more to localise than the change was worth.

The Tool Boundary

The event path is the one place in this ladder where reading the manual page’s worked example carefully is worth more than any debugging tool. The race in R8 cannot be found by stepping through code — it is a window between two lines that are both correct — and the only reliable defences are the specification’s prescribed extra poll and the counter that proves it fired.

An AI assistant is appropriate for reviewing code once it works, clarifying a concept a document left unclear, and grading comprehension answers. It is not appropriate for writing or debugging the implementation.
