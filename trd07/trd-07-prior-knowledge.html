TRD-07: Completion Efficiency

Prior Knowledge — Limen RDMA Transport Project
Depends on: TRD-06  |  Difficulty: High  |  Estimated: 4–6 sessions

1   Where This Fits

Six rungs built a transport that works. Every send is signalled, every completion is polled in a tight spin, every payload is fetched by the adapter from a registered buffer, and exactly one operation is in flight at a time. It is correct and it is naive in four separate ways.

This rung fixes all four. You will add inline data for small payloads, unsignaled sends with periodic signalling, completion-queue moderation, and event-driven reaping as an alternative to spinning — and, critically, you will make each one selectable at runtime so TRD-08 can measure them against each other.

Two warnings before starting. First, every one of these trades something away, and the trade is the content of this rung; applying them without naming what was given up is cargo-culting. Second, none of them will measurably help on the software provider, because TRD-00 §9’s explanation still holds — the bottleneck is a CPU running the transport in software, and these optimisations reduce costs that are noise beside it. You are building the mechanisms and the measurement harness. TRD-08 is where the numbers arrive.

This is the hardest rung after TRD-02, and for a different reason: the failure in §6 is a hang caused by a race you cannot see in the source.

2   Where the Time Actually Goes

Per small message, the naive implementation pays roughly this:

CostPaid onRemoved by
Adapter fetches the payload by DMAEvery sendInline data (§3)
Completion generated, written, polledEvery sendUnsignaled sends (§4)
One interrupt or poll per completionEvery completionModeration (§5)
A core spinning at 100% while idleContinuouslyEvent-driven reaping (§6)
Round trip latency with nothing in flightEvery messagePipelining (§7)

On hardware these are the dominant per-message costs once the transport itself is in silicon. A 64-byte send might cost 1.5 microseconds naively and under 1 microsecond with the first two applied — a third of the time spent on bookkeeping rather than on moving data.

The last row is the largest and the least discussed. With one operation outstanding, the link is idle for an entire round trip per message, so throughput is bounded by latency rather than by bandwidth. Pipelining is what unsignaled sends exist to make practical.

3   Inline Data

Normally a work request points at a registered buffer and the adapter fetches the payload by direct memory access. For a small payload that fetch costs more than the payload is worth.

IBV_SEND_INLINE copies the payload into the work request itself. The adapter receives the data with the descriptor and performs no separate fetch.[1] Three consequences:

  • The local key is not checked, because the adapter never touches your memory. The buffer need not even be registered.
  • The buffer is reusable immediately after ibv_post_send returns — not after the completion. The data has already been copied.
  • The remote side is unaware. Inline affects only how the local adapter obtains the data.[1]

The second point is worth sitting with: it is the only mechanism in this ladder that relaxes TRD-03 §10’s buffer ownership rule, and it does so completely.

The limit must be requested before the queue pair exists

max_inline_data is a field of ibv_qp_init_attr.cap, set at creation. Providers frequently grant more than requested, and some grant zero unless asked. Read it back after ibv_create_qp — as TRD-02 R2 taught — and use the granted value, because posting inline data larger than it produces EINVAL from ibv_post_send.

Typical hardware grants 64 to 1024 bytes. Requesting a large value costs send-queue memory per entry, so it is not free.

The tradeoff: the payload is copied by the CPU into the descriptor rather than fetched by the adapter. Below the threshold that copy is cheaper than the DMA round trip; above it, it is not. That threshold is a measurement, not a constant, and finding it is TRD-08’s business.

4   Unsignaled Sends

TRD-02 created the queue pair with sq_sig_all at zero, so sends produce completions only when flagged. TRD-03 flagged every one and R9 there made you observe what happens when you do not: the data moves and nothing tells you.

The technique is to signal periodically — every nth send — rather than always or never.

Why periodic signalling is sufficient

Work requests on a send queue complete in order. A completion for request n therefore implies every request before it has also completed. One completion in sixteen still bounds buffer reuse and still drains the send queue; it simply does so at coarser granularity.

What you give up is granularity. You no longer know that request 5 finished — only that everything through 16 did. So buffers must be reused in batches, and you need n of them in flight rather than one. That is why unsignaled sends and buffer pooling arrive together in every real transport.

What you also give up is prompt error reporting. An unsignaled request that fails still terminates the queue pair and flushes everything outstanding, but you learn about it at the next signalled completion rather than immediately. The failure is not lost; its detection is delayed by up to n operations.

Never signal nothing. Completions are what drain the send queue, so with no signalling the queue fills and ibv_post_send eventually returns ENOMEM with every request having succeeded — a confusing failure that TRD-03 §11 lists and that this technique makes easy to reach. The signalling period must divide into the send queue depth with room to spare.

5   Completion Queue Moderation

Moderation batches completion notifications: rather than notifying on every completion, the adapter waits until a count is reached or a period elapses, then notifies once. Fewer interrupts, fewer wakeups, higher throughput — at the cost of up to the configured period in added latency.

It is configured with ibv_modify_cq and an ibv_moderate_cq structure carrying cq_count and cq_period, the latter in microseconds. Either may be zero to disable that half.

This is an optional capability. ibv_modify_cq may return EOPNOTSUPP or fail outright on providers that do not implement it, and the software provider is one of them. Treat a failure as “unavailable” rather than as an error: report it and continue. A rung that refuses to run because an optimisation is unsupported is worse than one that reports the fact.

The tradeoff is unusually explicit here because you set the numbers directly. A period of 16 microseconds adds up to 16 microseconds of latency to a completion that would otherwise be reported immediately — ruinous for a latency-bound workload, free for a throughput-bound one.

6   Event-Driven Reaping, and the Race

Every rung so far has polled in a tight loop. That is the lowest-latency approach and it burns a core continuously whether or not anything is happening.

The alternative is a completion channel: a file descriptor that becomes readable when a completion arrives, so a thread can block instead of spinning.

struct ibv_comp_channel *ch = ibv_create_comp_channel(ctx);
struct ibv_cq *cq = ibv_create_cq(ctx, depth, nullptr, ch, 0);

TRD-02 passed nullptr for the channel, which selected polling. Passing a channel selects the event path.

The sequence, and why each step is where it is

ibv_req_notify_cq(cq, 0);              /* arm BEFORE any completion can arrive */

for (;;) {
    struct ibv_cq *ev_cq; void *ev_ctx;
    ibv_get_cq_event(ch, &ev_cq, &ev_ctx);   /* blocks */
    ++unacked;

    ibv_req_notify_cq(cq, 0);          /* RE-ARM: the CQ is now disarmed */

    while (ibv_poll_cq(cq, n, wc) > 0) { /* DRAIN completely */ }

    if (unacked >= 64) { ibv_ack_cq_events(cq, unacked); unacked = 0; }
}

Four rules, each of which corrects a specific failure:

Arm before the first completion can arrive. ibv_req_notify_cq requests notification for the next completion added; anything already in the queue when you call it produces no notification.[3] Arming after posting means the completion may already be there and no event will ever come.

Re-arm after every event. Once a notification is sent the completion queue is disarmed and sends no further notifications until re-armed.[2] Forgetting this yields exactly one event and then silence.

Drain completely. One event does not mean one completion — it means at least one. Several may have accumulated, and any left in the queue will not generate a new event, because the next notification fires only for completions added after the re-arm. Poll until empty every time. Note also that an event may arrive with no completion behind it at all, which is legal and must not be treated as an error.[3]

Batch the acknowledgements. ibv_ack_cq_events takes a mutex and is relatively expensive on the data path; acknowledging many events in one call performs better.[2][3] Count them and acknowledge in batches. Every event must be acknowledged before the completion queue is destroyed, so drain the count during teardown.

The race

Even with all four rules, a completion arriving between your final poll and your call to ibv_req_notify_cq generates no notification — it was already in the queue when you armed. The thread then blocks in ibv_get_cq_event forever with work sitting in the queue.

The remedy is prescribed by the specification itself: poll the completion queue once more after requesting notification.[4] If that poll returns anything, handle it and do not block.

The window is a few instructions wide, which is what makes this so dangerous. It does not appear in development, it does not appear under light load, and it appears as a permanent hang under sustained traffic on faster hardware. The linux-rdma mailing list has an entire thread devoted to spotting this in code that looks correct.[5] A kernel-side flag was eventually added so drivers could report whether the extra poll was necessary, on the grounds that some hardware does generate the event anyway and the redundant poll is waste[4] — but at the userspace verbs level the extra poll is the portable answer.

The corrected shape:

while (ibv_poll_cq(cq, n, wc) > 0) { handle(); }
ibv_req_notify_cq(cq, 0);
while (ibv_poll_cq(cq, n, wc) > 0) { handle(); }   /* the race-closing poll */
ibv_get_cq_event(ch, &ev_cq, &ev_ctx);              /* now safe to block */

Non-blocking channels

The channel’s file descriptor can be made non-blocking and driven by poll or epoll, which is how a server integrates RDMA completions with other event sources. That is the same descriptor discipline as TRD-05’s connection-manager channel, and combining both in one event loop is how a real server is structured.

7   Pipelining

The largest win is not in this list of four. With one operation outstanding, the link idles for a full round trip per message and throughput is bounded by latency. Posting several before reaping any keeps the adapter busy.

The bounds are ones you have already met. The send queue’s depth, max_send_wr, caps outstanding sends. For reads, the negotiated max_rd_atomic from TRD-06 §5 caps outstanding requests far lower — often 16 or fewer, and 1 in this ladder’s configuration. Writes and sends pipeline deeply; reads do not.

Pipelining is what makes unsignaled sends worth having: with one message in flight there is nothing to batch. The two techniques are the same technique.

8   Choosing

TechniqueGainsCosts
Inline dataRemoves a DMA fetch; frees the buffer immediatelyCPU copy; bounded by max_inline_data; send-queue memory
Unsignaled sendsRemoves most completion processingCoarser buffer reuse; delayed error detection; needs pooling
ModerationFewer interrupts and wakeupsUp to the configured period in added latency; often unsupported
Event-drivenFrees a core; scales to many queuesWakeup latency; the §6 race; more code
PipeliningDecouples throughput from latencyMore buffers in flight; bounded hard for reads

The pattern: every row above trades latency for CPU, or CPU for latency, or granularity for throughput. There is no row that is free, and a transport that applies all of them uniformly has chosen a point on a curve without knowing it.

Real transports select per workload. Bulk transfer takes moderation and deep pipelining and does not care about a few microseconds. A latency-critical control path takes inline data and polls, and accepts a burned core. The same library does both, in different connections.

10   What Is Deliberately Left Out

No buffer pool with a proper allocator. Unsignaled sends need n buffers in flight and this rung uses a fixed ring indexed by sequence number, which is enough to be correct and is not a general allocator.

No multiple completion queues, no separate send and receive queues, no completion vectors bound to specific cores. All matter for a multi-core server and none for two nodes.

No adaptive tuning. Real transports adjust the signalling period and moderation settings in response to observed load. Doing that requires measurement, which is TRD-08.

And no conclusions about which technique is best. You are building selectable mechanisms. Anyone who tells you inline data is worth 30% has measured it on specific hardware at a specific size, and TRD-08 is where you get your own number.

11   Further Reading

Read before starting:

  • ibv_get_cq_event(3)[3] — contains a complete worked example of the event loop and the statement that acknowledging is expensive. Read the example line by line; §6 is an annotation of it.
  • RDMAmojo on ibv_req_notify_cq[6] — the arming semantics, and specifically that completions already present do not notify.

Read while implementing:

  • ibv_post_send(3)[1] — the inline and signalled flag semantics, for the fourth and last time.
  • NVIDIA’s active queue pair operations chapter[2] — the clearest statement of the arm/disarm cycle and the acknowledgement batching rationale.

Reference as needed:

  • The linux-rdma race thread[5] — experienced developers finding this bug in code that looks correct. Worth reading once for calibration about how subtle it is.
  • Dreier’s missed-events patch[4] — states the specification’s remedy explicitly and explains why some hardware makes the extra poll redundant.
