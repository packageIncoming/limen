TRD-00: Fabric Up

Comprehension — Limen RDMA Transport Project
8 questions  |  Answer in writing before the key  |  Est.: 45–70 minutes

Questions

Q1. What is rxe0, concretely? Name what sits between an ibv_post_send call and the physical wire on Soft-RoCE that would not be there on a hardware adapter, and say which of RDMA’s three defining properties that layer eliminates.

Q2. RoCEv2 rides UDP port 4791. Reliable-connected queue pairs guarantee ordered, reliable, non-duplicated delivery. Why UDP rather than TCP, and where does the reliability actually come from?

Q3. What is a GID? Explain why a single RoCE port has more than one entry in its GID table, why you had to choose one in R1, and why rping in R3 did not ask you for it.

Q4. Your R4 packet capture succeeded. On a hardware RDMA adapter the same command typically shows nothing. Explain both facts with one mechanism, and say what that tells you about which of the three properties from Q1 this fabric actually has.

Q5. R6 compared RDMA against TCP over the same link. State which won on your fabric, then explain the result. Then say what the comparison would look like on a hardware adapter and why.

Q6. ibv_devinfo reports transport: InfiniBand (0) and link_layer: Ethernet on the same port. Explain why this is not a contradiction, and what each field is actually describing.

Q7. R2 and R3 both proved the fabric moves bytes, and both were required. What does a failure of exactly one tell you that a failure of both does not? Give the specific diagnosis implied by each single-failure case.

Q8. Two-sided and one-sided operations both move bytes between machines. Describe precisely what “the remote CPU is not involved” means for a one-sided operation — not merely that it is idle. Then name one problem this creates that has no equivalent in the sockets model.

Answer all eight in writing before turning the page. Writing is the point — an answer that feels clear in your head and falls apart on paper was never clear. Then compare against the key. Where your answer is thinner than the key’s, reread the Prior Knowledge section named at the end of that answer before starting TRD-01. Where you disagree with the key and can defend the disagreement, that is a good sign rather than a wrong answer.

Answer Key

Q1 — Answer

rxe0 is not a device. It is a software provider registered with the kernel’s RDMA subsystem that presents the same interface a hardware adapter would present, and implements the RoCEv2 transport in kernel code over an ordinary Ethernet interface.

What sits between a posted work request and the wire is the kernel itself — specifically rdma_rxe’s processing threads, and then the entire ordinary Linux network stack. On a hardware adapter, posting a work request means writing a descriptor into a queue in mapped memory and ringing a doorbell; the adapter reads the descriptor, performs direct memory access against the registered buffer, and transmits. No kernel code executes. On rxe, the “adapter” is kernel threads reading the same descriptor, copying the payload through the network stack, and handing it to the netdev driver.

The property eliminated is kernel bypass. Zero copy goes with it as a consequence, since the software path copies. Remote CPU bypass is preserved at the API level — a one-sided write still requires no participation from the remote application — but not in reality, because the remote kernel does the work the remote adapter would otherwise do.

Common miss: describing rxe as an emulator or simulator. It is neither. It is a complete, conformant implementation of the same specification, and its packets are indistinguishable on the wire from a hardware adapter’s — which is exactly what your R4 capture showed. Only the performance differs. That distinction is why your code will transfer to hardware unchanged.

Covered in Prior Knowledge §7 and §9. Demonstrated by R4 and R6.

Q2 — Answer

UDP is used purely as an encapsulation, not as a transport. It contributes exactly two things: a routable IP header, so RoCEv2 can cross subnets where RoCEv1’s raw Ethernet framing could not, and a port number letting the receiving stack demultiplex RoCE traffic from everything else. Your R4 capture saw both.

The reliability comes from the InfiniBand transport headers carried inside the UDP payload — sequence numbers, acknowledgements, and retransmission, implemented by the adapter exactly as on native InfiniBand. UDP is not asked to provide any of it.

TCP would be wrong for two reasons. It would duplicate reliability the InfiniBand transport already provides, paying twice for one guarantee. And more fundamentally, TCP is a byte-stream abstraction with kernel-managed connection state — precisely the thing RDMA exists to bypass. Putting the transport in the adapter is the whole design; layering it on a kernel-managed stream protocol would reintroduce the CPU on the data path.

Common miss: “UDP is faster than TCP, so they used UDP.” Speed is not the reason and the comparison is not meaningful — the InfiniBand transport does the reliability work either way. The real answer is about layering: UDP is the thinnest available wrapper supplying routing and demultiplexing, and nothing else was wanted from it.

Covered in Prior Knowledge §8, and normatively in reference [1].

Q3 — Answer

A GID is a Global Identifier: a 128-bit value identifying an RDMA port, inherited from InfiniBand’s addressing scheme. In RoCE it is not independent — it is derived from the interface’s IP address, with IPv4 addresses appearing as IPv4-mapped IPv6 addresses. That is why the correct entry ended in your dotted-quad in hex.

A port has multiple entries because the same IP address is representable under more than one RoCE version and address family. A typical rxe port carries a RoCEv1 entry and a RoCEv2 entry for the IPv4 address, plus entries for any IPv6 addresses. They are different indices naming the same interface under different encapsulation rules, so choosing wrongly produces a connection attempt that is well-formed and reaches nothing.

Why R2 asked and R3 did not: ibv_rc_pingpong uses raw verbs, where the GID is a field you fill into an address vector during the transition to Ready-To-Receive. Nothing chooses it for you, so the tool exposes it as an argument. rping uses the connection manager, which resolves an IP address to a device, a port, and the correct GID index on your behalf. That resolution is the primary service the connection manager provides, and it is why TRD-05 deletes a substantial amount of code you will have written by then.

Common miss: treating index 0 as a default that ought to work. Index 0 is RoCEv1 on many configurations, and RoCEv1 is not routable. If both ends happen to pick the same wrong index it can appear to work on a flat network and fail the moment a router is involved.

Covered in Prior Knowledge §8. Exercised by R1 and R3.

Q4 — Answer

One mechanism explains both: whether the packets pass through the host’s network stack.

On Soft-RoCE the provider is kernel code. It builds the RoCEv2 encapsulation in software and hands the result to the ordinary network stack for transmission, exactly as any other UDP datagram. A packet sniffer attaches to that stack, so it sees them. Your capture succeeded.

On a hardware adapter, the adapter builds and transmits those packets itself. The host stack is never involved on the data path — that is what kernel bypass means — so there is nothing for a sniffer attached to the host stack to observe. Practitioners resort to vendor tools such as ibdump, or to a switch mirror port capturing off the wire rather than off the host.

What it tells you: this fabric does not have kernel bypass. The capture is a direct measurement of its absence. On hardware, the failure of the same command would be evidence of its presence — a rare case where a tool producing no output is the informative result.

It is worth noticing that this makes Soft-RoCE far more debuggable than hardware. Being able to read the wire format directly is a genuine advantage for learning, and it exists precisely because the performance property you eventually want is missing.

Common miss: attributing the hardware case to encryption, or to the traffic “not being real packets.” The packets are ordinary UDP and identical in format on both fabrics. The difference is entirely about which component transmits them and therefore where they can be observed.

Covered in Prior Knowledge §7 and §9. Measured by R4.

Q5 — Answer

TCP almost certainly won, and frequently by a wide margin. If your measurement disagreed, say so and account for it — but the expected result on soft-RoCE is that ordinary sockets beat RDMA.

The reason: TCP over a virtual link is a mature, heavily optimised kernel path with segmentation offload and decades of tuning. Soft-RoCE runs the entire InfiniBand transport in software — queue-pair state machines, sequence numbering, acknowledgements, encapsulation — and then hands the result to that same kernel network stack. It performs strictly more work over the same wire, using the same CPU, to move the same bytes.

Which is precisely why the comparison was worth making. Measuring only the RDMA number invites the conclusion that the technology is slow. The comparison shows instead that this implementation is slow, and names exactly what is missing: RDMA’s advantage comes from hardware performing the transport work and writing directly into memory. Remove the hardware and you retain all the protocol cost and none of the benefit.

On hardware the comparison inverts, decisively. The adapter performs the transport in silicon and writes directly into registered memory, so the CPU cost per transfer approaches zero and latency drops from tens of microseconds to one or two — roughly an order of magnitude better than TCP on the same link, with a fraction of the CPU. The gap is largest exactly where soft-RoCE is worst: small messages at high rates, where per-message software cost dominates.

Common miss: reporting the numbers without explaining them, or worse, assuming RDMA won and writing the explanation for a result you did not measure. R6 exists to make you confront a counter-intuitive measurement honestly, and an explanation that does not match your own data has skipped the exercise.

Covered in Prior Knowledge §9 and §13. Measured by R5 and R6.

Q6 — Answer

The two fields describe different layers, and the apparent conflict comes from reading both as “what kind of network is this.”

link_layer describes the physical and data-link technology carrying frames: Ethernet here, as opposed to InfiniBand’s own link layer on a native fabric.

transport describes which transport protocol’s semantics the adapter implements above that link: queue pairs, work requests, completions, the reliable-connected service, memory keys. That protocol is defined by the InfiniBand architecture specification, and RoCE reuses it without modification.

So the port correctly reports that it speaks the InfiniBand transport over an Ethernet link, which is the definition of RoCE. This is not an rxe quirk — a hardware RoCE adapter reports the same pair. It is also why the API is called verbs rather than something Ethernet-flavoured, and why InfiniBand documentation applies almost entirely to RoCE programming.

Common miss: concluding the device is misconfigured and trying to fix the transport field. There is nothing to fix. A related miss is assuming InfiniBand documentation is therefore inapplicable — the opposite is true, and it is why the specification and the vendor programming manual are primary references for a project that never touches InfiniBand hardware.

Covered in Prior Knowledge §8 and §11. Observed in S9.

Q7 — Answer

Failure of both means the fault is below both tools: no device, port down, wrong interface bound, firewall dropping 4791, or no route between the nodes. Everything they share is suspect and nothing is eliminated. That is a setup problem, not a requirement problem.

Failure of exactly one eliminates the entire shared substrate and isolates the fault to what the two tools do differently — which is only connection establishment, since the data path is identical.

  • R2 fails, R3 passes. The fabric works and the connection manager can establish connections over it. The fault is in raw-verbs connection setup, and in practice it is almost always the GID index: the connection manager chose correctly and you did not. Diagnosis is to revisit R1 — and note that the failure tells you your reasoning was wrong, not merely your number.
  • R3 fails, R2 passes. The fabric works and raw verbs can move data over it. The fault is in the connection-manager path specifically, which means rdma_ucm is not loaded or /dev/infiniband/rdma_cm does not exist. The data path is proven, so nothing about the device or the network is in question.

This is the design principle behind the whole rung: each check that passes eliminates a class of cause for the next one’s failure. It is also why the two are separate requirements rather than one — running only one converts an unhelpful “it does not work” into nothing at all.

Common miss: treating the two tools as redundant because both move bytes. They share a data path and differ in connection setup. A learner who skips R3 will hit a connection-manager problem in TRD-05 with no evidence the fabric underneath was ever fine.

Covered in Prior Knowledge §11 and §12. Exercised by R2 and R3.

Q8 — Answer

For a one-sided operation, “not involved” means the remote CPU executes no instructions on behalf of the transfer and receives no notification that it occurred. The initiating side’s work request carries both the payload and the destination virtual address together with a remote key. The remote adapter validates the key against its registered regions and writes directly into that memory. It generates no completion on the remote completion queue, raises no interrupt, and schedules nothing. The remote application, watching its own completion queue, would see nothing at all.

Contrast two-sided, where the receiver must have posted a receive work request in advance, the receiving adapter consumes that posted buffer, and the receiver reaps a completion telling it data arrived and how much. The receiver chooses the destination address and learns of the event.

The problem this creates: there is no notification, so the receiver cannot know its memory changed. Sockets never has this problem — data arriving is inherently an event the receiver observes, because observing it is how the data is obtained. With one-sided operations the application must construct its own signalling: polling a flag byte the sender writes last, using a subsequent small send as a doorbell, or using the immediate-data variant that does produce a remote completion. Every one of those is a protocol you design and can get wrong, and getting it wrong produces a reader observing a partially written buffer.

An equally valid answer is the trust boundary: handing a peer a remote key grants it unsupervised write access to a region of your address space for the connection’s lifetime, with no per-operation check by your software. There is no sockets equivalent, because a sockets peer can only hand you bytes you chose to read.

Common miss: “the remote CPU is idle, so it can do other work.” That describes a benefit and misses the mechanism — and it is not reliably true, since the remote CPU may be busy with anything. The point is not spare capacity; it is that the remote side is unaware, and unawareness is what forces you to build signalling on top.

Covered in Prior Knowledge §7. Built in TRD-03 (two-sided) and TRD-06 (one-sided).
