TRD-01: Context, Protection Domain, Memory Registration

Prior Knowledge — Limen RDMA Transport Project
Depends on: TRD-00  |  Difficulty: Medium  |  Estimated: 3–4 sessions

1   Where This Fits

TRD-00 left you with a verified fabric and a build system that finds the RDMA libraries but compiles nothing. Reference tools moved bytes across it; you did not.

This rung writes the project's first verbs code. By the end you will have a diagnostic program that enumerates adapters, opens one, reports its real capabilities, allocates a protection domain, registers a buffer, and prints the keys that registration produced — then tears all of it down in the correct order without leaking.

Nothing here transmits anything. There is no connection, no queue pair, and no peer. That is not a limitation of the rung; it is the shape of the API. Every object built here must exist before a queue pair can be created, and the memory you register here is the memory every later transfer will name. TRD-02 creates the queue pair from this protection domain. TRD-03 posts work requests that reference this memory region by its key.

2   The Object Graph

Verbs objects form a strict ownership hierarchy. Each is created from a parent, and each must be destroyed before its parent. Learning the graph now prevents an entire class of confusing failure later, because the API does not always tell you clearly when you have violated it.

Figure 1 — The verbs object graph. Destruction runs against every arrow: children first, always.

Three of the four boxes you will build are singletons in a simple program — one context, one protection domain, one memory region. Real transports hold many memory regions and several queue pairs against a single protection domain, which is why the graph branches.

3   Enumerating Devices

The entry point to the entire API is ibv_get_device_list(). It returns a null-terminated array of pointers to device descriptors and, through an out parameter, how many there are.[4]

int num = 0;
struct ibv_device **list = ibv_get_device_list(&num);
if (!list) { /* errno is set */ }

The descriptors are opaque. Two accessors are useful: ibv_get_device_name() gives the kernel's name for the device — the same string TRD-00 used with -d — and ibv_get_device_guid() gives its globally unique identifier as a 64-bit value in network byte order.

The list must be released with ibv_free_device_list(). It is safe, and conventional, to free it immediately after opening the device you want: the context returned by ibv_open_device() holds its own reference and remains valid after the list is gone. The reference implementation does exactly this.[2]

An empty list is not an error. It means the kernel has no RDMA devices registered — most often that rdma_rxe is not loaded or the link was never created. Distinguish this case from a failed call, because the two need different fixes and reporting them identically will waste someone's evening.

4   The Device Context

ibv_open_device() takes a descriptor and returns a struct ibv_context *. This is the handle everything else is created from, and it is the point at which the userspace library loads the provider driver for that specific device — the software provider for rxe, a vendor driver for hardware.

Opening a device is a real operation, not a lookup. Underneath, the library opens a character device under /dev/infiniband/, and the file descriptor for it lives in the context's cmd_fd field. Every subsequent verbs call that must reach the kernel travels through it. This is worth knowing for two reasons: it explains why permissions on /dev/infiniband/ matter, and it is why strace is useful for diagnosing verbs programs even though the data path later bypasses the kernel entirely.

The matching teardown is ibv_close_device(). It must be the last verbs call your program makes.

6   Protection Domains

A protection domain is an isolation boundary, and it is the simplest object in the API to create and the easiest to misunderstand. ibv_alloc_pd() takes a context and returns a handle. It has no attributes and nothing to configure.[6]

Its purpose is enforcement. Every memory region and every queue pair belongs to exactly one protection domain, and the adapter refuses any operation in which a queue pair addresses a memory region from a different domain. A work request naming a key from the wrong domain fails with a protection error rather than reading the memory.

This matters because RDMA hands the adapter direct access to process memory. Without a scoping mechanism, one connection's key could name any registered buffer in the process. The protection domain is the mechanism that makes multi-tenancy possible: a server handling many clients gives each connection its own domain, and a bug or a hostile peer on one connection cannot reach another's buffers.

Limen will use a single domain for a long while, which makes the enforcement invisible. Understanding it now is what makes the eventual protection error in TRD-03 or TRD-06 diagnosable rather than mystifying.

7   Memory Registration

This is the concept the rung exists for, and the one with no analogue in sockets programming.

The problem

Your program addresses memory by virtual address. The adapter cannot use virtual addresses — it is a peripheral performing direct memory access, and it needs physical addresses. Two things stand in the way.

First, the mapping from virtual to physical is per-process and known only to the kernel's page tables. Second, and worse, that mapping is not stable. The kernel may swap a page out, migrate it during compaction, or relocate it for any number of reasons. A physical address handed to a peripheral could be pointing at unrelated data microseconds later.

What registration does

ibv_reg_mr() is where that problem is solved.[3] Passing a protection domain, an address, a length, and a set of access flags, the call does the following:

  1. Pins the pages. The kernel takes a reference on every page in the range through the common ib_umem path, marking them unswappable and unmovable for as long as the registration lives.
  2. Builds a translation table. The virtual-to-physical mapping for the range is recorded where the provider can consult it. On hardware this table is programmed into the adapter and the pages are mapped for DMA; on the software provider it is kept in kernel memory, since there is no device to program.
  3. Accounts against the locked-memory limit. Pinned pages count against RLIMIT_MEMLOCK.[11]
  4. Generates two keys. A local key and a remote key, discussed in section 8.
Figure 2 — What ibv_reg_mr() produces. The buffer is contiguous only in virtual space; registration records where its pages actually live and freezes them there.

What it costs

Registration is expensive — hundreds of microseconds to milliseconds for a large region, dominated by walking and pinning every page. It is emphatically not something to do per transfer. Real transports register buffers once at startup and reuse them for the lifetime of the process, and Limen will do the same. This single fact shapes the architecture of every RDMA application ever written: the buffer pool exists because registration is expensive.

Pinned memory is also memory the kernel cannot reclaim. A process that registers gigabytes has removed those gigabytes from the system's reach, which is why the locked-memory limit exists.

The locked-memory limit

RLIMIT_MEMLOCK caps how much memory a process may pin.[11] Historically the default was tiny — 64 kilobytes on many distributions — which made an unexplained registration failure the single most common first encounter with RDMA. Current systems often set it to unlimited for ordinary users, so you may not hit it; on a hardware adapter, in a container, or on a hardened host, you very likely will.

Check yours with ulimit -l. Page pinning happens on the software provider exactly as it does on hardware, through the same kernel code path, so the failure R8 asks you to handle is real on this fabric rather than simulated. The point of R8 is not to guarantee you hit the ceiling — it is that a registration failure must produce a message naming the probable cause, because the raw failure gives you a bare ENOMEM with nothing to act on.

Access flags

The fourth argument is a bitmask declaring what the region permits.[3] It is not a hint; the adapter enforces it.

FlagPermits
0 (no flags)Local read only. Legal, and correct for a send-only buffer.
IBV_ACCESS_LOCAL_WRITEThe local adapter may write here. Required for any receive buffer and for the destination of a local RDMA read.
IBV_ACCESS_REMOTE_READA peer may read this region with RDMA_READ.
IBV_ACCESS_REMOTE_WRITEA peer may write this region with RDMA_WRITE.
IBV_ACCESS_REMOTE_ATOMICA peer may perform atomic operations here.
IBV_ACCESS_MW_BINDMemory windows may be bound against this region. Not used in this ladder.
Granting IBV_ACCESS_REMOTE_WRITE or IBV_ACCESS_REMOTE_ATOMIC without also granting IBV_ACCESS_LOCAL_WRITE is invalid, and ibv_reg_mr() rejects it.[3] The reason is not arbitrary: a remote write is ultimately performed by the local adapter writing into local memory, so local write permission is a prerequisite for remote write permission. R7 makes you demonstrate this deliberately, because meeting it by accident later is confusing.

Grant the minimum. A region registered with remote write permission is a region any peer holding its key may overwrite, for as long as the registration lives.

8   Keys: lkey and rkey

Registration returns a struct ibv_mr whose two most important fields are lkey and rkey. Both are 32-bit handles naming the region, and confusing them is a standard early mistake.

lkey (local)rkey (remote)
Used byYour own work requestsThe peer's work requests
Appears inThe lkey field of every scatter-gather entry you postThe rkey field of a one-sided work request, on the far side
TravelsNever leaves the machineSent to the peer during connection setup
Meaningful whenAlwaysOnly if remote access flags were granted
First used inTRD-03TRD-06

The remote key is a capability. Handing it to a peer grants that peer direct access to the region for as long as the registration lives, with no per-operation check by your software — your program is not consulted and is not notified. This is the trust boundary at the centre of RDMA's security model, and it is the reason protection domains exist and the reason access flags should be minimal.

A one-sided operation therefore needs three things from the peer: the remote virtual address, the length, and the remote key. TRD-06 exchanges exactly that triple during connection setup. Printing the keys in this TRD is what makes that exchange concrete when you reach it.

9   Destruction Order

Every object must be destroyed before its parent. Reversed against Figure 1, the order for this TRD is:

ibv_dereg_mr(mr);        /* children of the PD, first */
ibv_dealloc_pd(pd);      /* then the PD */
ibv_close_device(ctx);   /* then the context, last */

Violating this is not always loud. ibv_dealloc_pd() with a live memory region returns EBUSY, which a program that ignores return values will never see — and the process then exits with pinned pages and kernel objects still referenced. The kernel cleans up on process exit, so a short program appears to work. A long-running one leaks until registration starts failing.

This is the case that motivates TRD-04. Three objects can be ordered by hand. A transport with a dozen regions, several queue pairs, completion queues, and an event channel cannot, especially on error paths where half the objects exist and half do not.

10   Error Handling in Verbs

The verbs API uses three different error conventions, and the inconsistency is real rather than a misreading. Check the manual page for each function; do not generalize from the last one you used.

ConventionFunctionsHow to read it
Returns a pointer, NULL on failure, sets errno ibv_open_device, ibv_alloc_pd, ibv_reg_mr, ibv_get_device_list Check for NULL, then read errno. Familiar C convention.
Returns 0, or an errno value on failure ibv_query_device, ibv_query_port, ibv_dealloc_pd, ibv_dereg_mr The return value is the error code. Do not read errno — it may hold something stale. Pass the return value to strerror().
Returns 0, or -1 on failure ibv_close_device Classic form.

The middle convention causes the most damage, because if (ibv_query_port(...) < 0) compiles, looks correct, and never fires — the failure return is positive. R10 requires every verbs call to be checked with the convention its own manual page documents.

12   What Is Deliberately Left Out

This TRD registers one region of one buffer with one protection domain. Real transports maintain pools of pre-registered buffers, because registration cost forbids doing it per message. Limen builds no pool — TRD-03 reuses a single buffer, and pooling is deferred until there is a reason for it.

Also absent: memory windows, which provide finer-grained and cheaper-to-rebind remote access than a full registration; on-demand paging, which lifts the pinning requirement on adapters that support it; and registration caches, which every production RDMA library has and every one of them has had bugs in. None is needed to move bytes, and each is a substantial topic.

The keys printed here go nowhere. There is no peer to send them to and no connection to send them over. TRD-05 builds the exchange and TRD-06 uses the remote key for the first time. Printing them now is deliberate: it makes the value concrete before it acquires a job.

Read before starting the requirements:

  • ibv_reg_mr(3)[3] — the full flag table and the constraint between remote and local write. Two pages, and the densest useful text for this rung.
  • ibv_get_device_list(3) and ibv_open_device(3)[4] — short, and they settle the list-lifetime question in section 3.

  • ibv_query_device(3) and ibv_query_port(3)[5] — the complete attribute structures, which are longer than the subset tabulated in section 5.

  • RDMAmojo[7] — its per-function pages on ibv_reg_mr and ibv_alloc_pd go beyond the manual pages, particularly on flag interactions.
