TRD-01: Context, Protection Domain, Memory Registration

Hints — Limen RDMA Transport Project
Level 1 = nudge  |  Level 2 = stronger push  |  Try Level 1 for 15+ minutes before escalating

Level 1 points at the right place. Level 2 names the mechanism. Give Level 1 fifteen minutes of real attempts on a specific blocker before opening Level 2.

Unlike TRD-00, this is a code rung, and the hints are calibrated accordingly: Level 2 gives you function names, signatures, and the shape of the solution, but never a working implementation. Where a snippet appears it demonstrates an API's usage pattern, not the requirement's answer.

H1 — Build Target and Argument Handling (R1)

Level 1

TRD-00's CMake file located the library and stored the path in a variable. A target needs three things from you: which sources compile into it, which libraries it links, and which warning flags apply. The variable holding the library path is already there.

For parsing, the standard library has a function for exactly this. Its main quirk is that it distinguishes flags that take a value from flags that do not by a character in a format string, and it communicates the value through a global. Do not hand-roll a loop over argv until you have looked at it — but note that it does not handle long options like --check-access, so decide early whether to use the GNU extension that does, or to special-case that one string before the loop.

Level 2
add_executable(limen_devinfo src/limen_devinfo.c)
target_compile_options(limen_devinfo PRIVATE -Wall -Wextra)
target_link_libraries(limen_devinfo PRIVATE ${IBVERBS_LIB})
target_include_directories(limen_devinfo PRIVATE ${IBVERBS_INCLUDE_DIR} include)

For arguments, getopt_long() from <getopt.h> handles both forms. Build a struct option[] with an entry for check-access taking no_argument, and a short option string of "d:p:s:h". The trailing colon marks an option that requires a value, which arrives in the global optarg.

Parse numbers with strtoull() and check the end pointer — atoi() cannot distinguish zero from garbage, and R1 requires you to reject garbage:

char *end = NULL;
errno = 0;
unsigned long long v = strtoull(optarg, &end, 10);
if (errno || end == optarg || *end != '\0' || v == 0) { /* usage error, exit 1 */ }

H2 — Device Enumeration (R2)

Level 1

One function returns the list and takes a pointer through which it reports the count. Read its manual page for what a null return means versus a successful return with a count of zero — R2 requires you to treat those differently, and the page states the distinction plainly.

Two accessor functions turn an opaque device pointer into a name and into a GUID. The GUID comes back in network byte order, so printing it directly on a little-endian machine gives you a byte-reversed value. There is a standard function for the 64-bit conversion.

Level 2
int num = 0;
struct ibv_device **list = ibv_get_device_list(&num);
if (!list) { /* verbs failure — errno is set — exit 3 */ }
if (num == 0) { /* no devices — exit 2 with the rdma_rxe hint */ }

for (int i = 0; i < num; i++) {
    const char *name = ibv_get_device_name(list[i]);
    uint64_t guid = be64toh(ibv_get_device_guid(list[i]));
    printf("device: %s guid: 0x%016" PRIx64 "\n", name, guid);
}

be64toh() is in <endian.h>; PRIx64 is in <inttypes.h>. Call ibv_free_device_list(list) on every path out, including the two error exits — R2 says it must not leak on the paths that exit early, and those are exactly the paths people forget.

H3 — Open a Named Device (R3)

Level 1

Matching is a loop and a string comparison. The interesting requirement is the error message: when the name matches nothing, R3 wants the available names listed. You already wrote the code that prints them in R2 — consider whether that should be a function rather than an inline loop.

On the lifetime question: section 3 of the Prior Knowledge document tells you whether the list may be freed once the context exists. If you are unsure, the manual page settles it, and the reference implementation demonstrates it.

Level 2
struct ibv_device *dev = NULL;
for (int i = 0; i < num; i++)
    if (strcmp(ibv_get_device_name(list[i]), want) == 0) { dev = list[i]; break; }

if (!dev) { /* print available names to stderr, free list, exit 2 */ }

struct ibv_context *ctx = ibv_open_device(dev);
ibv_free_device_list(list);            /* safe: ctx holds its own reference */
list = NULL;
if (!ctx) { /* errno is set — exit 3 */ }

Setting list to NULL after freeing lets a single cleanup block at the end of the function free it conditionally without double-freeing. That pattern will carry you through R10.

If ibv_open_device fails with EACCES, the fault is permissions on /dev/infiniband/uverbs0, not your code.

H4 — Report Device Attributes (R4)

Level 1

One call fills one structure. The structure is larger than the eleven fields R4 asks for; read the header or the manual page to see the whole thing, because TRD-02 will send you back for more of it.

Watch the return convention. This function does not follow the pointer-and-errno pattern you used in H2 and H3 — section 10 of the Prior Knowledge document has the table. Writing the check the familiar way produces code that compiles and never detects a failure.

Two fields need thought about their type before you print them: the GUID, which has the same byte-order issue as H2, and the maximum region size, which is large enough that the wrong format specifier truncates it.

Level 2
struct ibv_device_attr da;
int rc = ibv_query_device(ctx, &da);
if (rc != 0) {                            /* NOT rc < 0 — the failure return is positive */
    fprintf(stderr, "ibv_query_device: %s (%d)\n", strerror(rc), rc);
    /* exit 3 via the cleanup path */
}

The return value is the errno code, so pass it straight to strerror() and do not read the global errno.

max_mr_size is a uint64_t — print with PRIu64. fw_ver is a fixed-size character array, not a pointer, and is often empty on the software provider; print it as-is rather than substituting a placeholder. node_guid needs the same be64toh() treatment as H2.

H5 — Report Port Attributes (R5)

Level 1

Same return convention as H4. The port number is an argument, and there is a numbering convention stated in a callout in section 5 of the Prior Knowledge document that catches nearly everyone once.

Three of the five fields are enumerations and R5 requires symbolic output. Two of the three have conversion helpers provided by the library — search the header for functions whose names suggest turning a state or a width into a string. The third, the MTU, does not have one, and the mapping from its enum values to byte counts is not linear in the way you might guess. Look at the enum definition rather than assuming.

Level 2
if (port < 1 || port > da.phys_port_cnt) { /* usage error, exit 1 */ }

struct ibv_port_attr pa;
rc = ibv_query_port(ctx, (uint8_t)port, &pa);
if (rc != 0) { /* strerror(rc), exit 3 */ }

ibv_port_state_str(pa.state) gives you "ACTIVE" and similar — note it omits the PORT_ prefix that R5's output contract requires, so prepend it or map the enum yourself.

For the link layer, switch on pa.link_layer against IBV_LINK_LAYER_ETHERNET, IBV_LINK_LAYER_INFINIBAND, and IBV_LINK_LAYER_UNSPECIFIED.

For the MTU, write a small switch. The enumerators are IBV_MTU_256, IBV_MTU_512, IBV_MTU_1024, IBV_MTU_2048, and IBV_MTU_4096, and their underlying integer values are 1 through 5 — which is exactly why printing the enum directly gives you a number that looks like nonsense.

H6 — Allocate a Protection Domain (R6)

Level 1

This is the shortest requirement in the TRD. One call, one argument, a pointer back. It has no attributes and nothing to configure. If you are looking for what to pass, you have already found it.

The only thing to be careful about is what happens to it later — it must be released before the context closes, and R10 checks that.

Level 2
struct ibv_pd *pd = ibv_alloc_pd(ctx);
if (!pd) { /* errno is set — exit 3 via cleanup */ }
printf("pd: allocated\n");

H7 — Register a Memory Region (R7)

Level 1

Four arguments: the domain, where the buffer is, how big it is, and what is permitted. The flags are a bitmask you combine with |, and their names are in the manual page.

Allocate the buffer before registering it, and consider touching it — writing zeros across it — before the call. On some providers registration of untouched pages behaves differently from registration of faulted-in pages, and starting from a known state removes a variable.

For rendering the flags symbolically, you need to go the other direction: from a bitmask back to names. A table of flag-and-name pairs walked in a loop is the usual approach and is worth writing as a helper, because R8 prints flags too.

Level 2
void *buf = calloc(1, size);           /* calloc also faults the pages in */
if (!buf) { /* exit 3 via cleanup */ }

int access = IBV_ACCESS_LOCAL_WRITE
           | IBV_ACCESS_REMOTE_READ
           | IBV_ACCESS_REMOTE_WRITE;

struct ibv_mr *mr = ibv_reg_mr(pd, buf, size, access);
if (!mr) { /* errno is set — this is R9's path */ }

printf("mr: addr=%p length=%zu lkey=0x%08x rkey=0x%08x access=%s\n",
       mr->addr, mr->length, mr->lkey, mr->rkey, flags_to_string(access));

Print mr->addr and mr->length from the returned structure, not the variables you passed. R7 asks for this deliberately — the values agree here, and knowing that they are reported rather than echoed is what lets you notice a provider that adjusts them.

For the helper, a static array of { int flag; const char *name; } walked with a separator variable is enough. It is roughly fifteen lines and both R7 and R8 use it.

H8 — Access Flag Constraint (R8)

Level 1

Register a second, small buffer with exactly one flag set — the remote-write one — and nothing else. The call is required to fail. Your job is to report which failure, symbolically.

Going from an integer errno to its symbolic name is not something the standard library does; strerror() gives you the human description, not the identifier. R8's output contract wants both. A small lookup table over the handful of codes you can plausibly see is the pragmatic answer.

Think about the success case too. R8 says an unexpected success is a finding rather than a pass, which means that branch needs to clean up after itself before exiting.

Level 2
char probe[4096] = {0};
errno = 0;
struct ibv_mr *bad = ibv_reg_mr(pd, probe, sizeof probe, IBV_ACCESS_REMOTE_WRITE);

if (!bad) {
    int e = errno;
    printf("access-check: REMOTE_WRITE without LOCAL_WRITE rejected: %s (%s)\n",
           errno_name(e), strerror(e));
} else {
    fprintf(stderr, "access-check: registration unexpectedly succeeded\n");
    ibv_dereg_mr(bad);
    /* exit 3 via cleanup */
}

Set errno = 0 before the call. It is only meaningful after a failure, and a stale value from an earlier call will otherwise be reported as this call's cause.

errno_name() is your own three-line lookup: EINVAL, ENOMEM, EACCES, EBUSY, and a default returning the number as a string covers everything this TRD can produce.

H9 — Graceful Registration Failure (R9)

Level 1

Most of this requirement is already satisfied if R7's failure branch is written properly — the addition is reporting the locked-memory limit alongside the error.

There is a syscall wrapper for reading resource limits. It fills a structure with a soft and a hard value, and the constant naming the locked-memory resource is the one you want. Unlimited is represented by a specific sentinel constant rather than by a large number, so compare against the constant instead of picking a threshold.

To provoke the failure for testing, ask for more than the limit allows. If your limit is unlimited, you cannot provoke it, and that is a property of your host rather than a defect — the test suite handles that case.

Level 2
#include <sys/resource.h>

struct rlimit rl;
if (getrlimit(RLIMIT_MEMLOCK, &rl) == 0) {
    if (rl.rlim_cur == RLIM_INFINITY)
        fprintf(stderr, "  RLIMIT_MEMLOCK soft: unlimited\n");
    else
        fprintf(stderr, "  RLIMIT_MEMLOCK soft: %llu bytes\n",
                (unsigned long long)rl.rlim_cur);
}

Check your own limit with ulimit -l. If it reports a number, request roughly double it to provoke the failure; if it reports unlimited, this path cannot be exercised on your host.

The failure branch must still reach teardown. If it exits directly it will leak the protection domain and the context, and R10's leak check will catch it.

H10 — Teardown and Error Discipline (R10)

Level 1

The problem R10 poses is that there are now six things that might need releasing — the device list, the buffer, the memory region, the protection domain, the context — and eight or nine places the program can decide to stop. Writing cleanup at each exit point produces nine copies of nearly the same code and one of them will be wrong.

The classic C answer is a single cleanup block at the end, reached by jumping to it, with every handle initialized to a value that means "not created" so the block can test each one. Initialize once at the top, jump on failure, release conditionally in reverse order at the bottom.

Note that three different verbs functions in your teardown use three different return conventions. Section 10 of the Prior Knowledge document has the table. The teardown: line reports each one, so you have to read all three correctly.

Level 2
int rc = 0;
struct ibv_device **list = NULL;
struct ibv_context *ctx  = NULL;
struct ibv_pd      *pd   = NULL;
struct ibv_mr      *mr   = NULL;
void               *buf  = NULL;

/* ... on any failure: rc = 3; goto cleanup; ... */

cleanup: {
    const char *mr_s = "n/a", *pd_s = "n/a", *ctx_s = "n/a";
    int e;

    if (mr)  { e = ibv_dereg_mr(mr);    mr_s  = e ? errno_name(e) : "ok"; }
    free(buf);
    if (pd)  { e = ibv_dealloc_pd(pd);  pd_s  = e ? errno_name(e) : "ok"; }
    if (ctx) { ctx_s = ibv_close_device(ctx) ? "failed" : "ok"; }
    if (list) ibv_free_device_list(list);

    printf("teardown: mr=%s pd=%s context=%s\n", mr_s, pd_s, ctx_s);
    return rc;
}

Three conventions in five lines: ibv_dereg_mr and ibv_dealloc_pd return an errno value, ibv_close_device returns -1, and ibv_free_device_list returns nothing. Getting any of them wrong compiles cleanly.

If ibv_dealloc_pd reports EBUSY, a child of the domain is still alive — you deallocated before deregistering. That is the destruction-order fault from section 9, and the teardown: line exists so you see it rather than exiting silently.

Verify with:

valgrind --leak-check=full --error-exitcode=42 \
  ./build/limen_devinfo -d rxe0 -s 1048576

Expect zero bytes definitely lost. Some providers report a small fixed amount as still reachable at exit; that is not a leak and R10 does not count it.

Debugging This TRD

QuestionInstrument
Is the device even there?ibv_devinfo -d rxe0. If the reference tool cannot see it, your program will not either — that is a TRD-00 regression, not a bug here.
Does my output match the reference?Run ibv_devinfo -v -d rxe0 beside your program and compare fields. Disagreement on a value means you read the wrong struct member.
Which syscall failed?strace -f -e trace=openat,ioctl,write ./build/limen_devinfo -d rxe0. Verbs setup calls reach the kernel through an ioctl on /dev/infiniband/uverbs0, so the failing one is visible.
Did the kernel object?sudo dmesg -T | tail -30 immediately after a failure. Provider errors frequently appear there with more detail than errno carries.
What is my locked-memory limit?ulimit -l, and cat /proc/self/limits for both soft and hard.
Am I leaking?valgrind --leak-check=full --show-leak-kinds=definite
Is a handle null when I use it?gdb --args ./build/limen_devinfo -d rxe0 -s 4096, break on the verbs call, inspect the arguments.

The highest-value habit at this rung is running the reference tool alongside your own and diffing the fields. Nearly every wrong value here is a struct member read incorrectly rather than a call made incorrectly, and the reference output makes that obvious in seconds.

The Tool Boundary

Debugger, strace, dmesg, valgrind, and the manual pages before a chat window. This rung has three separate error conventions and a handful of struct members whose types matter, and every one of those is settled by reading the manual page for the function in front of you. Building the habit of reaching for man 3 ibv_reg_mr rather than asking is the difference between a TRD-06 you can debug and one you cannot.

An AI assistant is appropriate for reviewing code once it works, clarifying a concept a document left unclear, and grading comprehension answers. It is not appropriate for writing or debugging the implementation.
