TRD-02: Queue Pairs and the State Machine

Hints — Limen RDMA Transport Project
Level 1 = nudge  |  Level 2 = stronger push  |  Try Level 1 for 15+ minutes before escalating

Level 1 points at the right place. Level 2 names the mechanism and gives values where a value is a fact rather than a decision.

This rung has a different failure character than the previous two. Most of what goes wrong here goes wrong at R6, produces EINVAL, and says nothing about which of eleven fields was at fault. The Level 1 hints for R5 through R7 therefore lean on narrowing the search rather than on the API, because the API call itself is not the hard part — knowing which field is wrong is.

H1 — Completion Queue (R1)

Level 1

Five parameters. Three of them you pass a neutral value: the opaque user pointer, the completion channel used for event-driven reaping, and the completion vector for interrupt affinity. All three are covered in section 3 of the Prior Knowledge document with the value to use at this rung.

The capacity is the interesting one. Work out how many completions can be outstanding at once given the two queue depths you will choose in R2, then clamp against the device ceiling you captured in TRD-01. Then read the created object's own capacity field, because R1 asks you to report both numbers and they may differ.

Level 2
int want_cqe = send_wr + recv_wr;
if (want_cqe > da.max_cqe) want_cqe = da.max_cqe;

struct ibv_cq *cq = ibv_create_cq(ctx, want_cqe, NULL, NULL, 0);
if (!cq) { /* errno set — exit 3 via cleanup */ }

printf("cq: cqe=%d (requested %d)\n", cq->cqe, want_cqe);

NULL for the user context, NULL for the channel — that selects polling rather than event-driven completion, which is what TRD-03 uses — and 0 for the completion vector.

H2 — Queue Pair Creation (R2)

Level 1

The creating call takes the protection domain, not the context. If you are reaching for the context, look again at section 4 of the Prior Knowledge document and at why the binding matters.

The initialization structure has a nested capability structure with four numbers. Clamp each against its device ceiling from TRD-01 — they are not all bounded by the same attribute, so check which bounds which.

The important subtlety: the call writes back into the structure you passed. Print from the structure after the call, not from the constants you chose. Also zero-initialize the whole structure before filling it — it contains fields this rung does not set, and leaving them holding stack garbage is a failure that appears intermittently.

Level 2
struct ibv_qp_init_attr init;
memset(&init, 0, sizeof init);          /* not optional */
init.send_cq = cq;
init.recv_cq = cq;
init.qp_type = IBV_QPT_RC;
init.cap.max_send_wr  = MIN(16, da.max_qp_wr);
init.cap.max_recv_wr  = MIN(16, da.max_qp_wr);
init.cap.max_send_sge = MIN(1,  da.max_sge);
init.cap.max_recv_sge = MIN(1,  da.max_sge);

struct ibv_qp *qp = ibv_create_qp(pd, &init);
if (!qp) { /* errno set — ENOMEM usually means a cap exceeded a limit */ }

printf("qp: type=RC max_send_wr=%u max_recv_wr=%u max_send_sge=%u max_recv_sge=%u\n",
       init.cap.max_send_wr, init.cap.max_recv_wr,
       init.cap.max_send_sge, init.cap.max_recv_sge);

The queue pair number you need for R3 is qp->qp_num, available immediately after creation.

H3 — Local Endpoint Identity (R3)

Level 1

Four values, from four different places: one is a field on the queue pair you just created, one you invent, one comes from a query call taking a port and an index, and one is a field of the port attributes you already fetched in TRD-01's code.

The sequence number is 24 bits. Mask whatever your random source produces down to that width rather than trusting it to be in range.

The GID is a union of a 128-bit raw form and a structured form. For printing, walk the raw bytes; for the zero check R3 requires, the structured form has a field that is non-zero on any valid GID and is exactly what the reference implementation tests.

Level 2
union ibv_gid gid;
if (ibv_query_gid(ctx, port, gid_index, &gid)) { /* exit 3 */ }

if (!gid.global.interface_id && !gid.global.subnet_prefix) {
    fprintf(stderr, "gid index %d is empty — enumerate with show_gids\n", gid_index);
    /* exit 3 via cleanup */
}

srand48(getpid() * time(NULL));
uint32_t psn = lrand48() & 0xffffff;      /* 24 bits */

For printing in the conventional form, walk the sixteen raw bytes two at a time:

char buf[40];
for (int i = 0; i < 8; i++)
    sprintf(buf + i * 5, "%04x%s",
            (gid.raw[i*2] << 8) | gid.raw[i*2+1], i < 7 ? ":" : "");

Compare the result against show_gids output for the same index. If they disagree you have a byte-order bug, and finding it now is far cheaper than finding it at R6.

H4 — Side-Channel Exchange (R4)

Level 1

Ordinary sockets. Server binds, listens, accepts; client connects. Nothing about this is RDMA-specific and it should take under an hour.

The one real trap is ordering. If both sides read before either writes, both block forever and the program simply hangs with no error. Decide the order deliberately and write it down in a comment: one side writes first, or both write before either reads.

Set SO_REUSEADDR on the listening socket. You will restart this program dozens of times while debugging R6, and without it every restart within the socket's lingering interval fails to bind.

Level 2

One text line each way is sufficient:

/* send: qpn:psn:gid:lid, newline-terminated */
char out[128];
snprintf(out, sizeof out, "%06x:%06x:%s:%04x\n",
         qp->qp_num, psn, gid_str, port_attr.lid);
write_all(fd, out, strlen(out));

/* receive and parse the peer's */
char in[128];
read_line(fd, in, sizeof in);
sscanf(in, "%x:%x:%39[^:]:%x", &rem_qpn, &rem_psn, rem_gid_str, &rem_lid);

Write yours first, then read theirs, on both sides. That works because TCP buffers the write — neither side blocks on writing a hundred bytes — so both writes complete before either read needs to satisfy.

Parse the peer's GID string back into a union ibv_gid by reading eight groups with sscanf and storing each as two bytes, exactly reversing the printing loop from H3. Verify the round trip locally before wiring up the peer: print a GID, parse it back, compare the sixteen bytes. A bug here manifests as EINVAL at R6 and looks nothing like a string bug.

Wrap read() and write() in loops. A short read on a hundred-byte line is unlikely but not impossible, and the resulting truncated GID would send you hunting through your verbs code.

H5 — RESET → INIT (R5)

Level 1

Four fields, four mask flags, and the table in section 5 of the Prior Knowledge document lists exactly which. Two of the four take a value that is essentially fixed at this rung, one is the port number, and one is a decision.

The decision is the access flags — and note that it is a different access-flag field from the one you passed to the registration call in TRD-01. The callout in section 6 explains the relationship. Choose for what TRD-06 will need, not for what this rung needs, because the field cannot be changed later without tearing the connection down.

Zero the attribute structure first. You are naming four fields in the mask, but the structure has forty, and the ones you did not set are read on some providers.

Level 2
struct ibv_qp_attr attr;
memset(&attr, 0, sizeof attr);
attr.qp_state        = IBV_QPS_INIT;
attr.pkey_index      = 0;
attr.port_num        = port;
attr.qp_access_flags = IBV_ACCESS_REMOTE_READ | IBV_ACCESS_REMOTE_WRITE;

int rc = ibv_modify_qp(qp, &attr,
                       IBV_QP_STATE | IBV_QP_PKEY_INDEX |
                       IBV_QP_PORT  | IBV_QP_ACCESS_FLAGS);
if (rc != 0) { /* rc IS the errno value — see R10 */ }

rc != 0, not rc < 0. The manual page specifies that the return value is the errno code on failure.[1] Widely circulated vendor documentation says otherwise;[4] for the library you are linking, the manual page is correct.

H6 — INIT → RTR (R6)

Level 1

This is where you will lose time. Before writing anything, read section 8 of the Prior Knowledge document in full — the whole section, not the code fragment.

Three checks to run before you start debugging anything else, in this order:

  1. Is is_global set to 1? On RoCE it must be. The reasoning that says otherwise — "the peer is on the same subnet, so no global routing is needed" — is correct on InfiniBand and wrong here.[3]
  2. Are you assigning the peer's sequence number to the receive-side field, and an index rather than a value to the source GID field? Those two are asymmetric and both look reasonable when written the wrong way round.
  3. Does every field you set appear in the mask, and does every flag in the mask correspond to a field you set? A field set but unnamed is silently discarded; a field named but unset is read as stack garbage.

If all three are clean and it still fails, print every attribute you are passing — which is what R10 requires anyway, so write that first and let it tell you.

Level 2
struct ibv_qp_attr attr;
memset(&attr, 0, sizeof attr);
attr.qp_state           = IBV_QPS_RTR;
attr.path_mtu           = port_attr.active_mtu;   /* enum, must match both ends */
attr.dest_qp_num        = rem_qpn;                /* PEER's queue pair number   */
attr.rq_psn             = rem_psn;                /* PEER's sequence number     */
attr.max_dest_rd_atomic = 1;
attr.min_rnr_timer      = 12;                     /* encoded, ~0.64 ms          */

attr.ah_attr.is_global     = 1;                   /* REQUIRED on RoCE           */
attr.ah_attr.port_num      = port;
attr.ah_attr.sl            = 0;
attr.ah_attr.src_path_bits = 0;
attr.ah_attr.dlid          = 0;                   /* ignored on Ethernet        */
attr.ah_attr.grh.dgid        = rem_gid;           /* PEER's GID VALUE           */
attr.ah_attr.grh.sgid_index  = gid_index;         /* index into YOUR OWN table  */
attr.ah_attr.grh.hop_limit   = 1;
attr.ah_attr.grh.traffic_class = 0;
attr.ah_attr.grh.flow_label    = 0;

int rc = ibv_modify_qp(qp, &attr,
                       IBV_QP_STATE              | IBV_QP_AV                 |
                       IBV_QP_PATH_MTU           | IBV_QP_DEST_QPN           |
                       IBV_QP_RQ_PSN             | IBV_QP_MAX_DEST_RD_ATOMIC |
                       IBV_QP_MIN_RNR_TIMER);

The two lines worth rereading are the destination GID and the source GID index. The first is 128 bits of the peer's identity that arrived over the side channel. The second is a small integer selecting an entry in your own table. They sit adjacent in the same structure and are entirely different kinds of thing.[2]

The reference implementation guards the global-route block behind a test for a non-zero peer GID, which is worth copying even in a RoCE-only program because it documents why the fields are set.[5]

H7 — RTR → RTS (R7)

Level 1

Six fields, and after R6 this one is straightforward — it needs nothing from the peer.

Four of the six are policy numbers whose conventional values are given in section 9 of the Prior Knowledge document with their meanings. Note that the timeout is exponentially encoded rather than a duration, and that zero means infinite rather than immediate — a queue pair with a zero timeout hangs instead of reporting an error.

The one thing to get right is which sequence number belongs here. R7's callout states it directly. If you set the same value in both R6 and R7 you have made the mistake.

Level 2
struct ibv_qp_attr attr;
memset(&attr, 0, sizeof attr);
attr.qp_state      = IBV_QPS_RTS;
attr.sq_psn        = my_psn;                       /* YOUR sequence number */
attr.timeout       = 14;                           /* ~4.096us * 2^14      */
attr.retry_cnt     = 7;
attr.rnr_retry     = 7;                            /* 7 = retry forever    */
attr.max_rd_atomic = MIN(1, da.max_qp_rd_atom);

int rc = ibv_modify_qp(qp, &attr,
                       IBV_QP_STATE     | IBV_QP_SQ_PSN    |
                       IBV_QP_TIMEOUT   | IBV_QP_RETRY_CNT |
                       IBV_QP_RNR_RETRY | IBV_QP_MAX_QP_RD_ATOMIC);

max_rd_atomic here is the outgoing counterpart to max_dest_rd_atomic at R6. One bounds reads you issue, the other bounds reads you accept.

H8 — Verify State (R8)

Level 1

The readback call takes four arguments rather than three: the queue pair, an attribute structure, a mask naming what you want back, and an initialization-attribute structure it also fills. The last one is required even if you do not use it.

Map the state enum to its symbolic name with a switch. There is no library helper for this one.

Level 2
struct ibv_qp_attr      qattr;
struct ibv_qp_init_attr qinit;
memset(&qattr, 0, sizeof qattr);
memset(&qinit, 0, sizeof qinit);

int rc = ibv_query_qp(qp, &qattr, IBV_QP_STATE, &qinit);
if (rc != 0) { /* exit 3 */ }

printf("verify: qp_state=%s\n", qp_state_name(qattr.qp_state));
if (qattr.qp_state != IBV_QPS_RTS) { /* exit 3 */ }

qp_state_name() is a seven-case switch over IBV_QPS_RESET, INIT, RTR, RTS, SQD, SQE, and ERR. Include all seven — the value you most want to see named is ERR, and a default branch printing an integer is exactly the case where you need the name.

H9 — GID Index Validation (R9)

Level 1

Two checks, and both are cheap. The port attributes carry the table length, so an index at or above it is a usage error you can reject before touching the fabric. And a successfully retrieved GID that is entirely zero means the entry exists but is unpopulated, which is not a usage error but is also not something to proceed from.

Resist the temptation to default the index to 0. Section 8 of TRD-00's Prior Knowledge explains why index 0 is frequently RoCEv1 and therefore wrong, and a default that is wrong most of the time is worse than a required argument.

Level 2
if (gid_index < 0 || gid_index >= port_attr.gid_tbl_len) {
    fprintf(stderr, "gid index %d out of range (table length %d)\n",
            gid_index, port_attr.gid_tbl_len);
    return 1;                                    /* usage error */
}

To find the right index on your fabric, from TRD-00:

show_gids
cat /sys/class/infiniband/rxe0/ports/1/gid_attrs/types/*

Choose the entry whose type reads RoCE v2 and whose GID ends in your dotted-quad address. Record it in the README — you will type it on every invocation for the rest of the ladder.

H10 — Transition Failure Diagnosis (R10)

Level 1

Write this before R6, not after. It is the instrument that makes R6 debuggable, and building it first converts a blind search over eleven fields into reading a printout.

You need two helpers: one turning an errno into its symbolic name, which you wrote in TRD-01 and can extend, and one turning an attribute mask into pipe-separated flag names. The second is the same table-walk pattern as the access-flag renderer from TRD-01 H7 — a static array of flag-and-name pairs.

Then a function taking the transition name, the return code, the mask, and the attribute structure, which prints everything the mask names. Call it from all three transitions so the diagnostic is identical wherever the failure occurs.

Level 2
static const struct { int flag; const char *name; } QP_MASKS[] = {
    { IBV_QP_STATE,              "IBV_QP_STATE" },
    { IBV_QP_PKEY_INDEX,         "IBV_QP_PKEY_INDEX" },
    { IBV_QP_PORT,               "IBV_QP_PORT" },
    { IBV_QP_ACCESS_FLAGS,       "IBV_QP_ACCESS_FLAGS" },
    { IBV_QP_AV,                 "IBV_QP_AV" },
    { IBV_QP_PATH_MTU,           "IBV_QP_PATH_MTU" },
    { IBV_QP_DEST_QPN,           "IBV_QP_DEST_QPN" },
    { IBV_QP_RQ_PSN,             "IBV_QP_RQ_PSN" },
    { IBV_QP_MAX_DEST_RD_ATOMIC, "IBV_QP_MAX_DEST_RD_ATOMIC" },
    { IBV_QP_MIN_RNR_TIMER,      "IBV_QP_MIN_RNR_TIMER" },
    { IBV_QP_SQ_PSN,             "IBV_QP_SQ_PSN" },
    { IBV_QP_MAX_QP_RD_ATOMIC,   "IBV_QP_MAX_QP_RD_ATOMIC" },
    { IBV_QP_TIMEOUT,            "IBV_QP_TIMEOUT" },
    { IBV_QP_RETRY_CNT,          "IBV_QP_RETRY_CNT" },
    { IBV_QP_RNR_RETRY,          "IBV_QP_RNR_RETRY" },
};

Walk it, emitting a name for each set bit with | between. Then print the attributes conditionally on the mask, so the RTR failure shows the address vector and the RTS failure does not clutter the output with it.

To exercise the path deliberately, add a hidden --force-rtr-fail flag that clears is_global before the R6 call. The test suite uses it, and it also gives you a known-bad case to develop the diagnostic against before you have a real failure.

H11 — Teardown Order (R11)

Level 1

Five handles now, plus two sockets and a buffer. The single-cleanup-block pattern from TRD-01 H10 still works; it just has more lines.

The new ordering constraint is not obvious from the creation order: the queue pair references the completion queue, so it must be destroyed first. Destroying the completion queue while a queue pair still points at it returns EBUSY — the same class of fault as deallocating a protection domain with a live memory region, one level down.

If keeping the order straight is starting to feel like a chore you will eventually get wrong, note that feeling. It is the entire argument for TRD-04.

Level 2
cleanup: {
    const char *qp_s = "n/a", *cq_s = "n/a", *mr_s = "n/a",
               *pd_s = "n/a", *ctx_s = "n/a";
    int e;

    if (qp)  { e = ibv_destroy_qp(qp);  qp_s = e ? errno_name(e) : "ok"; }
    if (cq)  { e = ibv_destroy_cq(cq);  cq_s = e ? errno_name(e) : "ok"; }
    if (mr)  { e = ibv_dereg_mr(mr);    mr_s = e ? errno_name(e) : "ok"; }
    free(buf);
    if (pd)  { e = ibv_dealloc_pd(pd);  pd_s = e ? errno_name(e) : "ok"; }
    if (ctx) { ctx_s = ibv_close_device(ctx) ? "failed" : "ok"; }
    if (list) ibv_free_device_list(list);
    if (sock >= 0)   close(sock);
    if (listen_fd >= 0) close(listen_fd);

    printf("teardown: qp=%s cq=%s mr=%s pd=%s context=%s\n",
           qp_s, cq_s, mr_s, pd_s, ctx_s);
    return rc;
}

Verify both paths, not just the happy one:

valgrind --leak-check=full ./build/limen_connect -d rxe0 -g 3 10.0.0.1
valgrind --leak-check=full ./build/limen_connect -d rxe0 -g 3 --force-rtr-fail 10.0.0.1

Debugging This TRD

QuestionInstrument
Which field made RTR fail?Your own R10 diagnostic. Build it first. Nothing else answers this.
Is my GID string round-tripping?Print, parse, compare all sixteen bytes, locally, before involving a peer.
Did the side channel actually deliver?sudo tcpdump -i any -A -n port 18515 — the values are plain text and readable directly.
Which GID index is correct here?show_gids, and /sys/class/infiniband/rxe0/ports/1/gid_attrs/types/
Does the reference implementation work on this fabric?ibv_rc_pingpong -d rxe0 -g <idx>. If it fails too, the fault is the fabric or the index, not your code. Always establish this before debugging your own program.
What did the kernel think?sudo dmesg -T | tail -30 immediately after a failed transition.
Which state did it actually reach?Your R8 readback. Call it after every transition while debugging, not only at the end.
Is it hung or is it failing?gdb -p <pid> and a backtrace. A hang in read() is a side-channel ordering bug; a hang elsewhere is not.
The single most useful check

Run ibv_rc_pingpong -d rxe0 -g <your index> between the two nodes before debugging anything of your own. It performs exactly this bringup. If it succeeds and yours fails, the fault is definitively in your code and the index is definitively right. If it fails too, stop reading your own program.

The Tool Boundary

This rung rewards instrumentation over inspection more than any other. EINVAL from a transition carries no information, so the productive move is always to make the program report what it passed — which is R10, and which is why R10 exists as a requirement rather than as advice. Reading your own code hoping to spot the wrong field is the slow path, and it is the path most people take first.

An AI assistant is appropriate for reviewing code once it works, clarifying a concept a document left unclear, and grading comprehension answers. It is not appropriate for writing or debugging the implementation.
