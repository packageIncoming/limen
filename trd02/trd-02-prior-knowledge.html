TRD-02: Queue Pairs and the State Machine

Prior Knowledge — Limen RDMA Transport Project
Depends on: TRD-01  |  Difficulty: High  |  Estimated: 4–6 sessions

1   Where This Fits

TRD-01 left you with an open device, a protection domain, and a registered buffer whose keys you printed. Nothing was connected to anything, because nothing in the API so far can be.

This rung builds the connection. You will create a completion queue, create a reliable-connected queue pair against the protection domain from TRD-01, exchange four values with a peer over an ordinary TCP socket, and drive the queue pair through four states until both ends are ready to send. At the end, both sides query their queue pair and report RTS.

Nothing is transmitted over RDMA. The queue pair is connected and idle. TRD-03 posts the first work request into it.

This is the hardest rung in the ladder, and the difficulty is concentrated in one place: the transition from INIT to RTR requires eleven fields to be correct simultaneously, and getting any of them wrong produces an error code that does not identify which. Sections 6 through 9 exist to make that transition survivable.

2   What a Queue Pair Is

A queue pair is a connection endpoint consisting of two queues: a send queue and a receive queue. You place work requests into them; the adapter removes work requests from them and acts on them. The name is literal — it is a pair of queues, and the pairing is what makes it one endpoint rather than two.

The closest analogy is a socket, and it is worth being precise about where the analogy fails, because relying on it past that point is how people get lost.

TCP socketQueue pair
Created bysocket()ibv_create_qp()
Connection stateManaged by the kernel; you observe itManaged by you, explicitly, through four transitions
Addressing the peerAn IP address and a portThe peer's queue pair number, packet sequence number, and GID
How the peer is discoveredThe kernel resolves and handshakesYou transfer the values yourself, by any means you like
Sendingwrite() — returns when the data is bufferedPost a work request — returns immediately, completion arrives later
BufferingThe kernel holds a send and receive bufferNone. Your buffers are the buffers.
Flow controlThe receive window, managed for youNone you did not build

The last three rows are the substance. A queue pair has no buffers of its own and does no bookkeeping on your behalf. Every guarantee beyond ordered reliable delivery of individual messages is yours to construct.

Transport service types

The InfiniBand transport defines several service types.[1] Three matter in practice:

TypeConstantProperties
Reliable ConnectedIBV_QPT_RCOne peer for the queue pair's lifetime. Delivery is acknowledged, ordered, and retransmitted on loss. Supports one-sided operations and atomics. This is what Limen uses.
Unreliable ConnectedIBV_QPT_UCOne peer, no acknowledgement or retransmission. Supports RDMA_WRITE but not RDMA_READ or atomics, because both require a response.
Unreliable DatagramIBV_QPT_UDAny peer per message, like UDP. No one-sided operations at all. Limited to one path MTU per message.

Reliable Connected is chosen because Limen's later rungs need one-sided reads and atomics, and because the reliability is implemented in the transport rather than by you. The cost is that a queue pair is bound to exactly one peer, so a server handling N clients holds N queue pairs.

3   Completion Queues

A queue pair must be given a completion queue before it can be created, because a queue pair with nowhere to report finished work is not a usable object.

The adapter deposits a completion queue entry for each finished work request: an identifier you chose when posting, a status, an opcode, and a byte count. You retrieve them by polling. That is TRD-03's business — here the completion queue only needs to exist and be correctly sized.

struct ibv_cq *ibv_create_cq(struct ibv_context *context,
                             int                 cqe,
                             void               *cq_context,
                             struct ibv_comp_channel *channel,
                             int                 comp_vector);

cqe is the minimum number of entries. cq_context is an opaque pointer handed back to you on events; pass NULL. channel is for event-driven completion, which arrives in TRD-07; pass NULL to poll. comp_vector selects a completion vector for interrupt affinity; pass 0.[3]

The provider may give you more than you asked for

The created queue's cqe field may exceed the number you requested — providers round up to a convenient size. Read cq->cqe after creation and use that, not your request. The same is true of queue pair capabilities, discussed in section 4.

Sizing

A completion queue must be deep enough to hold every completion that can be outstanding at once, which is the send queue depth plus the receive queue depth. If it overflows, the behaviour is not a graceful error — the queue pair goes to an error state and outstanding work is lost.

Both queues share one completion queue in this design, which is the common arrangement and the one the reference implementation uses.[2] Separate queues are also legal and become interesting in TRD-07.

Size against the device limits recorded in TRD-01, not against a constant. max_cqe is the ceiling.

4   Creating the Queue Pair

struct ibv_qp_init_attr init = {
    .send_cq = cq,
    .recv_cq = cq,
    .cap     = {
        .max_send_wr  = 16,   /* outstanding sends   */
        .max_recv_wr  = 16,   /* outstanding receives */
        .max_send_sge = 1,    /* buffers per send    */
        .max_recv_sge = 1,    /* buffers per receive */
    },
    .qp_type = IBV_QPT_RC,
};
struct ibv_qp *qp = ibv_create_qp(pd, &init);

The queue pair is created from the protection domain, not the context — which is what binds it to the same domain as the memory regions it will address. Section 6 of TRD-01's Prior Knowledge explains why that binding is enforced.

Four capacity numbers, each with a ceiling from the device attributes captured in TRD-01:

FieldBounded byMeaning
max_send_wrmax_qp_wrWork requests that may be outstanding on the send queue. Posting beyond this returns ENOMEM.
max_recv_wrmax_qp_wrThe same for receives. Too small is how you meet the receiver-not-ready condition in TRD-03.
max_send_sgemax_sgeScatter-gather entries per send — how many discontiguous buffers one request may name.
max_recv_sgemax_sgeThe same for receives.
ibv_create_qp() writes back into the cap structure you passed. The granted values may be larger than requested, and on some providers max_send_sge comes back smaller in specific configurations. Read the structure after the call and use what you were granted. Code that assumes it received what it asked for is code that overflows a queue on a different adapter.

After creation, qp->qp_num holds the queue pair number the provider assigned. That value is one of the four things the peer must be told.

5   The State Machine

A newly created queue pair is in RESET. It cannot send, cannot receive, and cannot be posted to. Reaching a usable state means three explicit transitions, each supplying information the adapter does not yet have.

Figure 1 — The reliable-connected queue pair state machine as this rung uses it.

All transitions go through one function:

int ibv_modify_qp(struct ibv_qp *qp, struct ibv_qp_attr *attr, int attr_mask);

The mask names which fields of attr you have filled in. The adapter ignores everything not named in the mask — so a field you set but forget to name in the mask is silently discarded, and a field you name but forget to set is read as whatever was on the stack. Both failure modes are common and neither announces itself.

Return convention, and a widely published error

ibv_modify_qp() returns 0 on success or the value of errno on failure.[4] Vendor documentation that is otherwise excellent states it returns -1 and sets errno.[6] For the library you are linking against, the manual page is correct. Test for a non-zero return and pass that return value to strerror(); do not read the global errno, and do not test for -1.

Required attributes per transition

For a reliable-connected queue pair, the manual page specifies the minimum mask for each transition.[4] These are minimums; you may name additional attributes.

TransitionRequired mask
RESET → INITIBV_QP_STATE, IBV_QP_PKEY_INDEX, IBV_QP_PORT, IBV_QP_ACCESS_FLAGS
INIT → RTRIBV_QP_STATE, IBV_QP_AV, IBV_QP_PATH_MTU, IBV_QP_DEST_QPN, IBV_QP_RQ_PSN, IBV_QP_MAX_DEST_RD_ATOMIC, IBV_QP_MIN_RNR_TIMER
RTR → RTSIBV_QP_STATE, IBV_QP_SQ_PSN, IBV_QP_MAX_QP_RD_ATOMIC, IBV_QP_RETRY_CNT, IBV_QP_RNR_RETRY, IBV_QP_TIMEOUT

The masks differ per service type. Unreliable Datagram, for instance, needs a queue key at INIT and almost nothing at RTR. Copying a mask from a UD example into an RC program is a recognisable way to lose an afternoon.

6   RESET → INIT

This transition supplies the queue pair's local identity. Nothing about the peer is known yet.

FieldValue and reasoning
qp_stateIBV_QPS_INIT
pkey_index0. Partition keys are an InfiniBand fabric-partitioning mechanism with no role in a two-node RoCE setup, but the field is required.
port_numThe physical port, numbered from 1.
qp_access_flagsWhat incoming remote operations this queue pair permits.
Two independent access checks

qp_access_flags is not the same as the access flags you passed to ibv_reg_mr() in TRD-01. An incoming one-sided operation is permitted only if both allow it — the queue pair must accept that class of operation, and the targeted memory region must permit that access. The reference implementation sets this to 0 because it only does two-sided transfer.[2] Limen needs IBV_ACCESS_REMOTE_READ and IBV_ACCESS_REMOTE_WRITE here, because TRD-06 depends on them and the value cannot be changed once the queue pair is connected without a transition back through RESET.

After this transition the queue pair may accept posted receive requests, though it cannot yet receive anything from the wire. It still cannot send.

7   INIT → RTR

This is the transition that fails. It supplies the peer's identity, and every field must be right at once.

FieldValue and reasoning
qp_stateIBV_QPS_RTR
path_mtuAn enum, not a byte count. Must be identical on both ends — use the port's active_mtu from TRD-01, and if the two nodes disagree, the smaller.
dest_qp_numThe peer's queue pair number, received over the side channel.
rq_psnThe peer's starting packet sequence number. Your receive queue must expect the number the peer's send queue will begin with.
max_dest_rd_atomicHow many incoming reads and atomics may be outstanding. 1 is correct here.
min_rnr_timerHow long the peer waits before retrying after a receiver-not-ready response. An encoded value, not milliseconds; 12 is the conventional choice and corresponds to 0.64 ms.[2]
ah_attrThe address vector. Section 8.

Packet sequence numbers

Every reliable-connected packet carries a 24-bit sequence number, and the receiver checks it. The two ends must therefore agree on where the sequence starts, in each direction independently: your rq_psn must equal the peer's sq_psn, and vice versa.

Each side picks its own starting number, conventionally at random, and sends it to the peer. The reference implementation uses a random 24-bit value.[2] Zero would work on a fresh fabric; randomising guards against a stale packet from a previous connection being accepted by a new one.

Getting these crossed — assigning your own starting number to rq_psn instead of the peer's — is a mistake the transition accepts without complaint. It fails later, in TRD-03, as a transfer that never completes.

8   The Address Vector, and the RoCE Trap

The ah_attr field describes how to reach the peer. Its layout:[7]

struct ibv_ah_attr {
    struct ibv_global_route grh;            /* global route header */
    uint16_t                dlid;           /* destination LID — InfiniBand only */
    uint8_t                 sl;             /* service level */
    uint8_t                 src_path_bits;
    uint8_t                 static_rate;
    uint8_t                 is_global;      /* use the GRH? */
    uint8_t                 port_num;
};

struct ibv_global_route {
    union ibv_gid dgid;         /* destination GID */
    uint32_t      flow_label;
    uint8_t       sgid_index;   /* index into the LOCAL GID table */
    uint8_t       hop_limit;
    uint8_t       traffic_class;
};

Native InfiniBand addresses a peer within a subnet by Local Identifier — the dlid field — and only needs the global route header to cross subnets. Ethernet has no Local Identifier at all.

On RoCE, is_global must be 1 and the global route header must be populated. Leaving is_global at 0 because the peer is on the same subnet — which is correct reasoning on InfiniBand — produces EINVAL on this transition, with nothing in the error identifying the cause. This is the single most common failure in RoCE queue pair setup and it has been tripping people since RoCE was introduced.[5]

The reference implementation handles both fabrics by setting is_global = 0 with a destination LID, then overriding when the peer supplied a non-zero GID:[2]

if (dest->gid.global.interface_id) {
    attr.ah_attr.is_global      = 1;
    attr.ah_attr.grh.hop_limit  = 1;
    attr.ah_attr.grh.dgid       = dest->gid;
    attr.ah_attr.grh.sgid_index = sgid_idx;
}

On RoCE the peer's GID is always non-zero, so the branch always fires. Writing that conditional yourself is worthwhile even in a RoCE-only program, because it documents why the fields are set.

The two GIDs are not symmetric

This asymmetry causes real confusion, so state it explicitly:

  • grh.dgid is the peer's GID value, received over the side channel. A 128-bit quantity.
  • grh.sgid_index is an index into your own GID table, not a value and not the peer's. It selects which of your local GIDs is used as the source.

Retrieve your own GID with ibv_query_gid(ctx, port_num, index, &gid). That index is the same one TRD-00 made you pass to the reference tool with -g, and it is your responsibility for the same reason: section 8 of TRD-00's Prior Knowledge explains why a RoCE port has several table entries and how the wrong one fails.

hop_limit is the IP time-to-live for the encapsulating packet. A value of 1 works on a single subnet; anything crossing a router needs more. sl and traffic_class map to quality-of-service on a configured fabric and are 0 here. dlid is ignored entirely when the link layer is Ethernet.

9   RTR → RTS

The final transition supplies retry and timeout policy, and enables sending. It requires nothing from the peer, so it needs no further exchange.

FieldValue and reasoning
qp_stateIBV_QPS_RTS
sq_psnYour starting packet sequence number — the one you sent the peer, which it assigned to its rq_psn.
timeoutEncoded acknowledgement timeout, approximately 4.096 µs × 2^timeout. 14 is conventional, roughly 67 ms.[2] Zero means infinite, which hangs rather than errors.
retry_cntRetries after a transport timeout. 7 is the maximum and the conventional choice.
rnr_retryRetries after a receiver-not-ready response. 7 means retry indefinitely.
max_rd_atomicOutstanding outgoing reads and atomics. The counterpart to max_dest_rd_atomic at RTR. Bounded by max_qp_rd_atom from TRD-01.

A queue pair in RTS is connected. If the peer is also in RTS, the connection is live in both directions.

Ordering between the two sides

A peer cannot receive until it reaches RTR. If one side reaches RTS and sends while the other is still in INIT, the packet is dropped and the sender retries — recoverable, given the retry policy, but only if the retry budget outlasts the delay. The reliable ordering is: both sides reach RTR, then both proceed to RTS. In practice the side-channel exchange provides enough synchronisation, because neither side has the peer's parameters until the other has sent them.

10   The Side Channel

Four values must reach the peer before the RTR transition can be performed:

ValueSourceConsumed as
Queue pair numberqp->qp_numdest_qp_num at RTR
Packet sequence numberChosen at random by yourq_psn at RTR
GIDibv_query_gid()grh.dgid at RTR
LIDport_attr.liddlid — unused on RoCE, carried for symmetry

Nothing specifies how they travel. RDMA has no equivalent of a TCP handshake at this layer; the specification defines what a connected queue pair needs and is silent on how the two ends come to agree. A plain TCP socket is the conventional answer and is what the reference implementation uses.[2]

Two practical points. Format the values as text rather than sending a struct — endianness and padding differ across machines, and a text line is trivially inspectable when the exchange is what broke. Second, both sides must send and receive before either transitions, so the exchange is a genuine round trip rather than one-way.

Figure 2 — Sequence for this rung. The RDMA fabric carries nothing; every arrow is TCP.

TRD-05 deletes all of this. The connection manager performs the same exchange for you, driven by an IP address. Building it by hand first is what makes the connection manager legible rather than magical.

11   Verifying State

ibv_query_qp() reads back a queue pair's attributes, including its current state.[8] Like the other query functions it takes a mask naming what you want.

struct ibv_qp_attr      attr;
struct ibv_qp_init_attr init;
int rc = ibv_query_qp(qp, &attr, IBV_QP_STATE | IBV_QP_AV, &init);
/* attr.qp_state is now IBV_QPS_RTS if the bringup succeeded */

Two reasons this matters here. It is the gate for the rung — a queue pair reporting RTS on both ends is what "connected" means with nothing yet transmitted. And it is a diagnostic: a queue pair that silently fell to IBV_QPS_ERR looks identical from the outside to one that is idle, and querying is the only way to tell.

The states are IBV_QPS_RESET, IBV_QPS_INIT, IBV_QPS_RTR, IBV_QPS_RTS, IBV_QPS_SQD, IBV_QPS_SQE, and IBV_QPS_ERR. Recovery from the error state requires transitioning back through RESET and repeating the entire bringup.

13   What Is Deliberately Left Out

One queue pair, one peer, one connection. A server holding many clients holds many queue pairs, and the multiplexing that implies is not addressed here.

The side channel is throwaway. It has no framing, no version negotiation, and no error handling worth the name, because TRD-05 deletes it. Do not invest in it.

Nothing is posted to either queue and nothing is polled. The queue pair sits connected and idle, which is a state that would never occur in a real transport but is exactly the right place to stop while the state machine is the thing being learned. TRD-03 posts the first work request.

Also absent: shared receive queues, which let many queue pairs draw from one pool of receive buffers; queue pair reuse via a return transition to RESET; and alternate paths for failover. None is needed and each is a topic.

  • ibv_modify_qp(3)[4] — the required-attribute tables for every service type, and the return convention. The densest and most necessary page for this rung.
  • rc_pingpong.c, the functions performing bringup and the parameter exchange[2] — you annotated this in TRD-00 and reread it in TRD-01.
