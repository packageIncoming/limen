TRD-03: Two-Sided Transfer

Hints — Limen RDMA Transport Project
Level 1 = nudge  |  Level 2 = stronger push  |  Try Level 1 for 15+ minutes before escalating

Level 1 points at the right place. Level 2 names the mechanism.

The failure character of this rung differs from TRD-02 again. There, everything failed at one call with one uninformative error. Here, the characteristic failure is a program that hangs — and a hang gives you nothing at all unless you built the instrumentation that distinguishes "waiting" from "stuck." Build R4's timeout early; it is what makes the rest of this rung debuggable.

H1 — Separate Send and Receive Buffers (R1)

Level 1

You need one buffer to send from and rx_depth places to receive into. The simplest arrangement that satisfies R1 is a single allocation sized for all of them, registered once, with slot i at a computed offset — one registration, several addresses.

Two registrations also work and are arguably clearer. Either is defensible; what is not defensible is one buffer used for both directions, because the send and the receive are concurrent from the adapter's point of view even when your loop treats them as sequential.

Whichever you choose, hold onto the base address and the local key. Every scatter-gather entry you build for the rest of the ladder needs both.

Level 2
size_t slot   = msg_size;
size_t rx_len = slot * rx_depth;

void *tx_buf = aligned_alloc(4096, slot);
void *rx_buf = aligned_alloc(4096, rx_len);
memset(tx_buf, 0, slot);
memset(rx_buf, 0, rx_len);

int acc = IBV_ACCESS_LOCAL_WRITE | IBV_ACCESS_REMOTE_READ | IBV_ACCESS_REMOTE_WRITE;
struct ibv_mr *tx_mr = ibv_reg_mr(pd, tx_buf, slot,   acc);
struct ibv_mr *rx_mr = ibv_reg_mr(pd, rx_buf, rx_len, acc);

The receive region must carry IBV_ACCESS_LOCAL_WRITE — the adapter writes into it locally when a message lands, and without that flag the receive fails with a local protection error. TRD-01's section 7 covers why remote write additionally requires it.

Slot i lives at (char *)rx_buf + i * slot. Page-aligning the allocation is not required but makes the registration cheaper and the addresses easier to read in a debugger.

H2 — Post Receives Before Any Send (R2)

Level 1

A receive work request is three fields plus a scatter-gather list. Build one per slot and either post them in a loop or chain them through the next pointer and post once — both are correct, and the chained form is what a real transport does.

The wr_id is yours to define. Choose a scheme now that will still make sense in R5 when a completion arrives carrying nothing but that value: it must tell you which slot, and it must be distinguishable from a send's identifier at a glance.

For the synchronisation the warning in R2 demands: you already have a TCP socket open from TRD-02's exchange. Do not open another. One byte each way after posting is sufficient and is the same write-then-read pattern you used there.

Level 2
#define WRID_RECV(slot)  (0x100u + (slot))     /* receives: 0x100, 0x101, ... */
#define WRID_SEND        (0x001u)               /* sends:    0x001            */
#define IS_RECV(id)      ((id) >= 0x100u)

static int post_recv(struct ibv_qp *qp, struct ibv_mr *mr,
                     void *base, size_t slot_size, unsigned slot)
{
    struct ibv_sge sge = {
        .addr   = (uintptr_t)((char *)base + slot * slot_size),
        .length = (uint32_t)slot_size,
        .lkey   = mr->lkey,
    };
    struct ibv_recv_wr wr = {
        .wr_id   = WRID_RECV(slot),
        .next    = NULL,
        .sg_list = &sge,
        .num_sge = 1,
    };
    struct ibv_recv_wr *bad = NULL;
    return ibv_post_recv(qp, &wr, &bad);        /* 0, or an errno value */
}

Post rx_depth of these before the ready exchange. Then:

char ready = 'R';
write_all(sock, &ready, 1);
read_all(sock, &ready, 1);        /* both sides have posted once this returns */

Note the return convention: ibv_post_recv returns 0 or an errno value, like ibv_modify_qp. Test != 0.

H3 — Post a Send (R3)

Level 1

The send work request is the receive form plus two fields: what operation, and what flags. The opcode you want moves a message into the peer's next posted receive.

The flags field is where this rung's most instructive trap lives. Reread the warning in section 5 of the Prior Knowledge document and check what TRD-02's queue pair creation set. If you post a send with no flags and then wait for a completion, you will wait forever, and nothing will indicate why.

Zero the work request structure before filling it. It contains a union for opcode-specific fields that this rung does not use, and leaving it holding stack contents is a failure that appears only sometimes.

Level 2
static int post_send(struct ibv_qp *qp, struct ibv_mr *mr,
                     void *buf, size_t len, int signaled)
{
    struct ibv_sge sge = {
        .addr   = (uintptr_t)buf,
        .length = (uint32_t)len,
        .lkey   = mr->lkey,
    };
    struct ibv_send_wr wr;
    memset(&wr, 0, sizeof wr);
    wr.wr_id      = WRID_SEND;
    wr.next       = NULL;
    wr.sg_list    = &sge;
    wr.num_sge    = 1;
    wr.opcode     = IBV_WR_SEND;
    wr.send_flags = signaled ? IBV_SEND_SIGNALED : 0;

    struct ibv_send_wr *bad = NULL;
    return ibv_post_send(qp, &wr, &bad);        /* 0, or an errno value */
}

If this returns ENOMEM, the send queue is full — you have more requests outstanding than max_send_wr and are not reaping completions fast enough. With unsignalled sends that is easy to reach, because nothing drains the queue.

H4 — Poll for Completions (R4)

Level 1

The call is non-blocking and returns a count. Zero means the queue was empty, which will be the answer the overwhelming majority of the time — treat it as the normal case, not as a condition.

Two things a first attempt usually gets wrong. Read only as many array entries as the return value says; the rest were not written and contain whatever was there before. And a negative return is the error case, not zero.[2]

The timeout matters more than it looks. Without one, the R8 experiments produce a program you have to kill from another terminal, with no output distinguishing "the peer never replied" from "I deadlocked myself." Take a timestamp before the loop and check elapsed time each iteration.

Level 2
/* Wait for one completion, or time out. Returns 1, 0 on timeout, -1 on error. */
static int wait_completion(struct ibv_cq *cq, struct ibv_wc *wc, int timeout_sec)
{
    struct timespec t0, now;
    clock_gettime(CLOCK_MONOTONIC, &t0);

    for (;;) {
        int n = ibv_poll_cq(cq, 1, wc);
        if (n < 0)  return -1;                  /* poll itself failed  */
        if (n > 0)  return 1;                   /* got one             */

        clock_gettime(CLOCK_MONOTONIC, &now);
        if (now.tv_sec - t0.tv_sec >= timeout_sec) return 0;
    }
}

A tight spin is correct here — it is what polling means, and TRD-07 introduces the event-driven alternative and the reason to want it. Do not add a sleep; it would mask the latency this design exists to avoid and would distort TRD-08's numbers.

Polling more than one completion per call is more efficient and worth doing once the single-entry version works. Remember that each completion returned is removed from the queue permanently — if you poll four and handle two, the other two are gone.[2]

H5 — Interpret Completions (R5)

Level 1

The structure has thirteen fields and, on an error, four of them mean anything. Read the callout in section 6 of the Prior Knowledge document before writing the printing code, because the natural implementation — one format string covering every case — is wrong in exactly the situation where you most need the output to be true.

Structure the function as a branch on status first, with two entirely separate printing paths. It feels like duplication and it is not.

There is a library function for the status string. There is not one for the opcode; write a switch.

Level 2
static void report_completion(const struct ibv_wc *wc)
{
    if (wc->status != IBV_WC_SUCCESS) {
        printf("completion: wr_id=0x%016" PRIx64 " status=%s "
               "vendor_err=0x%08x qp_num=0x%08x\n",
               wc->wr_id, ibv_wc_status_str(wc->status),
               wc->vendor_err, wc->qp_num);
        printf("  note: opcode and byte_len are not valid on an error completion\n");
        return;                       /* nothing else in wc is trustworthy */
    }

    if (IS_RECV(wc->wr_id))
        printf("completion: wr_id=0x%016" PRIx64 " opcode=%s status=SUCCESS "
               "byte_len=%u\n", wc->wr_id, opcode_name(wc->opcode), wc->byte_len);
    else
        printf("completion: wr_id=0x%016" PRIx64 " opcode=%s status=SUCCESS\n",
               wc->wr_id, opcode_name(wc->opcode));
}

opcode_name() is a switch over IBV_WC_SEND, IBV_WC_RECV, IBV_WC_RDMA_WRITE, and IBV_WC_RDMA_READ. The last two are unused until TRD-06; include them now so the function does not need revisiting.

Note that byte_len is only printed for receives. On a send completion it carries nothing the request did not already state.

H6 — Ping-Pong Loop (R6)

Level 1

The two roles differ only in who sends first. Write one loop with a single conditional at the top rather than two loops — they will diverge otherwise, and a bug in one role that is absent in the other is very hard to see.

Per round, each side reaps two completions: one receive and one send. Decide deliberately whether you reap the send completion immediately or let it accumulate, and note that the send buffer is not yours to refill until you have.

The ordering constraint in R6's callout is the one thing here that is not obvious and does not fail immediately. Getting it backwards works at low iteration counts and fails at high ones, which is the worst way for a bug to behave.

Level 2
unsigned slot = 0;
if (is_client) {
    fill_pattern(tx_buf, msg_size, 0);
    post_send(qp, tx_mr, tx_buf, msg_size, signaled);
    sent++;
}

for (unsigned i = 0; i < iterations; i++) {
    struct ibv_wc wc;

    /* 1. wait for the peer's message */
    int r = wait_completion(cq, &wc, 10);
    if (r == 0) { /* timeout — R8's infinite-retry case */ }
    if (r < 0 || wc.status != IBV_WC_SUCCESS) { /* R10 path */ }

    if (IS_RECV(wc.wr_id)) {
        recvd++;
        slot = (unsigned)(wc.wr_id - 0x100u);
        verify_pattern(rx_slot(slot), wc.byte_len, i);   /* R7 */

        post_recv(qp, rx_mr, rx_buf, msg_size, slot);    /* 2. replenish FIRST */

        if (i + 1 < iterations || !is_client) {
            fill_pattern(tx_buf, msg_size, i + 1);
            post_send(qp, tx_mr, tx_buf, msg_size, signaled);  /* 3. then reply */
            sent++;
        }
    }

    /* 4. drain any send completion that has arrived */
    if (signaled) { /* poll and account for it */ }
}

Steps 2 and 3 in that order are R6's callout. The replenished receive is in place before anything you do can cause the peer to send.

The send completion and the receive completion arrive on the same queue in an order you do not control. Branch on wr_id rather than assuming which comes first — that assumption holds on a slow fabric and stops holding when you speed it up.

H7 — Payload Verification (R7)

Level 1

A constant fill proves nothing beyond "some bytes arrived." What you want is a pattern from which a wrong message is detectable, not just a wrong byte — so encode the round number into it and make the rest position-dependent.

Verify against the length the completion reported rather than the length you expected. They should agree; confirming that is free and is the only way you would notice if they ever did not.

On a mismatch, print the offset, the expected byte, and the byte found. A bare "mismatch" tells you nothing, and the offset in particular distinguishes a wholly wrong message from a partially written one — which are different faults with different causes.

Level 2
static void fill_pattern(void *buf, size_t len, unsigned iter)
{
    unsigned char *p = buf;
    for (size_t i = 0; i < len; i++)
        p[i] = (unsigned char)((i * 31u + iter * 131u) & 0xff);
}

static size_t verify_pattern(const void *buf, size_t len, unsigned iter)
{
    const unsigned char *p = buf;
    for (size_t i = 0; i < len; i++) {
        unsigned char want = (unsigned char)((i * 31u + iter * 131u) & 0xff);
        if (p[i] != want) {
            fprintf(stderr, "mismatch at offset %zu: expected 0x%02x got 0x%02x "
                            "(iteration %u)\n", i, want, p[i], iter);
            return i + 1;                 /* non-zero = mismatch, and where */
        }
    }
    return 0;
}

The multipliers matter slightly: both odd, and different, so that neither a shifted buffer nor an off-by-one iteration produces a pattern that happens to match. A checksum would also work; a byte pattern is preferable here because a mismatch localises itself.

H8 — Provoke Receiver Not Ready (R8)

Level 1

Two flags, and the interesting part is that they demonstrate the same fault producing two entirely different symptoms.

--no-recv alone: skip the posting loop. The peer sends into a queue pair with nothing posted. With the retry count TRD-02 gave you, the sender keeps trying and your side simply never sees anything — so what you observe is R4's timeout firing. If your timeout is not built, what you observe is a program you have to kill.

--rnr-retry needs to reach the RTS transition, which means threading a value from argument parsing down into the bringup code you factored out of TRD-02. That plumbing is the only real work in this requirement.

Run the flag on the server and the unmodified program on the client. It is the side that fails to post whose peer suffers.

Level 2

In bringup, replace the constant from TRD-02's H7:

attr.rnr_retry = (uint8_t)opt_rnr_retry;      /* default 7 = infinite */

Then skip the posting loop under the flag, and report it prominently — a silent skip produces a mysterious hang, which defeats the purpose:

if (opt_no_recv) {
    printf("recv: posted=0 depth=%u size=%zu  (--no-recv: RNR will be provoked)\n",
           rx_depth, msg_size);
} else {
    for (unsigned i = 0; i < rx_depth; i++) post_recv(...);
}

The two experiments:

# infinite retry — the client times out with no completion at all
server:  limen_pingpong -d rxe0 -g 3 --no-recv
client:  limen_pingpong -d rxe0 -g 3 10.0.0.1

# finite retry — the client gets a named error completion
server:  limen_pingpong -d rxe0 -g 3 --no-recv --rnr-retry 1
client:  limen_pingpong -d rxe0 -g 3 --rnr-retry 1 10.0.0.1

Set the retry value on both sides. It governs the sender's behaviour, so the side that must observe the error is the side whose value matters — but keeping them equal removes a variable while you are learning what the difference does.

Capture both outputs for docs/transfer-log.md. The pair is the most valuable artefact this rung produces, because it is the same defect wearing two faces.

H9 — Unsignalled Send (R9)

Level 1

The flag plumbing already exists from H3. The work is in the loop: it must not wait for a completion that is never coming.

Think about what still arrives. Receives are always signalled — there is no way to suppress a receive completion — so the peer's messages still generate completions on your side. It is only your own sends that go silent.

The reporting requirement is the point. Print the counts so that the asymmetry is visible in the output rather than something you have to take on trust.

Level 2

Track the two completion kinds separately and report both:

printf("result: iterations=%u sent=%u received=%u send_completions=%u "
       "mismatches=%zu\n", iterations, sent, recvd, send_comps, mismatches);

With --unsignaled, sent equals the iteration count and send_completions is zero, while the peer's received also equals the iteration count. That is the whole demonstration: the data moved, and nothing told you.

Guard the send-completion wait on the flag rather than trying to poll for something that will not appear:

if (signaled) { /* reap the send completion before refilling tx_buf */ }
else          { /* the buffer is NOT safe yet — see below */ }
Without a completion there is no signal that the adapter has finished reading the send buffer, so refilling it is technically unsafe even though a strict ping-pong makes a collision unlikely. Real code handles this by signalling periodically — every nth send — so completions still arrive and still bound buffer reuse, just less often. That is TRD-07's technique, and noticing the problem here is what makes it land there.

H10 — Error Consequences (R10)

Level 1

Two things to record, and one thing not to do.

Record the first non-success status in a variable initialised to success, and write it only if it is still success. That single guard is what makes R10's requirement work, because the flush errors that follow a real failure will otherwise overwrite it.

Record the queue pair's state after the failure, using the same readback call as TRD-02's R8. It will be the error state; confirming it in output is what distinguishes a failed transfer from a dead connection.

Do not attempt to recover. Section 9 of the Prior Knowledge document explains why there is nothing to attempt.

Level 2
enum ibv_wc_status first_error = IBV_WC_SUCCESS;

/* ... in the completion handler ... */
if (wc.status != IBV_WC_SUCCESS) {
    if (first_error == IBV_WC_SUCCESS)      /* first one only */
        first_error = wc.status;
    report_completion(&wc);

    struct ibv_qp_attr      a;
    struct ibv_qp_init_attr ia;
    memset(&a, 0, sizeof a); memset(&ia, 0, sizeof ia);
    if (ibv_query_qp(qp, &a, IBV_QP_STATE, &ia) == 0)
        printf("qp_state_after_error: %s\n", qp_state_name(a.qp_state));

    rc = 5;
    goto cleanup;                            /* teardown still runs */
}

Reuse qp_state_name() from TRD-02's H8. The value you are about to see printed for the first time is ERR, which is precisely the case that switch's default branch would have hidden behind an integer.

If you want to observe the flush burst rather than exiting on the first error, drain the completion queue before leaving — you will see one meaningful status followed by IBV_WC_WR_FLUSH_ERR for everything that was outstanding.[6] Worth doing once, for the picture.

H11 — Buffer Ownership and Teardown (R11)

Level 1

Teardown is TRD-02's block with one more memory region. Mechanical.

The ownership rule is not mechanical and has no compiler support. The discipline that works is to make the unsafe action impossible to reach rather than remembering not to take it: refill the send buffer only at the point in the loop where the completion has just been reaped, so the two are adjacent and the ordering is visible in one screenful.

If you find yourself adding a comment that says "do not touch this until the completion arrives," that comment is doing the work a type should be doing. Note the feeling; it is the second half of TRD-04's argument and you will be asked about it in the comprehension questions.

Level 2
cleanup: {
    const char *qp_s="n/a", *cq_s="n/a", *rx_s="n/a",
               *tx_s="n/a", *pd_s="n/a", *ctx_s="n/a";
    int e;
    if (qp)    { e = ibv_destroy_qp(qp);    qp_s = e ? errno_name(e) : "ok"; }
    if (cq)    { e = ibv_destroy_cq(cq);    cq_s = e ? errno_name(e) : "ok"; }
    if (rx_mr) { e = ibv_dereg_mr(rx_mr);   rx_s = e ? errno_name(e) : "ok"; }
    if (tx_mr) { e = ibv_dereg_mr(tx_mr);   tx_s = e ? errno_name(e) : "ok"; }
    free(rx_buf); free(tx_buf);
    if (pd)    { e = ibv_dealloc_pd(pd);    pd_s = e ? errno_name(e) : "ok"; }
    if (ctx)   { ctx_s = ibv_close_device(ctx) ? "failed" : "ok"; }
    if (list)  ibv_free_device_list(list);
    if (sock >= 0)      close(sock);
    if (listen_fd >= 0) close(listen_fd);

    printf("teardown: qp=%s cq=%s rx_mr=%s tx_mr=%s pd=%s context=%s\n",
           qp_s, cq_s, rx_s, tx_s, pd_s, ctx_s);
    return rc;
}

Three leak checks, not one — the failure paths are where cleanup is usually wrong:

valgrind --leak-check=full ./build/limen_pingpong -d rxe0 -g 3 -n 20 10.0.0.1
valgrind --leak-check=full ./build/limen_pingpong -d rxe0 -g 3 --rnr-retry 1 10.0.0.1
valgrind --leak-check=full ./build/limen_pingpong -d rxe0 -g 3 -s 64 10.0.0.1

Debugging This TRD

QuestionInstrument
Is it hung or is it waiting?R4's timeout. Build it first; without it every failure on this rung looks identical.
Hung with no completion at allAlmost always an unposted receive with infinite retry. Rerun with --rnr-retry 1 and the fabric will name the problem for you.
Send seemed to work but nothing completedCheck IBV_SEND_SIGNALED. The transfer was happening the whole time.
First transfer fails with retry-exceededA TRD-02 defect — crossed sequence numbers. Compare the two nodes' printed local: and remote: lines.
Is anything on the wire?sudo tcpdump -i any -n udp port 4791 -c 20. Traffic with no completions is a posting or polling bug; no traffic is a bringup bug.
Local protection errorPrint the region base, length, and key next to the request's address and key. One of them will not belong to the other.
Payload wrong only sometimesA buffer touched while the adapter owned it. Look for a write to tx_buf that is not immediately after reaping its completion.
Does the reference tool still work?ibv_rc_pingpong -d rxe0 -g <idx>. Establishes the fabric before you debug your own program. Always do this first.
What state is the queue pair in?R10's readback, called after every completion while debugging rather than only on error.
The most useful single technique on this rung

When something hangs, rerun with --rnr-retry 1. Infinite retry is the default and it converts a self-describing error into silence. One flag turns the most confusing failure in RDMA into a completion status that names itself.

The Tool Boundary

A hang tells you nothing, so the productive move is always to make the program capable of reporting that it is stuck — R4's timeout — and then to make the fabric capable of reporting why — the finite retry count. Both are instrumentation you build before you need it, and both are requirements rather than advice for that reason.

An AI assistant is appropriate for reviewing code once it works, clarifying a concept a document left unclear, and grading comprehension answers. It is not appropriate for writing or debugging the implementation.
