TRD-03: Two-Sided Transfer

Requirements — Limen RDMA Transport Project
Depends on: TRD-02  |  Difficulty: Medium-High  |  Estimated: 3–5 sessions

Objective

Build limen_pingpong: a two-node program that brings up a connected queue pair as in TRD-02, then posts receive and send work requests, polls completions, verifies payloads, and runs a bounded ping-pong loop. It must also be able to provoke the receiver-not-ready condition deliberately and report what happened.

What This Is Not

No flow control. The ping-pong is self-limiting because each side sends only in reply, and that is the property this rung exploits rather than solves. Credit schemes are TRD-05 territory at the earliest and are not built here.

No pipelining and no unsignalled sends as a technique — one message outstanding at a time, every send signalled. TRD-07 changes both, deliberately, once there is something to measure.

Nothing one-sided. The remote key printed in TRD-01 stays unused. Both peers run, both post, both poll.

Still no C++ resource management. This program reaches seven handles and two buffers with ownership rules the type system does not express, which is the complete argument for TRD-04.

Technical Requirements

R1 — Separate Send and Receive Buffers

Register two memory regions, or one region with two non-overlapping halves: one the send buffer, one an array of rx_depth receive slots each of the message size.

Sharing a single buffer for both directions happens to work in a strict ping-pong and breaks the moment anything overlaps. Separating them now costs nothing and removes a class of failure that would otherwise appear in TRD-07 as intermittent corruption.

Print the recv: line reporting slots posted, depth, and message size.

Stuck? → Hints H1

R2 — Post Receives Before Any Send

After the queue pair reaches RTS and before signalling readiness to the peer, post rx_depth receive work requests, one per slot, each with a wr_id that identifies which slot it names.

Clamp rx_depth to the max_recv_wr the provider granted in TRD-02 — the granted value, not the requested one.

Both sides must have posted before either sends. Use the side channel: after posting, exchange a one-byte ready marker over the TCP socket already open from R4 of TRD-02, and only then begin. Without that synchronisation the first message can arrive before the peer's receives are posted, and section 8 of the Prior Knowledge document describes what happens next.
Stuck? → Hints H2

R3 — Post a Send

Post an IBV_WR_SEND work request naming the send buffer through a single scatter-gather entry carrying the region's local key.

Set IBV_SEND_SIGNALED unless --unsignaled was given. TRD-02 created the queue pair with sq_sig_all at zero, so without this flag no send completion is generated.[1]

Use a wr_id scheme that distinguishes send requests from receive requests at a glance — the completion carries nothing else identifying which queue it came from.

Stuck? → Hints H3

R4 — Poll for Completions

Poll the completion queue in a loop. Read only the first n entries of your array, where n is the value the call returned; a negative return is a failure and exits 3.[2]

Zero is the ordinary case and is not an error. A polling loop that treats it as one will fail constantly.

Bound the wait. A loop with no timeout is indistinguishable from a hang, and R8 requires you to be able to tell those apart. Ten seconds without a completion is a timeout, reported as such, exiting 5.

Stuck? → Hints H4

R5 — Interpret Completions Correctly

Branch on status before reading anything else.

On success, print the completion: line with wr_id, the opcode rendered symbolically, the status, and — for receive completions only — byte_len.

On failure, print only wr_id, status, vendor_err, and qp_num, followed by the note line shown in the Output Contract. Those four are the only fields the specification guarantees are valid when the status is not success; opcode and byte_len are undefined and printing them produces confident nonsense.[2]

Use ibv_wc_status_str() for the status text rather than writing a table.

Stuck? → Hints H5

R6 — Ping-Pong Loop

Run -n rounds. Each round: reap a receive completion, verify the payload, post a replacement receive, then post the reply. The client sends the opening message.

Replenish before replying

Post the replacement receive before posting the reply, not after. Replying first opens a window in which the peer's answer can arrive at a queue pair with no receive posted, and on a fast link that window is wide enough to hit.

Track sends posted, receives reaped, and completions of each kind. Print the result: line at the end.

Stuck? → Hints H6

R7 — Payload Verification

Fill the send buffer with a pattern that encodes the iteration number, so that a duplicated, stale, or reordered message is detectable rather than merely a byte mismatch. Verify every received message against the pattern expected for that round.

Count mismatches and report them in the result: line. Any non-zero count exits 6, distinctly from a completion error, because a successful completion carrying wrong data is a different fault with different causes.

Verify the full byte_len reported by the completion, not the size you expected. Those agreeing is a fact worth confirming rather than assuming.

Stuck? → Hints H7

R8 — Provoke Receiver Not Ready

The program must be able to demonstrate the condition in both of its forms.

  • --no-recv with the default --rnr-retry 7: the peer's send is retried indefinitely and your polling loop reaches R4's timeout. Report the timeout explicitly, naming an unposted receive as the probable cause.
  • --no-recv --rnr-retry 1: the retry budget is finite, so the sender receives an IBV_WC_RNR_RETRY_EXC_ERR completion. Report it through R5's error path.

The same fault therefore produces a silent hang under one configuration and a self-naming error under another, and the difference is a single value set at the RTS transition. Being able to switch between them on demand is the point of this requirement.

Stuck? → Hints H8

R9 — Unsignalled Send Demonstration

With --unsignaled, omit IBV_SEND_SIGNALED. The transfer still occurs and the peer still receives, but no send completion is generated.

The program must not hang waiting for one. Report the absence explicitly — that sends were posted, that receives were reaped, and that zero send completions appeared — and exit 0, since nothing failed.

This exists so that the flag's effect is observed rather than believed. It is also a trap this rung inherits from TRD-02: an unsignalled send that works is invisible, and a loop written to expect a completion waits forever for one that was never coming.

Stuck? → Hints H9

R10 — Error Consequences

On the first non-success completion, query the queue pair and print qp_state_after_error: with the state rendered symbolically. It will be ERR.[3]

Record the first non-success status in the result: line as first_error. When a queue pair enters the error state every outstanding request is completed with IBV_WC_WR_FLUSH_ERR,[6] so one real failure produces a burst of completions of which exactly one names the cause. A program that reports the last error it saw reports the debris.

Do not attempt recovery. A reliable-connected queue pair in the error state requires transitioning back through RESET and repeating the whole of TRD-02 on both nodes; exit 5 and let teardown run.

Stuck? → Hints H10

R11 — Buffer Ownership and Teardown

Do not write the send buffer for round n+1 until the completion for round n has been reaped. Do not read a receive slot until its completion has appeared. Nothing enforces this and violations produce intermittent corruption under load rather than an error.[1]

Teardown in reverse creation order, now covering both memory regions: queue pair, completion queue, receive region, send region, protection domain, context. Print the teardown: line reporting every stage.

Every exit path unwinds, including the R8 timeout and the R10 error path. Under valgrind --leak-check=full, zero bytes definitely lost on a successful run, on an RNR run, and on a verification failure.

Stuck? → Hints H11

What Comes Next

TRD-04 replaces every hand-written cleanup path in this program with C++ types that own their resources. The seven handles, two buffers, and the ownership rule in R11 that the type system cannot currently express are the whole argument, and this program is the thing that gets refactored.

The four captures in docs/transfer-log.md are not busywork. TRD-07 changes the signalling policy and the queue depths deliberately, and the unsignalled capture is the baseline that makes those changes legible rather than mysterious.
