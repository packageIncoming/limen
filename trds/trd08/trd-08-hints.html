TRD-08: Benchmark Harness

Hints — Limen RDMA Transport Project
Level 1 = nudge  |  Level 2 = stronger push  |  Try Level 1 for 15+ minutes before escalating

Level 1 points at the right place. Level 2 names the mechanism.

This rung fails differently from every other one. Nothing hangs, nothing errors, nothing corrupts — the harness runs cleanly and produces numbers that are wrong in ways the output does not reveal. The defence is R8: validate against a reference before believing anything, and treat a discrepancy as your bug until proven otherwise.

Build order: R1 and R2 first, because everything downstream depends on the clock being sound and the warm-up being right. Then R3, which is where the numbers become readable. Then R8 — validate before building the sweeps, so you are not sweeping a broken measurement.

H1 — Clock Discipline (R1)

Level 1

One function, one clock constant, and a subtraction. The part worth thinking about is the return type: nanoseconds do not fit comfortably in a 32-bit value and the structure has two fields that must be combined without losing precision.

For the floor: loop, take timestamps, subtract, and report the median rather than the mean — the same reasoning as §3, applied to your instrument. Discard the first few hundred, because the clock path warms up too.

Level 2
static inline uint64_t now_ns() {
    timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    return (uint64_t)ts.tv_sec * 1000000000ull + (uint64_t)ts.tv_nsec;
}
/* --clock-floor */
std::vector<uint64_t> d;
d.reserve(10000);
for (int i = 0; i < 10500; ++i) {
    uint64_t a = now_ns(), b = now_ns();
    if (i >= 500) d.push_back(b - a);      /* discard the first 500 */
}
std::sort(d.begin(), d.end());
std::printf("clock: median=%lu ns min=%lu ns p99=%lu ns\n",
            d[d.size()/2], d.front(), d[d.size()*99/100]);

Expect 20–40 ns on a modern system where clock_gettime is served from the vDSO. If you see hundreds of nanoseconds, the call is entering the kernel — common in some virtual machine configurations — and you should say so in the report, because it changes your error bar.

H2 — Warm-Up (R2)

Level 1

Excluding the first n samples is one condition in the recording branch. The requirement is the justification, not the exclusion.

To find the right number, do the opposite of what warm-up does: record everything from iteration zero, then look at where the curve flattens. Print every hundredth sample and read the column — the transition is usually obvious without plotting anything.

Level 2
for (unsigned i = 0; i < warmup + iterations; ++i) {
    uint64_t t0 = now_ns();
    do_operation();
    uint64_t dt = now_ns() - t0;
    if (i >= warmup) samples.push_back(dt);
    else if (opt_show_warmup && i % 100 == 0)
        std::printf("warmup[%u] = %lu ns\n", i, dt);
}

Typical shape: the first handful of samples several times the steady-state figure, converging within a few hundred iterations. Record a short table in the report:

iteration:     0     100    500   1000   2000
latency (us): 89.2   44.1   41.3   41.0   41.1
→ flat by ~500; default warmup set to 1000 for margin.

That is the whole justification and it is worth more than citing a convention.

H3 — Distribution (R3)

Level 1

Keep every sample in a vector, sort once at the end, and index. A million samples of 8 bytes each is 8 MB, which is nothing — do not be tempted into streaming quantile estimation for a problem this size.

Watch the index arithmetic on percentiles. Off-by-one errors here are silent and produce figures that are almost right, which is worse than obviously wrong. A quick consistency check — each percentile at least as large as the one below it — catches most of them.

For the median-versus-mean comparison the requirement asks for, compute the ratio and state what it indicates rather than leaving the reader to divide.

Level 2
static uint64_t pct(const std::vector<uint64_t> &s, double p) {
    if (s.empty()) return 0;
    size_t i = (size_t)(p / 100.0 * (double)(s.size() - 1) + 0.5);
    return s[std::min(i, s.size() - 1)];
}

std::sort(samples.begin(), samples.end());
double mean = std::accumulate(samples.begin(), samples.end(), 0.0) / samples.size();
double med  = (double)pct(samples, 50);
std::printf("  median/mean ratio = %.3f  (%s distribution)\n",
            med / mean,
            std::fabs(med / mean - 1.0) < 0.10 ? "fairly flat" : "skewed — tail present");

For the JSON, emit the raw samples rather than only the summary, so the distribution can be re-analysed later without re-running:

{"config": {...}, "conditions": {...},
 "samples_ns": [41230, 41180, 41310, ...]}

A million integers is a few megabytes of JSON. Acceptable, and it means a question you think of next week does not require the fabric to still exist.

H4 — Coordinated Omission (R4)

Level 1

Read §4 of the Prior Knowledge document twice before writing this. The code difference between the correct and incorrect versions is one line, and the conceptual difference is the whole point of the rung.

The one line: where the interval starts. In the closed loop it starts when you send. In the open loop it starts when you should have sent, which is a value computed before the loop began and independent of whatever the system did.

The behaviour to get right: when you are behind schedule, do not sleep. Sleeping to “catch up” to a schedule you have already missed is precisely the coordination the technique is named after.

Level 2
/* --mode response: open loop against a fixed schedule */
const uint64_t interval = 1000000000ull / rate;      /* ns between ops */
const uint64_t t_start  = now_ns();

for (unsigned i = 0; i < iterations; ++i) {
    uint64_t intended = t_start + (uint64_t)i * interval;

    uint64_t t = now_ns();
    if (t < intended) {
        busy_wait_until(intended);                   /* early: wait      */
    } else {
        ++behind;                                    /* late: do NOT sleep */
    }

    do_operation();
    samples.push_back(now_ns() - intended);          /* from INTENDED */
}

Prefer a busy wait to nanosleep for sub-millisecond intervals — sleep granularity is coarser than the intervals you care about and would itself distort the schedule.

Report behind. A large count means the requested rate exceeds what the system can sustain, and the response figures are then measuring saturation rather than the rate you asked for — which is worth knowing and worth stating.

Label the outputs so the distinction survives into the report:

report: mode=latency  quantity=service_time  (closed loop, 1 outstanding)
report: mode=response quantity=response_time (open loop, target 50000 ops/s, behind=12)

H5 — Bandwidth (R5)

Level 1

Opposite methodology to latency: many operations in flight, total bytes over elapsed time. TRD-07’s pipelining is what makes this possible — use it rather than reimplementing it.

Run long enough that connection setup and warm-up are negligible relative to the measured window. Start the timer after warm-up, not at program start.

The unit conversion has two traps in it: a factor of eight, and a binary-versus-decimal convention. Do the conversion once, in one place, and label every figure.

Level 2
uint64_t t0 = now_ns();
/* ... transfer `iterations` messages of `size` bytes, pipelined ... */
uint64_t elapsed = now_ns() - t0;

double bytes   = (double)iterations * (double)size;
double sec     = (double)elapsed / 1e9;
double mib_s   = bytes / sec / (1024.0 * 1024.0);
double gbit_s  = bytes * 8.0 / sec / 1e9;
double msg_s   = (double)iterations / sec;

std::printf("bandwidth: %.2f MiB/s  %.3f Gbit/s  %.0f msg/s  (size=%zu, %.2f s)\n",
            mib_s, gbit_s, msg_s, size, sec);

MiB uses 1024-based units, Gbit uses 1000-based — matching the reference tools, which default to MiB/sec and offer a flag for Gbit/sec.[3] Mixing conventions silently is how a 7% discrepancy appears from nowhere.

Report the elapsed time too. A bandwidth figure from a 40-millisecond window is not a sustained measurement and the duration is what lets a reader judge that.

H6 — The Sweeps (R6)

Level 1

Two nested loops and a table formatter. The engineering is in making the output readable enough that the shape is visible without a spreadsheet.

The size sweep should reduce iteration count as size grows, or the large sizes take minutes. Keeping total bytes roughly constant per size is the usual approach.

For the option sweep, change exactly one switch from the baseline per row. A row differing in two switches cannot be attributed to either.

The requirement about the noise floor is the part that matters. Compute the difference, then compare it against R7’s spread, and print a marker rather than a percentage when it is smaller.

Level 2
size(B)  iters   med(us)  p99(us)  MiB/s   Gbit/s   msg/s
     64  100000    41.2     58.3     1.48    0.012   24270
    256  100000    41.6     59.1     5.87    0.049   24038
   1024   50000    42.9     61.0    22.75    0.191   23320
   ...
1048576     500   890.1   1102.4   112.30    0.942     112
option              med(us)  delta      p99(us)  verdict
baseline              41.2      —          58.3    —
inline=on             41.0    -0.5%        58.1    within noise (4.1%)
signal_every=16       40.9    -0.7%        57.9    within noise (4.1%)
pipeline=8            28.4   -31.1%        39.2    SIGNIFICANT
reap=event            47.8   +16.0%        71.4    SIGNIFICANT (worse)
op=write              40.8    -1.0%        57.6    within noise (4.1%)
const char *verdict(double delta_pct, double noise_pct) {
    if (std::fabs(delta_pct) <= noise_pct) return "within noise";
    return delta_pct < 0 ? "SIGNIFICANT" : "SIGNIFICANT (worse)";
}

That table is the report’s centrepiece, and the “within noise” rows are as much a result as the significant ones. Two rows will likely move on this fabric — pipelining, because it addresses idle time; and event mode, because wakeup cost is real everywhere.

H7 — Variance (R7)

Level 1

Wrap the whole measurement in a loop, collect one median per run, and report the spread of those medians. Not the spread of samples within a run — that is the distribution, which R3 already covers.

Express it as a percentage of the mean median, because that is the form the R6 comparison needs.

Print it before any comparison in the report. Stating the floor after presenting differences invites the reader to have already believed them.

Level 2
std::vector<double> medians;
for (unsigned r = 0; r < runs; ++r) medians.push_back(one_run());

double mean = std::accumulate(medians.begin(), medians.end(), 0.0) / medians.size();
auto [lo, hi] = std::minmax_element(medians.begin(), medians.end());
double spread_pct = (*hi - *lo) / mean * 100.0;

std::printf("variance: %u runs, medians %.2f-%.2f us, spread %.1f%% of mean\n"
            "  → no difference smaller than %.1f%% is meaningful\n",
            runs, *lo / 1000.0, *hi / 1000.0, spread_pct, spread_pct);

Expect a few percent on an idle virtual machine and considerably more on a loaded one. If the spread exceeds ten percent, close other work and re-run — a noise floor that large makes every comparison in R6 unusable, which is itself worth knowing before you spend an hour sweeping.

H8 — Validation (R8)

Level 1

Do this before the sweeps, not after. A validated harness sweeping is an afternoon well spent; an unvalidated one is an afternoon producing a table you will have to discard.

The convention question is answered by arithmetic, not by reading documentation. Measure a full round trip yourself, compare against theirs, and see whether the ratio is near one or near two. That is the experiment.

Match everything you can control — size, iterations, transport type, warm-up — because every unmatched parameter is a candidate explanation for a discrepancy you would otherwise have to chase.

Level 2
# reference
ib_send_lat -d rxe0 -s 64 -n 10000            # server
ib_send_lat -d rxe0 -s 64 -n 10000 10.0.0.1   # client

# yours, matched
./build/limen_bench -d rxe0 --mode latency -s 64 -n 10000 10.0.0.1

Their output columns, in order: #bytes #iterations t_min t_max t_typical t_avg t_stdev 99% 99.9%. Compare their t_typical — the median — against yours.

ib_send_lat t_typical : 41.30 us
limen_bench median RTT: 41.55 us
ratio 1.006  →  the reference reports the FULL round trip on this build.
                (a ratio near 2.0 would mean it reports one-way.)
discrepancy 0.6%, within the declared 25% tolerance.

Record that block verbatim in the report. It is short, it is the single most credibility-bearing paragraph in the document, and it answers the first question a skeptical reader will ask.

If you are outside tolerance, look at your harness first: warm-up not applied, the clock floor not subtracted where it should be, a percentile index off by one, or the two sides not actually running matched parameters.

H9 — Conditions (R9)

Level 1

Mechanical, and the temptation is to do it by hand at the end. Do not — a block assembled manually after the fact is the block that gets stale.

Most of it you can read programmatically at startup: the kernel release from a system call, the device attributes you have queried since TRD-01, and the effective configuration line TRD-07 R1 already builds.

Level 2
utsname u; uname(&u);
std::printf("conditions:\n"
            "  kernel:      %s %s\n"
            "  device:      %s (%s)\n"
            "  active_mtu:  %d\n"
            "  qp caps:     max_send_wr=%u max_sge=%u max_inline=%u\n"
            "  clock floor: %lu ns\n"
            "  warmup:      %u   iterations: %u   runs: %u\n"
            "  date:        %s\n",
            u.sysname, u.release, dev_name, provider,
            mtu_bytes, cap.max_send_wr, cap.max_send_sge, cap.max_inline_data,
            clock_floor_ns, warmup, iterations, runs, date_str);

Emit the same fields into the JSON. The report’s conditions section is then a paste rather than a transcription, and transcription is where errors enter.

H10 — The Report (R10)

Level 1

Write it in the order listed in R10. That order is not arbitrary — methodology and validation come before results so a reader knows whether to believe them, and the noise floor comes before comparisons so no difference is read as meaningful before its threshold is known.

The section people write badly is the last one. “What this does not show” is not a disclaimer; it is where you demonstrate you understand your own measurement’s limits, and it is the section a technical reader trusts you for.

On the flat results: state them plainly with their numbers and explain the mechanism. A null result with an explanation is a finding. A null result quietly omitted is a missing row someone will notice.

Level 2

A shape for the two hardest sections:

## Findings

1. Pipelining is the only optimisation with a significant effect here.
   Depth 8 reduced median service time 31% (41.2 → 28.4 us). It addresses
   idle time rather than per-operation cost, and idle time exists on any
   fabric. [Table 2, rows 1 and 4]

2. Inline data, periodic signalling, and one-sided operations showed no
   effect distinguishable from the 4.1% noise floor. This is the expected
   result on a software provider: each removes a cost — a DMA fetch, a
   completion, remote CPU involvement — that is a small fraction of the
   tens of microseconds the software transport itself costs. [Table 2]

3. Event-driven reaping was 16% worse than polling. Wakeup cost is real
   on any fabric; this is the one row where soft-RoCE gives a
   representative answer. [Table 2, row 5]

4. TCP outperformed RDMA on this link (iperf3 X Gbit/s vs Y Gbit/s),
   consistent with the TRD-00 baseline and for the same reason.

## What this does not show

- Nothing about hardware RDMA. Every figure is soft-RoCE, where the
  transport runs in kernel software. The absolute numbers are ~20x worse
  than a real adapter and the optimisation results do not transfer.
- Nothing about scaling. One connection, two nodes.
- Response-time figures at rates well below saturation only; the
  behaviour near saturation was not characterised.
- The 99.9th percentile is estimated from 10^5 samples, so it rests on
  ~100 observations and is correspondingly uncertain.

## What would change on hardware

Expectation, clearly labelled as such rather than measured: inline and
periodic signalling would become significant because the baseline drops
from ~41 us to ~2 us, so a cost that is 1% of the operation here becomes
a third of it there. The optimisations do not change; the denominator does.

Every numbered finding cites a table. That is the discipline that makes the document defensible — a reader can check any claim against the data without asking you.

The most important habit on this rung

Validate first, sweep second. Every other rung’s bugs announced themselves; this rung’s produce clean output that is quietly wrong, and the reference implementation is the only external check you have.

The Tool Boundary

The instrument here is another implementation of the same measurement. When your figure and theirs disagree, the disagreement is the information — investigate it rather than explaining it away, and assume your harness is at fault until you can show otherwise.

An AI assistant is appropriate for reviewing code once it works, clarifying a concept a document left unclear, and grading comprehension answers. It is not appropriate for writing or debugging the implementation, and it is emphatically not appropriate for interpreting your results — the findings section is where you demonstrate you understand what you measured.
