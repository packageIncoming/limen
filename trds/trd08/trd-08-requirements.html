TRD-08: Benchmark Harness

Requirements — Limen RDMA Transport Project
Depends on: TRD-07  |  Difficulty: Medium  |  Estimated: 3–4 sessions

Objective

Build limen_bench: a measurement harness producing defensible latency and bandwidth figures across payload sizes and across every option TRD-07 made selectable. It must avoid coordinated omission, report distributions rather than summaries, capture its own conditions, quantify its own variance, and validate against a reference implementation before any of its numbers are believed.

Then write the report. That artifact is the deliverable this entire ladder was building toward.

What This Is Not

Not an optimisation rung. You are measuring what TRD-07 built, not improving it. A finding that suggests a change is a finding to record, not to act on.

No CPU-cycle counters, cache-miss profiling, or flame graphs. Those answer why something is slow; this rung establishes whether.

No statistical significance testing. Report variance across runs and refuse to conclude anything smaller than it.

No multi-node scaling, no comparison against other RDMA libraries. Two nodes, one connection, validated against the reference micro-benchmarks.

Interface

./build/limen_bench -d <device> [-t <tcp_port>]
        --mode <latency|response|bandwidth|sweep>
        [-s <bytes>] [-n <iterations>] [--warmup <n>] [--runs <n>]
        [--rate <ops_per_sec>] [--op <send|write|read>]
        [ ...all TRD-07 options... ] [--json <path>] [--clock-floor] <peer>
ModeMeasures
latencyClosed-loop service time, one operation outstanding. Comparable to the reference tools.
responseOpen-loop response time against a schedule at --rate. Coordinated-omission-free.
bandwidthSustained throughput at one size with operations in flight.
sweepBandwidth and latency across a size sweep, and across the TRD-07 option matrix.

Exit codes are TRD-07’s, plus 9 for a validation discrepancy that exceeds the declared tolerance.

Technical Requirements

R1 — Clock Discipline, and Measure the Floor

Use clock_gettime(CLOCK_MONOTONIC). CLOCK_REALTIME can step and produce negative durations.

--clock-floor times ten thousand consecutive clock reads with no work between them and reports the median cost per call. Run it before anything else and record the figure in the report.

If the floor exceeds two percent of the smallest latency you intend to measure, say so in the report rather than quietly proceeding — a measurement whose instrument costs a meaningful fraction of the quantity is a measurement with a stated error bar, not an invalid one.

Stuck? → Hints H1

R2 — Warm-Up, and Justify the Number

Discard --warmup iterations before recording, defaulting to 1000. The reference tools do the same for the same reason.[3]

Justify the default empirically rather than by convention: run once with warm-up disabled, capture per-iteration latency for the first few thousand iterations, and identify where it flattens. Record that plot or table in the report and set the default from it.

Stuck? → Hints H2

R3 — Keep Every Sample, Report the Distribution

Retain every latency sample and compute percentiles by sorting once at the end. Do not summarise incrementally.

Report minimum, 50th, 90th, 99th, 99.9th, maximum, mean, and standard deviation — the reference tools’ column set plus the 90th.

Report the median and the mean side by side, and comment on the gap

t_typical in the reference output is the median, printed next to the mean deliberately: the comparison reveals distribution skew, and within roughly ten percent indicates a fairly flat distribution.[4] Your report must state the ratio and interpret it.

Also emit the raw samples to a file when --json is given, so the distribution can be re-analysed without re-running.

Stuck? → Hints H3

R4 — Avoid Coordinated Omission

Implement both modes and label them differently, because they measure different quantities.

  • --mode latency: closed loop, one operation outstanding, measured from issue. This is service time and it is what the reference tools measure.
  • --mode response: open loop at --rate, with each operation’s intended send time fixed in advance as start + i × interval, and latency measured from the intended time, not from when the send actually happened.

In response mode, when the harness falls behind schedule it must not sleep — it is already late, and the lateness is the measurement.

Run both at the same message size, report both, and explain the difference in the report. If the two are close, the system was keeping up; if the response figures are much worse at high percentiles, they are showing you queueing the closed loop concealed.

The report: output must name which quantity each figure is. A number labelled “latency” without saying which is the error this requirement exists to prevent.

Stuck? → Hints H4

R5 — Bandwidth

Measure sustained throughput with enough operations in flight to keep the adapter busy, over a duration long enough that start-up is negligible. Report average rather than peak.

Report in both MB/s and Gbit/s with the units labelled, and report message rate in operations per second separately — at small sizes the rate is the limiting quantity rather than the byte count.

Stuck? → Hints H5

R6 — The Sweeps

--mode sweep runs two sweeps and emits a table for each.

Size sweep: powers of two from 64 bytes to 1 MB, reporting latency percentiles and bandwidth at each. The shape of the curve is the result; a single figure at one size is not.

Option sweep: for each TRD-07 switch, the same measurement with it on and off, everything else held constant. Inline on and off; signalling period 1 and 16; pipeline depth 1 and 8; reaping poll and event; and for the operation type, two-sided send against one-sided write.

Each cell reports its median and 99th percentile, and the difference from the baseline as a percentage. Where the difference is smaller than the run-to-run variance from R7, the table must say so rather than reporting the percentage as though it meant something.

Stuck? → Hints H6

R7 — Variance Across Runs

--runs n repeats the entire measurement n times, defaulting to 5, and reports the spread of the median across runs.

That spread is your noise floor. No conclusion smaller than it may be drawn, and the report must state the floor before stating any comparison. A three percent improvement measured against five percent run-to-run variance is not an improvement.

Stuck? → Hints H7

R8 — Validate Against the Reference, and Establish Its Convention

Run ib_send_lat and ib_send_bw in a matched configuration — same message size, same iteration count, same transport type — and compare against your own figures.

First establish whether the reference reports the full round trip or half of it. Determine this empirically by measuring a full round trip yourself at the same size and seeing whether their figure matches yours or half of it. Record which. Assuming wrongly produces a clean factor-of-two error across an entire report.

Declare a tolerance in advance — 25% is reasonable on a software fabric — and exit 9 if the discrepancy exceeds it. A large discrepancy means one of you is wrong and the prior favours the reference implementation, so investigate your harness before concluding anything about your transport.

Stuck? → Hints H8

R9 — Capture the Conditions

Every result carries the environment needed to reproduce or dispute it: distribution and kernel release, hypervisor and virtual CPU count, RDMA device and provider, the port’s active MTU, the granted queue-pair capabilities and inline limit, the full effective configuration line from TRD-07 R1, the clock floor from R1, the warm-up count, iteration count, run count, and the date.

Emit it at the head of every report and into the JSON output. A number without its conditions cannot be reproduced by anyone, including you, next month.

Stuck? → Hints H9

R10 — The Report

Write docs/benchmark-report.md. This is the artifact the ladder exists to produce, and it is judged on honesty rather than on numbers.

It must contain:

  1. Methodology — what was measured, how, which clock, warm-up, run count, and the service-time-versus-response-time distinction from R4 stated explicitly.
  2. Conditions — R9’s block.
  3. Validation — the R8 comparison, the reference’s reporting convention as you determined it, and the discrepancy.
  4. Noise floor — R7’s spread, stated before any comparison.
  5. Results — both sweeps, with distributions rather than single figures.
  6. The TCP comparison — carried forward from TRD-00 R6, now with a real distribution beside it.
  7. Findings — what the numbers support, with every claim traceable to a table.
  8. What this does not show — the honest limits.
Most of TRD-07’s optimisations will show no measurable effect on this fabric. Record that as the finding it is. Section 9 of the Prior Knowledge document explains why, and a report that states “inline data showed no effect within a 4% noise floor, because the software provider’s per-operation cost dominates the DMA fetch it removes” is a stronger and more defensible document than one claiming improvements it did not measure.

The final section must state what would change on hardware and why — not as speculation dressed as data, but as a clearly-labelled expectation with its reasoning.

Stuck? → Hints H10

Deliverables

  • src/limen_bench.cpp, reusing the transport unchanged.
  • scripts/trd-08-tests.sh, executable, passing.
  • docs/benchmark-report.md — the eight sections from R10.
  • docs/results/ containing the JSON output from every run the report cites, so its tables can be regenerated.
  • An updated README.md whose summary states what the project does and what was measured, with the honest headline figure and its conditions.
  • Written answers to the comprehension questions.

What Comes Next

Nothing — this is the last rung. The transport is complete: two-sided and one-sided operations, a connection manager, an ownership layer, five tunable mechanisms, and a harness that measures them defensibly.

Two directions remain open. Hardware re-runs this harness against a real adapter with no code changes, and every flat line in your report becomes a curve — that comparison is the strongest artifact this project can produce, and it costs one evening once the cards exist. Atomics, memory windows, shared receive queues, and a multi-connection event loop extend the transport itself; each is a rung that could be written and none is needed for what this ladder set out to teach.
