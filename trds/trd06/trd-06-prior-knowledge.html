TRD-06: One-Sided Operations

Prior Knowledge — Limen RDMA Transport Project
Depends on: TRD-05  |  Difficulty: Medium  |  Estimated: 3–4 sessions

1   Where This Fits

Five rungs have built toward one thing. TRD-01 registered memory and printed a remote key that nothing used. TRD-02 set queue-pair access flags for operations that did not exist yet. TRD-05 carried an address, a length, and that remote key across the handshake and printed them on a line no code consumed.

This rung consumes all of it. You will write directly into a peer’s memory and read directly out of it, without the peer’s software participating in either.

This is the operation the technology exists for. Everything before it — the registration, the protection domains, the keys, the state machine — is scaffolding erected so that this operation can be safe. Two-sided SEND and RECV are a convenience that RDMA offers; one-sided access is what RDMA is.

It is also the rung with the most dangerous failure mode in the ladder, and the danger is not in the operations. It is in knowing when they have finished.

2   What Changes

In TRD-03 both sides ran. The sender posted, the receiver had posted a matching receive, and both reaped a completion. Data landed in a buffer the receiver had chosen, and the receiver was told it arrived.

One-sided operations remove the receiver from all of that.

Two-sided (TRD-03)One-sided (this rung)
Remote posts a receiveRequired, or RNRNot required, not consumed
Destination addressChosen by the receiverChosen by the sender, carried in the request
Remote completionYes — the arrival notificationNone
Remote CPUReaps and processesExecutes nothing, learns nothing
Needs from the peerA connectionA connection, a remote address, and an rkey
Local completionYes, if signalledYes, if signalled — unchanged

The local side is almost unchanged: you post a work request and reap a completion exactly as before. What disappears is everything on the far side.

A one-sided completion means less than a two-sided one

On an IBV_WR_SEND, your completion arrives after the peer’s adapter has acknowledged, so it tells you the message was delivered and that the peer’s receive buffer was consumed. On an IBV_WR_RDMA_WRITE, your completion tells you the write was acknowledged — and nothing whatever about whether the peer has noticed, because the peer cannot notice. That gap is what section 6 is about.

3   The Work Request

The structure is TRD-03’s, with the previously unused union populated:

struct ibv_send_wr {
    uint64_t             wr_id;
    struct ibv_send_wr  *next;
    struct ibv_sge      *sg_list;      /* LOCAL buffer, as before  */
    int                  num_sge;
    enum ibv_wr_opcode   opcode;       /* RDMA_WRITE / RDMA_READ   */
    unsigned int         send_flags;
    __be32               imm_data;     /* WRITE_WITH_IMM only      */
    union {
        struct {
            uint64_t remote_addr;      /* the PEER's address       */
            uint32_t rkey;             /* the PEER's key           */
        } rdma;
        /* ... atomic, ud ... */
    } wr;
};

Three fields describe two different machines, and keeping them straight is the whole of the mechanical difficulty:

FieldWhoseSource
sg_list[].addrYoursYour own registered buffer
sg_list[].lkeyYoursmr->lkey, as in TRD-03
wr.rdma.remote_addrTheirsThe ConnInfo from TRD-05’s handshake
wr.rdma.rkeyTheirsThe same ConnInfo

A local key where a remote key belongs, or your own address where the peer’s belongs, produces a remote access error rather than anything that names the mistake.

Opcodes

OpcodeEffect
IBV_WR_RDMA_WRITEYour local buffer is written into the peer’s memory at remote_addr. No remote completion, no receive consumed.
IBV_WR_RDMA_READThe peer’s memory at remote_addr is fetched into your local buffer. Your completion means the data has arrived.
IBV_WR_RDMA_WRITE_WITH_IMMA write that additionally carries four bytes of immediate data, consumes a receive request on the peer, and generates a remote completion.[3][6] Section 6.

RDMA_READ reverses the direction of every other operation you have posted: the scatter-gather list is where data will be deposited, not where it is read from. On a read, your local region needs IBV_ACCESS_LOCAL_WRITE, because your own adapter writes into it.

4   Two Access Gates, Again

An incoming one-sided operation passes two independent checks, and both were configured rungs ago:

  1. The queue pair — qp_access_flags, set at the INIT transition in TRD-02 R5, or supplied through the connection manager in TRD-05. Does this connection permit this class of operation at all?
  2. The memory region — the flags passed to ibv_reg_mr in TRD-01. Does this specific buffer permit this access from anyone?

Both must allow it.[4] Failing either produces IBV_WC_REM_ACCESS_ERR on the initiator, which does not distinguish between them.

OperationRemote QP needsRemote MR needs
RDMA_WRITEIBV_ACCESS_REMOTE_WRITEREMOTE_WRITE + LOCAL_WRITE
RDMA_READIBV_ACCESS_REMOTE_READREMOTE_READ

The LOCAL_WRITE requirement in the first row is the constraint TRD-01’s R8 made you provoke deliberately — a remote write is performed by the local adapter writing into local memory, so local write permission is its prerequisite.

The trust boundary, now real

Handing a peer your rkey grants unsupervised access to that region for as long as the registration lives. Your software is not consulted per operation, is not notified when one occurs, and cannot revoke the grant short of deregistering. TRD-01 described this; this rung is where it becomes an actual capability held by an actual peer.

5   RDMA READ and Responder Resources

A read is a request-and-response, so unlike a write it cannot be fire-and-forget. Two attributes bound how many may be in flight, and they are not the same field:

AttributeSet atBounds
max_rd_atomicRTS (TRD-02 R7)Reads and atomics you initiate that may be outstanding
max_dest_rd_atomicRTR (TRD-02 R6)Reads and atomics you serve that may be outstanding

Through the connection manager these become initiator_depth and responder_resources in rdma_conn_param, which TRD-05 R8 had you populate. Both are bounded by the device attributes captured in TRD-01: max_qp_init_rd_atom and max_qp_rd_atom respectively.

Posting more concurrent reads than the negotiated depth allows does not queue politely — it produces a transport error. If both sides set 1, as this ladder does, exactly one read may be outstanding at a time.

Ordering also differs. Write-class requests — SEND, RDMA_WRITE, RDMA_WRITE_WITH_IMM — are totally ordered within a send queue. Requests that return a value are tracked separately, so a read issued after a write is not automatically guaranteed to observe that write’s effect unless it is fenced.[7] IBV_SEND_FENCE exists for exactly this: it holds a request until all prior requests on the queue have completed.

6   How the Receiver Finds Out — and the Trap

This is the section that matters. An RDMA_WRITE lands in the peer’s memory and tells the peer nothing. Detecting it is a protocol you design, and there are three approaches, of which the most obvious one is wrong.

Figure 1 — Three ways to detect a one-sided write. Only two of them work.

A — polling the last byte, and why it fails

The natural idea: the payload is written in order, so watch the final byte, and when it changes the message has landed.

It is wrong. Within a single message, the order in which bytes are placed into the destination is not guaranteed. Reliable-connected service guarantees that messages are delivered reliably and in order relative to one another — it does not guarantee anything about the order of byte placement inside one message. A large write may be segmented, and nothing requires the final segment to land last.[2]

The failure profile is the worst available. On a short message that fits one packet, it works. On a quiet fabric, it works. Under load, at larger sizes, the observer occasionally sees the last byte set while earlier bytes still hold stale data — and reads a torn buffer with no error anywhere. This is the single most-repeated mistake in application-level RDMA code, and the correct advice is explicit: use work completions to know that the content is in memory.[2]

B — a separate flag write

Post two requests: the payload, then a second, tiny RDMA_WRITE to a distinct flag location. The peer polls the flag.

This is correct, and the reason is precise. Write-class work requests within one send queue are totally ordered against each other.[7] The flag write is a separate message, issued after the payload write, so it cannot be placed before the payload write has completed. Observing the flag therefore implies the payload is entirely present.

What it costs: a second round trip’s worth of request, and a polling loop burning a core on the remote side. What it preserves: the remote CPU never enters the data path, which is the property one-sided operations exist to provide.

C — write with immediate data

IBV_WR_RDMA_WRITE_WITH_IMM performs the write and additionally delivers four bytes of immediate data to the peer, generating a completion there.[3][5][6] The peer polls its completion queue exactly as in TRD-03 and finds an IBV_WC_RECV_RDMA_WITH_IMM carrying the immediate value.

The immediate field is genuinely useful — a length, a sequence number, a buffer index — and it removes the need for in-band framing.

It consumes a receive work request on the peer.[3][6] If none is posted, the responder returns a receiver-not-ready error, exactly as for a plain SEND.[5] Everything TRD-03 taught about RNR applies again, including that the connection manager fixed the minimum RNR timer at 655 ms. A write with immediate is a two-sided operation wearing a one-sided opcode, and calling it one-sided is a category error that produces a hang.

Which to choose is a real design decision. Flag polling wins on latency and keeps the receiver passive; immediate data wins on CPU efficiency and scales to many connections, because one completion queue can be polled instead of many memory locations. Production transports use both, in different places.

8   What Is Deliberately Left Out

No atomics. Compare-and-swap and fetch-and-add complete the one-sided family and are the basis of RDMA-based locking and lock-free remote data structures. They add a third access flag and their own outstanding-operation accounting, and nothing here needs them.

No scatter-gather across several remote regions, no memory windows, no dynamically re-registered buffers. One region, one address, exchanged once at connection time.

No credit scheme. The write-with-immediate path reintroduces the receiver-not-ready condition and this rung handles it by posting enough receives, exactly as TRD-03 did. Real flow control remains unbuilt.

And no measurement. One-sided operations should be dramatically cheaper than two-sided ones on real hardware, and on the software provider they are not, for the reasons in TRD-00’s section 9. TRD-08 is where the difference becomes visible.

Read before starting:

  • ibv_post_send(3)[1] — the opcode list and the wr.rdma union. You have read this page twice; read the parts you skipped.
  • RDMAmojo on ibv_post_send[3] — specifically the paragraph on immediate data consuming a receive request on the remote queue pair, and the comment thread on access-flag failures.

Read while implementing:

  • RDMAmojo on Fence[2] — short, and it contains the discussion that section 6 rests on, including why the last byte of a message is not a safe indicator.
  • ibv_reg_mr(3)[4] — the access flags, for the third time and the first time they all matter at once.

Reference as needed:

  • “Design and Evaluation of an RDMA-aware Data Shuffling Operator”[5] — a clear published treatment of the passive-versus-active receiver distinction and the synchronisation each requires.
