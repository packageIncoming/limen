TRD-07: Completion Efficiency

Requirements — Limen RDMA Transport Project
Depends on: TRD-06  |  Difficulty: High  |  Estimated: 4–6 sessions

Objective

Make every completion-side optimisation a selectable runtime option: inline data, unsignaled sends with periodic signalling, completion-queue moderation, event-driven reaping, and pipelining depth. Each must be independently switchable, correct in isolation and in combination, and reportable — so that TRD-08 can measure them against one another rather than against belief.

What This Is Not

Not a performance rung. None of these will measurably help on the software provider, for the reason TRD-00 §9 gives. You are building mechanisms and the switches that select them; TRD-08 produces the numbers.

No conclusions. Do not record that inline data is worth some percentage — you have not measured it and the figure would be from someone else’s hardware. Record what each technique trades.

No adaptive tuning, no buffer allocator, no multi-queue or per-core completion vectors. A fixed ring of buffers indexed by sequence number is sufficient and is not a general allocator.

Technical Requirements

R1 — Report the Effective Configuration

Print the config: line before any transfer, showing what is actually in force rather than what was requested. Where a request was clamped or refused, show the effective value.

Inline reports the granted max_inline_data, not the requested one. Moderation reports unavailable when the provider refuses it. Pipeline depth reports the value after clamping against the granted max_send_wr.

--report-config prints this line and exits 0 without connecting, so the suite can inspect a configuration without a peer.

Stuck? → Hints H1

R2 — Inline Data

Request max_inline_data in ibv_qp_init_attr.cap before creating the queue pair, read back what was granted, and report it.

With --inline, set IBV_SEND_INLINE on sends whose payload fits the granted limit. A payload exceeding it must fall back to a normal send rather than failing — and the fallback must be reported once, not silently.

Because inline copies the payload into the work request, the send buffer is reusable the moment ibv_post_send returns.[1] Your buffer-reuse tracking from R4 must account for that, since it is the only case in this ladder where TRD-03 §10’s ownership rule does not apply.

Stuck? → Hints H2

R3 — Periodic Signalling

With --signal-every n, set IBV_SEND_SIGNALED on every nth send and omit it otherwise. Report the count of send completions actually reaped; at n=16 over 1000 iterations it should be about 63, not 1000.

Signal the final send of a run regardless of the period, so that the run terminates with a known-complete send queue rather than with unreported work outstanding.

The period must leave the send queue drainable. Completions are what free send-queue entries, so a period approaching the queue depth fills it and ibv_post_send returns ENOMEM with every request having succeeded. Validate that signal_every is comfortably less than the granted max_send_wr and reject a value that is not, at argument-parse time.
Stuck? → Hints H3

R4 — Buffer Reuse Under Periodic Signalling

With signalling suppressed, you no longer learn when each individual buffer is free. Maintain a ring of at least signal_every send buffers and reuse a slot only once a completion has been reaped that covers it.

Work requests on a send queue complete in order, so a completion for request k establishes that every request up to k has completed. Track the highest covered sequence number and refuse to reuse beyond it.

Payload verification from TRD-03 R7 must continue to pass with zero mismatches at every signalling period the suite exercises. A reuse bug here produces corruption that appears only at higher rates, which is exactly the profile that survives testing.

Stuck? → Hints H4

R5 — Pipelining

With --pipeline depth, keep up to depth sends outstanding before reaping. Clamp against the granted max_send_wr and report the clamped value.

For RDMA_READ, the bound is different and much lower: the negotiated max_rd_atomic from TRD-06 §5. If the program supports a read mode, clamp reads separately and report both limits — conflating them produces a transport error that names neither.

Stuck? → Hints H5

R6 — Event-Driven Reaping

With --reap event, create a completion channel, associate it with the completion queue at creation, and block on events rather than spinning.

Implement the full sequence from §6 of the Prior Knowledge document: arm before any completion can arrive; re-arm after every event, because a notification disarms the queue;[2] drain completely on every event, because only completions added after the arm will notify;[3] and treat an event carrying no completion as normal rather than as an error.[3]

Impose a timeout on the blocking wait. Exit 8 if it expires — a distinct code, because a hang here has a specific cause and R8 exists to make you find it.

Stuck? → Hints H6

R7 — Batched Acknowledgement

Count events and acknowledge them in batches rather than one at a time. ibv_ack_cq_events takes a mutex and is relatively expensive on the data path.[2][3]

Every event must be acknowledged before the completion queue is destroyed, so flush the outstanding count during teardown. An unacknowledged event blocks destruction — the same class of hang as TRD-05’s unacknowledged connection-manager event, and worth recognising as the same shape.

Report received and acked counts on the events: line. They must be equal at exit.

Stuck? → Hints H7

R8 — Close the Arming Race, and Prove You Did

A completion arriving between your final poll and your call to ibv_req_notify_cq generates no notification, and the thread then blocks forever with work in the queue. The specification’s remedy is to poll once more after arming.[4]

Implement it, and count how many times that extra poll returns something. Report it as race_polls_hit on the events: line.

That counter is the requirement. A non-zero value is direct evidence that the race occurred and that your guard caught it; a zero value across a long run at high pipeline depth tells you the window was never hit here, which is not the same as it being impossible. Record both what you observed and what it establishes in docs/efficiency-notes.md.

Also provide --broken-arming, a hidden flag that omits the extra poll. The suite runs it at high concurrency and expects a timeout rather than completion; if it completes, say so honestly — the window is narrow and the software provider makes it narrower.

Stuck? → Hints H8

R9 — Moderation, Optional and Graceful

With --moderate count:usec, configure completion-queue moderation via ibv_modify_cq.

This is an optional provider capability and the software provider does not implement it. A failure is not an error: report moderation=unavailable on the config line, continue, and exit normally. A rung that refuses to run because an optimisation is unsupported is worse than one that reports the fact.

Where it is supported, note in docs/efficiency-notes.md that the period is added latency in the worst case — a 16-microsecond period delays a completion by up to 16 microseconds.

Stuck? → Hints H9

R10 — Correctness Across the Matrix, Regressions, Leaks

Every combination must be correct. The suite exercises a matrix of inline on and off, signalling periods of 1 and 16, pipeline depths of 1 and 8, and both reaping modes, and every cell must complete with zero mismatches.

Regressions: the TRD-03 suite and the TRD-05 suite must pass with the defaults, which are exactly TRD-06’s behaviour. Defaults that change observable behaviour mean the options are not options.

Teardown gains the completion channel, destroyed after the completion queue that references it. Leak checks on the poll path, the event path, and a run that exits through R6’s timeout.

Stuck? → Hints H10

Deliverables

  • limen_pingpong, extended with every option above, defaults unchanged.
  • A limen::CompletionChannel wrapper satisfying TRD-04’s static contract, declared so that it outlives the completion queue that references it.
  • scripts/trd-07-tests.sh, executable, passing.
  • docs/efficiency-notes.md recording: the granted inline limit on this fabric; the R8 race-counter observation and what it does and does not establish; whether moderation was available; and a table of the five techniques naming what each trades away — without performance claims, since none have been measured.
  • Written answers to the comprehension questions.

What Comes Next

TRD-08 measures all of it. Every switch built here becomes a variable in a sweep, and the trades named in your notes become numbers — latency percentiles across payload sizes with inline on and off, throughput against signalling period, and CPU cost against reaping mode.

It is also the rung where the hardware question resolves. These mechanisms reduce costs that are noise beside the software provider’s own overhead, so a sweep on rxe will show them doing approximately nothing. That result is honest and worth recording, and it is the cleanest argument for what a real adapter contributes.
