TRD-05: Connection Management

Hints — Limen RDMA Transport Project
Level 1 = nudge  |  Level 2 = stronger push  |  Try Level 1 for 15+ minutes before escalating

Level 1 points at the right place. Level 2 names the mechanism.

The characteristic failure here is a hang during teardown — the program does all its work, prints its results, and then stops without exiting. That is an unacknowledged event blocking a destructor, and it is the reason R3 exists. Build the Event type before anything else; every subsequent requirement depends on acknowledgement being automatic, and debugging a teardown hang without it is unpleasant.

H1 — EventChannel (R1)

Level 1

The simplest of the three. One creation function taking no arguments, one destruction function returning nothing. The shape is TRD-04's protection domain with different calls.

The destruction function returns void, which is a fourth release convention to add to the three you already normalised. Decide what close() should return when there is nothing to report, and keep it consistent with the others.

Note that the interface declares a static create() rather than a constructor taking nothing — think about why a default constructor and an acquiring constructor cannot both take zero arguments.

Level 2
EventChannel EventChannel::create() {
    EventChannel c;
    c.ch_ = rdma_create_event_channel();
    if (!c.ch_) throw VerbsError("rdma_create_event_channel", errno);
    return c;                              /* move, guaranteed elided */
}

int EventChannel::close() noexcept {
    if (!ch_) return 0;
    rdma_destroy_event_channel(ch_);       /* returns void */
    ch_ = nullptr;
    return 0;
}

The static factory sidesteps the ambiguity: the default constructor produces the empty state, and create() produces an acquired one. Both would otherwise need to be nullary constructors.

Returning 0 unconditionally from close() is honest here — the underlying call reports nothing, so there is nothing to report. Do not invent a status.

H2 — ConnectionId, With Adoption (R2)

Level 1

The creating constructor is routine. Adoption is the new idea: a way to construct a wrapper around a handle that already exists, without calling any acquisition function.

Make it a named static function rather than a constructor taking a raw pointer. A constructor from rdma_cm_id * would be implicitly callable in places you did not intend, and the whole point is that adopting is a deliberate transfer of responsibility. The name is the documentation.

The qp() accessor reads a field on the identifier that the library fills in when the queue pair is created. It is null before that, and every accessor on this type needs the same empty-state guard as TRD-04's.

Level 2
ConnectionId::ConnectionId(EventChannel &ch, rdma_port_space ps) {
    if (rdma_create_id(ch.get(), &id_, nullptr, ps))
        throw VerbsError("rdma_create_id", errno);
}

ConnectionId ConnectionId::adopt(rdma_cm_id *id) noexcept {
    ConnectionId c;
    c.id_ = id;                            /* no acquisition; we take over */
    return c;
}

ibv_qp *ConnectionId::qp() const noexcept { return id_ ? id_->qp : nullptr; }

int ConnectionId::close() noexcept {
    if (!id_) return 0;
    if (id_->qp) rdma_destroy_qp(id_);     /* before the id itself */
    int rc = rdma_destroy_id(id_) ? errno : 0;
    id_ = nullptr;
    return rc;
}

The queue pair created by rdma_create_qp is owned by the identifier, so destroy it through rdma_destroy_qp(id) before destroying the identifier. This is the one place where the queue pair is not a TRD-04 QueuePair — the CM created it and the CM's own function destroys it.

rdma_create_id takes a third argument for user context. Passing nullptr is fine here; a server tracking many connections would use it to attach per-connection state to the identifier the event hands back.

H3 — Event, Acknowledged by Destruction (R3)

Level 1

Write this one first. Everything else assumes it.

The constructor blocks until an event arrives, which makes it unusual — a constructor that waits. That is acceptable here and is what makes the calling code read as a sequence of steps rather than as a state machine.

The destructor acknowledges. Make ack() idempotent by the same clear-the-handle pattern as every other close(), so an explicit acknowledgement followed by scope exit is safe.

Think about what happens to the accessors after an explicit ack(). The event structure is gone, so every one of them must handle that — and the answer that removes the problem entirely is to copy what you need out of the structure at construction.

Level 2
Event::Event(EventChannel &ch) {
    if (rdma_get_cm_event(ch.get(), &ev_))
        throw VerbsError("rdma_get_cm_event", errno);
    /* Snapshot what survives acknowledgement. */
    type_   = ev_->event;
    status_ = ev_->status;
    id_     = ev_->id;
}

int Event::ack() noexcept {
    if (!ev_) return 0;
    int rc = rdma_ack_cm_event(ev_) ? errno : 0;
    ev_ = nullptr;
    return rc;
}

Event::~Event() noexcept {
    if (int e = ack(); e != 0) report_release_failure("rdma_ack_cm_event", e);
}

rdma_cm_event_type Event::type()   const noexcept { return type_; }
const char        *Event::name()   const noexcept { return rdma_event_str(type_); }
int                Event::status() const noexcept { return status_; }
rdma_cm_id        *Event::id()     const noexcept { return id_; }

Snapshotting the three scalar fields at construction means the accessors work whether or not the event has been acknowledged, which removes an entire category of question. The identifier pointer remains valid after acknowledgement because the identifier is a separate object with its own lifetime — only the event structure and its private data are released.

To confirm the type is doing its job, temporarily comment out the destructor's ack() and run the program. It will complete its work and then hang. Restore it. That thirty-second experiment is worth more than reading the rule.

H4 — Private Data Copied Out (R4)

Level 1

One function, a few lines, and the design constraint is what is absent from the interface rather than what is present.

The amount actually sent is a field on the connection parameters inside the event, not the size of the buffer. Use it. A payload shorter than the buffer is normal and the remainder is zeroed, so reading the whole buffer produces trailing zeros that look like a valid but wrong value.

Copy at construction rather than on demand, for the same reason as H3's snapshot — then the function works regardless of when it is called, and the ordering question disappears.

Level 2

In the constructor, alongside the other snapshots:

pd_len_ = 0;
if (ev_->param.conn.private_data && ev_->param.conn.private_data_len > 0) {
    pd_len_ = std::min<std::size_t>(ev_->param.conn.private_data_len, sizeof pd_);
    std::memcpy(pd_, ev_->param.conn.private_data, pd_len_);
}
std::size_t Event::copy_private_data(void *dst, std::size_t len) const noexcept {
    std::size_t n = std::min(len, pd_len_);
    if (n) std::memcpy(dst, pd_, n);
    return pd_len_;                    /* how much was available, not copied */
}

A fixed 256-byte member covers both direction limits with room to spare. Returning the available length rather than the copied length lets a caller detect truncation.

The interface deliberately offers no way to obtain ev_->param.conn.private_data. That is the requirement: with no accessor, a read after acknowledgement cannot be written.

H5 — Client Connection Path (R5)

Level 1

Four steps, three of which are "call this, then wait for that event." Write a small helper that constructs an Event, checks it is the type you expected, and reports and exits if not — you will call it three times and the error handling is identical each time.

The address needs to be a sockaddr. Build it with the ordinary networking calls; there is nothing RDMA-specific about it.

For the timeout: rdma_resolve_addr takes one in milliseconds for the resolution itself, but the event retrieval is separate and blocks independently. Both need bounding, and the one people forget is the second.

Level 2
static Event expect(EventChannel &ch, rdma_cm_event_type want) {
    Event e(ch);
    std::printf("cm: event %s\n", e.name());
    if (e.type() != want) {
        std::fprintf(stderr, "cm: expected %s, got %s (status %d)\n",
                     rdma_event_str(want), e.name(), e.status());
        throw VerbsError("unexpected cm event", EPROTO);
    }
    return e;                              /* moved out; acked by the caller's scope */
}
sockaddr_in dst{};
dst.sin_family = AF_INET;
dst.sin_port   = htons(port);
inet_pton(AF_INET, peer, &dst.sin_addr);

if (rdma_resolve_addr(id.get(), nullptr, (sockaddr *)&dst, 2000))
    throw VerbsError("rdma_resolve_addr", errno);
expect(ch, RDMA_CM_EVENT_ADDR_RESOLVED);

if (rdma_resolve_route(id.get(), 2000))
    throw VerbsError("rdma_resolve_route", errno);
expect(ch, RDMA_CM_EVENT_ROUTE_RESOLVED);

if (rdma_create_qp(id.get(), pd.get(), &init))
    throw VerbsError("rdma_create_qp", errno);

rdma_conn_param cp{};
/* ... R8 ... */
if (rdma_connect(id.get(), &cp)) throw VerbsError("rdma_connect", errno);
Event est = expect(ch, RDMA_CM_EVENT_ESTABLISHED);

To bound the blocking retrieval, set the channel's descriptor non-blocking and poll it:

int fd = ch.get()->fd;
fcntl(fd, F_SETFL, fcntl(fd, F_GETFL) | O_NONBLOCK);
pollfd p{fd, POLLIN, 0};
if (poll(&p, 1, timeout_ms) <= 0) { /* report and exit 7 */ }
Event e(ch);                               /* now returns immediately */

Note the assignment in expect: the returned Event is moved into the caller's scope and acknowledged when that scope ends. Constructing it as a temporary that is immediately discarded also works and acknowledges sooner — but bind it to a name when you need to read its private data.

H6 — Server Listen and Accept Path (R6)

Level 1

Bind and listen are unremarkable. The whole content of this requirement is what you do with the connect request event.

Three things must happen before that event goes out of scope, and the order matters: read its private data, take ownership of its identifier, and only then let it be acknowledged. Getting the first one after the acknowledgement is the failure R4 exists to prevent — and it is much easier to hit here than in the client path, because the event is doing two jobs at once.

Be explicit about which identifier each call takes. The listener and the connection are both in scope and both are valid arguments to every function, so a mix-up compiles.

Level 2
ConnectionId listener(ch, RDMA_PS_TCP);
if (rdma_bind_addr(listener.get(), (sockaddr *)&src))
    throw VerbsError("rdma_bind_addr", errno);
if (rdma_listen(listener.get(), 1))
    throw VerbsError("rdma_listen", errno);
std::printf("cm: listening on port %d\n", port);

ConnInfo peer_info{};
ConnectionId conn;
{
    Event req = expect(ch, RDMA_CM_EVENT_CONNECT_REQUEST);
    req.copy_private_data(&peer_info, sizeof peer_info);   /* FIRST */
    conn = ConnectionId::adopt(req.id());                  /* then adopt   */
    std::printf("cm: event CONNECT_REQUEST (new id adopted)\n");
}                                                          /* acked here   */

if (rdma_create_qp(conn.get(), pd.get(), &init))
    throw VerbsError("rdma_create_qp", errno);

rdma_conn_param cp{};
/* ... R8, with our own ConnInfo as private data ... */
if (rdma_accept(conn.get(), &cp)) throw VerbsError("rdma_accept", errno);
expect(ch, RDMA_CM_EVENT_ESTABLISHED);

The braces around the connect-request block are deliberate: they make the acknowledgement point visible, and everything that needs the event happens inside them. That is the shape to reach for whenever a resource's validity has a scope.

rdma_accept takes conn, never listener.[3] The listener remains bound and could accept again.

H7 — Handshake Payload (R7)

Level 1

Sixteen bytes of fixed-width fields. The only real work is byte order, and the only real trap is forgetting that a 64-bit address needs a 64-bit conversion — the standard header provides 16- and 32-bit helpers and not a 64-bit one on all platforms.

Put the size assertion next to the struct definition rather than in a test file. It documents the constraint at the point where someone would violate it by adding a field.

Fill it from the receive region's accessors — the address, the remote key, and the length are all things the TRD-04 MemoryRegion already exposes.

Level 2
struct ConnInfo {
    std::uint64_t addr;
    std::uint32_t rkey;
    std::uint32_t length;
};
static_assert(sizeof(ConnInfo) == 16, "unexpected layout");
static_assert(sizeof(ConnInfo) <= 56,  "exceeds the rdma_connect private data limit");
static ConnInfo to_wire(const MemoryRegion &mr) {
    return { htobe64((std::uint64_t)(uintptr_t)mr.data()),
             htobe32(mr.rkey()),
             htobe32((std::uint32_t)mr.size()) };
}
static ConnInfo from_wire(const ConnInfo &w) {
    return { be64toh(w.addr), be32toh(w.rkey), be32toh(w.length) };
}

htobe64 and be64toh are in <endian.h>. The 16-byte layout has no padding on any mainstream platform, and the first assertion is what tells you if that stops being true.

Verify the round trip locally before involving a peer: convert, convert back, compare. A byte-order bug here surfaces in TRD-06 as a remote access to an address that is not yours, which fails with a protection error naming nothing useful.

H8 — Connection Parameters (R8)

Level 1

Zero the structure, then set five fields. Two of them are bounded by device attributes you captured in TRD-01, and the pairing is not symmetric — one is bounded by what you can accept, the other by what you can issue.

One field you must not set: the queue pair number is ignored once a queue pair exists on the identifier, and setting it invites the belief that it is doing something.

Both sides populate a structure — the client's goes to rdma_connect and the server's to rdma_accept. The private data differs; the rest is the same.

Level 2
ConnInfo mine = to_wire(rx_mr);
rdma_conn_param cp{};
cp.private_data        = &mine;
cp.private_data_len    = sizeof mine;
cp.responder_resources = (uint8_t)std::min<uint32_t>(1, da.max_qp_rd_atom);
cp.initiator_depth     = (uint8_t)std::min<uint32_t>(1, da.max_qp_init_rd_atom);
cp.retry_count         = 7;
cp.rnr_retry_count     = (uint8_t)opt_rnr_retry;    /* 3-bit; 7 = infinite */

mine must outlive the call, but only the call — the library copies the contents.[2] A local is fine.

For docs/cm-notes.md, the sentence R8 asks for:

The CM configures InfiniBand QPs with a minimum RNR NAK timer of 0, which is
a 655 ms delay. TRD-02 set this field to 12 (0.64 ms) by hand. It is no longer
under our control, so the RNR retry interval is roughly 1000x longer than it
was in TRD-03. The finite-retry experiment still reports the same error; it
just takes seconds instead of milliseconds. This is not a defect.

H9 — Disconnection (R9)

Level 1

One call on the initiating side, and both sides then receive an event. The asymmetry is only in who calls; the handling is identical.

Write the waiting loop to tolerate an event you were not expecting rather than treating the first surprise as fatal. There is one event type in particular that can appear here legitimately and means nothing to this program.

Note that the non-initiating side is sitting in its event wait when the disconnect arrives, so nothing special is needed there — which is the useful property of driving everything through one channel.

Level 2
if (is_client) {
    std::printf("cm: disconnect requested\n");
    if (rdma_disconnect(id.get())) throw VerbsError("rdma_disconnect", errno);
}

for (;;) {
    Event e(ch);
    std::printf("cm: event %s\n", e.name());
    if (e.type() == RDMA_CM_EVENT_DISCONNECTED)   break;
    if (e.type() == RDMA_CM_EVENT_TIMEWAIT_EXIT)  continue;   /* nothing to do */
    std::fprintf(stderr, "cm: unexpected %s during shutdown\n", e.name());
    break;
}

TIMEWAIT_EXIT reports that the queue pair has left timewait and may be reused.[1] This program does not reuse queue pairs, so acknowledging and continuing is the whole handling. Treating it as unexpected produces a spurious error on a clean shutdown.

H10 — Delete the Side Channel (R10)

Level 1

Delete first, then fix what breaks — the same method as TRD-04's refactor, and for the same reason. Leaving the socket code in place while adding the CM path gives you two mechanisms doing one job and no compiler pressure to finish.

Count what goes: two sockets, the text encoding, the parsing, the ready marker, three attribute structures, three ibv_modify_qp calls, the GID query, the sequence number generation. It is a lot, and watching it go is the point of the rung.

Convince yourself the ready marker is genuinely unnecessary before removing it. R10 states why; make sure you agree, because if the reasoning is wrong you have reintroduced TRD-03's receiver-not-ready race.

Level 2

The ordering that makes the ready marker redundant: post receives, then call rdma_connect or rdma_accept. The handshake completes only after both sides have made their call, so ESTABLISHED on either side implies the peer had already posted. No message can arrive earlier because no connection existed.

/* both roles, before connecting or accepting */
for (unsigned i = 0; i < rx_depth; ++i) post_recv(id.qp(), rx_mr, i);
/* ... then rdma_connect / rdma_accept ... */

Verify the removal:

grep -nE '\b(socket|bind|listen|accept|connect)\s*\(' src/limen_pingpong.cpp \
  | grep -v rdma_
grep -n 'ibv_modify_qp' src/limen_pingpong.cpp

Both must be empty. The grep -v rdma_ is necessary because rdma_bind_addr, rdma_listen, rdma_accept, and rdma_connect all contain those words.

Note that post_recv now takes id.qp() — a raw ibv_qp * the CM owns — rather than a TRD-04 QueuePair. That is expected, and the comprehension questions ask about it.

H11 — Teardown, Regressions, Leaks (R11)

Level 1

Three new resources with an ordering that is only partly expressible through declaration order — the identifier must outlive its queue pair, the channel must outlive the identifier, and every event must be released before the identifier it concerns. The first two are containment; the third is not, because events are scoped locals rather than members.

Write down what declaration order does express and what it does not, then satisfy the remainder by scope. The braces from H6 are an example.

Run both regression suites before considering the rung done. They test different programs and both must pass — one untouched, one rewritten.

Level 2
class CmEndpoint {
    Context          ctx_;        /* destroyed 6th */
    EventChannel     ch_;         /* destroyed 5th */
    ProtectionDomain pd_;         /* destroyed 4th */
    MemoryRegion     rx_;         /* destroyed 3rd */
    MemoryRegion     tx_;         /* destroyed 2nd */
    ConnectionId     id_;         /* destroyed 1st — takes its qp with it */
};

The identifier goes first and destroys the queue pair the CM created for it, per H2's close(). The channel outlives the identifier because it is declared earlier. Events are not members and cannot be ordered this way — they are released by scope, which is why R3's RAII type is what makes the arrangement safe rather than merely tidy.

./scripts/trd-02-tests.sh --dev rxe0 --gid 3 --peer 10.0.0.1 --ssh you@10.0.0.1
./scripts/trd-03-tests.sh --dev rxe0 --gid 3 --peer 10.0.0.1 --ssh you@10.0.0.1

Leak-check three paths, the second of which is the one most likely to be wrong:

valgrind --leak-check=full ./build/limen_pingpong -d rxe0 -n 20 10.0.0.1
valgrind --leak-check=full ./build/limen_pingpong -d rxe0 -n 20 203.0.113.1  # no peer
valgrind --leak-check=full ./build/limen_pingpong -d rxe0 --rnr-retry 1 10.0.0.1

Debugging This TRD

QuestionInstrument
The program hangs after printing its resultsAn unacknowledged event. gdb -p <pid> and look for rdma_destroy_id in the backtrace.
Which event did I actually get?rdma_event_str on every event, printed unconditionally. Never branch on an event type without printing its name first.
Why was the connection rejected?event->status, and the peer's own output. A rejection is usually the other side failing at accept.
Is the payload arriving correctly?Print the ConnInfo on both sides, before and after byte-order conversion. Four numbers, and a mismatch is obvious.
Does the reference implementation work here?rping -s -a 10.0.0.1 -v -C 10. It uses exactly this API. If it fails, the fault is the fabric, not your code — same discipline as TRD-02.
Is the CM reaching the peer at all?sudo tcpdump -i any -n udp port 4791 during the handshake. The CM's own traffic is visible.
Address resolution failsConfirm the address is on the interface the rxe link was bound to in TRD-00. The CM resolves address to device, and an address on the wrong interface has no device.
Is my id ownership right?LIMEN_TRACE_RELEASE=1 and count the identifier releases. The server must release exactly two — the listener and the connection.
The single most useful check

Print every event by name as it arrives, on both sides, always. The event sequence is the state of the connection, and a program that reports it tells you where it stopped. One that branches silently tells you nothing, and this rung's failures are almost all "it stopped somewhere."

The Tool Boundary

Two habits carry this rung: the Event RAII type, which makes the worst failure unreachable, and printing every event name, which makes the rest diagnosable. Both are cheap and both are built before you need them.

An AI assistant is appropriate for reviewing code once it works, clarifying a concept a document left unclear, and grading comprehension answers. It is not appropriate for writing or debugging the implementation.
