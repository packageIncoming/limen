TRD-05: Connection Management

Prior Knowledge — Limen RDMA Transport Project
Depends on: TRD-04  |  Difficulty: Medium-High  |  Estimated: 4–5 sessions

1   Where This Fits

TRD-02 had you exchange four values over a hand-rolled TCP socket and then drive a queue pair through three transitions with eleven fields that had to be simultaneously correct. TRD-04 gave you types that own resources and release them in the right order without being told.

This rung deletes the first of those and stress-tests the second.

The RDMA connection manager performs the parameter exchange and the state transitions for you, driven by an IP address. All of TRD-02's bringup — the GID index, the address vector, the sequence numbers, the three ibv_modify_qp calls — disappears behind two function calls. You will delete the TCP side channel from the ping-pong program and never write one again.

What replaces it is an asynchronous event model with three ownership rules that do not fit the layer you just built. An identifier can be created by an event rather than by you. Destroying an identifier blocks until its events have been acknowledged. And a pointer handed to you inside an event becomes invalid at a moment you choose. Each of those is a real hazard, each is documented, and together they are the reason this rung exists rather than being a paragraph in TRD-02.

2   What the Connection Manager Is

librdmacm sits above libibverbs and provides connection establishment by IP address. It resolves an address to an RDMA device, resolves a route, exchanges endpoint parameters with the peer over the fabric's own management channel, creates the queue pair, and drives it to RTS.

The API is deliberately socket-shaped — bind, listen, accept, connect, disconnect — and the shape is a useful guide until it stops being one. The differences that matter:

The last row is the payoff. After RDMA_CM_EVENT_ESTABLISHED, the queue pair on id->qp is connected and ready — and you can post to it with exactly the code TRD-03 already contains.

3   The Event Channel

Every asynchronous result arrives through an event channel. rdma_create_event_channel() returns one; it holds a file descriptor, so it can be polled or made non-blocking, and by default rdma_get_cm_event() blocks until something arrives.[1]

struct rdma_cm_event {
    struct rdma_cm_id       *id;         /* the id this concerns          */
    struct rdma_cm_id       *listen_id;  /* for CONNECT_REQUEST           */
    enum rdma_cm_event_type  event;
    int                      status;     /* non-zero on the *_ERROR types */
    union {
        struct rdma_conn_param conn;
        struct rdma_ud_param   ud;
    } param;
};
Every event must be acknowledged

The event structure is allocated by the library and released by rdma_ack_cm_event(). There must be a one-to-one correspondence between successful gets and acks.[1][6] Failing to acknowledge does not merely leak — see section 6.

rdma_event_str() converts an event type to a printable name. Use it everywhere; the enumeration has more than a dozen members and an unexpected one is far more useful reported by name than by number.

rdma_accept is not called on the listening id. After rdma_listen, the connect request event delivers a newly created id — similar to a new socket, but already bound to a specific RDMA device — and rdma_accept is called on that.[3] The listener remains open for further requests.

5   Private Data

Both rdma_connect and rdma_accept carry an application payload to the peer, delivered in the corresponding event's param.conn.private_data. The contents are copied by the library, so your source buffer need not outlive the call.[2]

This is where TRD-06's remote key, address, and length travel. The exchange that TRD-02 built by hand over TCP becomes a struct in the handshake.

The limits are asymmetric, and small

56 bytes on rdma_connect, and 196 bytes on rdma_accept, for RDMA_PS_TCP.[2][3] The connect direction is the binding one. A remote key, a 64-bit address, and a length occupy sixteen bytes, so there is room — but not room for anything casual, and a payload designed against the accept limit will fail in the other direction.

Two further properties worth knowing. The received buffer may be larger than what the peer sent, with the remainder zeroed[1] — so never infer the payload length from the buffer length. And connections over iWARP require the active side to send the first message,[2] which does not affect RoCE but is the kind of transport-specific constraint that makes a hand-rolled protocol non-portable.

Encoding

The payload crosses machines, so fixed-width types and an explicit byte order are required, exactly as in TRD-02's text-based exchange. A packed struct with uint64_t and uint32_t members converted to network order is the straightforward answer. Do not send a struct with native padding and native endianness; it works between two identical nodes and is broken by construction.

6   Three Ownership Rules That Break the Layer

TRD-04 built a layer on the assumption that resources are created by you, owned by exactly one object, and released whenever you like. The connection manager violates all three assumptions, in three separate ways.

Rule 1 — An event creates an identifier

On RDMA_CM_EVENT_CONNECT_REQUEST, event->id references a new id created by the library.[1][3] You did not call anything to create it, and you are nevertheless responsible for destroying it.

So the server holds two identifiers with different origins: the listener it created, and the connection the event handed it. A wrapper type whose only constructor acquires a resource cannot represent the second. It needs an adopting constructor — one that takes an already-live handle and assumes responsibility for it. That is a genuinely different shape from the five wrappers of TRD-04, and it is the first thing this rung will make you add.

Rule 2 — Destruction blocks on acknowledgement

Destruction of an rdma_cm_id will block until related events have been acknowledged.[1][6] An unacknowledged event does not leak a few bytes — it deadlocks your destructor, and the program hangs during teardown with no diagnostic.

This is what makes the acknowledgement worth a type of its own. An event is a resource with a mandatory release, obtained from a function and released by another, whose omission has a consequence far worse than a leak. That is the exact shape RAII exists for:

class Event {
public:
    explicit Event(EventChannel &ch);      /* blocks until one arrives */
    ~Event() noexcept { if (ev_) rdma_ack_cm_event(ev_); }
    /* move-only, as in TRD-04 */
    rdma_cm_event_type type() const noexcept;
private:
    rdma_cm_event *ev_ = nullptr;
};

With that type, every early return and every exception acknowledges the event on the way out, and the deadlock becomes unreachable. Without it, one return on an error path in the middle of a handler produces a hang at shutdown that is very hard to attribute back to its cause.

Rule 3 — A pointer inside the event dies when you acknowledge

The private data buffer referenced by the event is deallocated by rdma_ack_cm_event.[1] So the payload you came for is invalidated by the call that releases the event — and if you are using the RAII type above, that call is a destructor running at a scope exit you may not be thinking about.

Copy the payload out before the event is acknowledged. Every time, without exception. The failure mode is a dangling read whose contents are frequently still intact, so it works in development and produces a wrong remote key under load.

Note the interaction: the RAII type from Rule 2 makes the acknowledgement automatic, which makes Rule 3 easier to get wrong, because there is no longer a visible rdma_ack_cm_event call to notice you are reading past. A well-designed Event type therefore does not expose the raw pointer at all — it exposes a function that copies the payload into a caller-supplied buffer, so reading after acknowledgement has no expression.

7   What the CM Takes Away

The convenience is not free, and one of the costs directly changes behaviour you observed in TRD-03.

The CM sets the minimum RNR timer to 0, meaning 655 ms

InfiniBand queue pairs established through the CM are configured with a minimum RNR NAK timer of 0, which corresponds to a delay of 655 ms.[2][3] TRD-02 had you set that field to 12, meaning 0.64 ms. You no longer control it.

The consequence is concrete: the receiver-not-ready retry interval from TRD-03 becomes roughly a thousand times longer. With rnr_retry at 7 the behaviour is unchanged — still an infinite hang — but with a finite retry count the failure now takes seconds rather than milliseconds to report. If TRD-03's suite suddenly seems slow after this rung, this is why, and it is not a defect.

What you retain: rdma_conn_param carries rnr_retry_count, retry_count, responder_resources, and initiator_depth,[2] so TRD-03's --rnr-retry flag survives, mapped to a different field. The retry count is a 3-bit value, and 7 still means infinite.

What you lose: the minimum RNR timer, the path MTU choice, the packet sequence numbers, the GID index, and direct control of the state transitions. For this project all of those are acceptable losses — and knowing precisely what was traded is why TRD-02 built them by hand first.

One more field worth noting: qp_num in rdma_conn_param is ignored by the library when a queue pair has already been created on the identifier.[3] Since you will always call rdma_create_qp first, you never set it.

8   Disconnection and Timewait

rdma_disconnect tears down the connection and both sides receive RDMA_CM_EVENT_DISCONNECTED. Either side may initiate; both must handle receiving it unprompted, because the peer may disconnect first.

After disconnection the queue pair enters a timewait state, and RDMA_CM_EVENT_TIMEWAIT_EXIT reports when it has left and the queue pair may be reused.[1] This ladder does not reuse queue pairs, so the event is one to recognise and acknowledge rather than act on — but a server that recycles connections would need it, and ignoring it there produces a resource that appears leaked and is merely waiting.

Two other events warrant explicit handling rather than a default branch. RDMA_CM_EVENT_DEVICE_REMOVAL requires you to destroy the associated identifier.[1] RDMA_CM_EVENT_ADDR_CHANGE signals that the underlying network device changed its hardware address, as after a bonding failover.[1] Neither will occur on a stable two-node lab, and a handler that treats an unexpected event as fatal — with a message naming it — is better than one that ignores it silently.

10   What Is Deliberately Left Out

One connection at a time. A server that holds many concurrent connections needs the event channel driven by a loop over a non-blocking descriptor with per-connection state, which is an event-loop design rather than an RDMA topic.

No reconnection, no retry on REJECTED, no address resolution timeouts beyond the default. All are policy, and policy without a use case is guesswork.

The hand-rolled bringup from TRD-02 is not deleted from the repository. limen_connect keeps it, and its test suite must keep passing. It is the reference for what the CM hides, and reading the two side by side is worth more than either alone.

11   Further Reading

Read before starting:

  • rdma_cm(7)[4] — the overview, and the index of every other page you will need. Read it once, completely.
  • rdma_get_cm_event(3)[1] — the event structure, the full event enumeration, the acknowledgement requirement, and the two ownership rules in section 6. The single most important page for this rung.

Read while implementing:

  • rdma_connect(3)[2] and rdma_accept(3)[3] — the connection properties, the asymmetric private data limits, and the RNR timer the CM imposes.
  • rping.c in the librdmacm examples[5] — you read this in TRD-00 when it was a tool. Read it now as a structural model; it is a complete implementation of exactly this rung.

Reference as needed:

  • rdma_cma.h[6] — the header's comments are terse and authoritative, and settle questions the manual pages leave ambiguous.
  • RDMA Aware Networks Programming User Manual, the CM event handling chapter[7] — a narrative walkthrough. Note the return-value caveat identified in TRD-02 before relying on its code.
