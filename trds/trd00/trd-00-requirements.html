TRD-00: Fabric Up

Requirements — Limen RDMA Transport Project
Depends on: None  |  Difficulty: Low  |  Setup: ~1 session  |  Requirements: 1–2 sessions

Objective

Watch RDMA work, and record what you see. You will make a software RDMA fabric carry real traffic, determine which of its addressing entries is correct and why, capture the packets on the wire to see what the encapsulation actually is, measure the fabric, and compare it against ordinary TCP over the same link.

The measurements and device attributes recorded here are consumed by later rungs. The packet capture is consumed by your understanding.

What This Is Not

You will not write RDMA code. No verbs calls, no queue pairs, no C++. The only file you author is a build configuration that locates two libraries and compiles nothing.

The programs you run are reference tools written by the people who wrote the libraries. Running someone else’s tool is not an achievement — reading what it tells you is the work, and every requirement below is about what you extract rather than what you execute.

Setup

Environment configuration. These are steps, not requirements: they have one correct outcome and no judgment in them. Work through them in order on both nodes, confirm at the gate in S4, then start the requirements.

If a step fails, consult the Setup Troubleshooting table at the end of this section before searching elsewhere.

S1 — Two virtual machines with a private network between them

Two Ubuntu 24.04 VMs, 2 vCPU and 2 GB each. Each needs two network adapters: NAT for internet access so package installation works, and a second adapter for RDMA traffic.

VirtualBox — power both VMs off, then from your host’s command line:

VBoxManage list vms
VBoxManage modifyvm "node-a" --nic2 intnet --intnet2 rdmalab
VBoxManage modifyvm "node-b" --nic2 intnet --intnet2 rdmalab

The name rdmalab is arbitrary and must match on both. On Windows, VBoxManage.exe lives in C:\Program Files\Oracle\VirtualBox\.

Equivalently through the interface: VM → Settings → Network → Adapter 2 tab → tick Enable Network Adapter → Attached to: Internal Network → Name: rdmalab. Leave Adapter 1 on NAT.

VMware: VM Settings → Add → Network Adapter → Host-only, on both VMs.

libvirt / virt-manager: attach both VMs to the same virtual network. The default NAT network already permits guest-to-guest traffic, so a second adapter is unnecessary — use the addresses libvirt assigned and skip to S5.

Internal Network is chosen over Host-only because it needs no configuration on the host at all. The host cannot reach the VMs on that adapter, which does not matter — only the VMs need to reach each other, and the NAT adapter still provides a console and internet.

S2 — Identify which interface is which

Boot both VMs. On each:

ip -br addr

Expect something like:

lo       UNKNOWN  127.0.0.1/8
enp0s3   UP       10.0.2.15/24
enp0s8   DOWN

VirtualBox NAT always assigns 10.0.2.15. The interface holding that address is Adapter 1 and is the wrong one. The other interface — the one with no address — is your RDMA interface.

Write its name down. Every remaining step uses it. These instructions say enp0s8; substitute yours.

S3 — Give each node an address

Node A:

sudo ip link set enp0s8 up
sudo ip addr add 10.0.0.1/24 dev enp0s8

Node B:

sudo ip link set enp0s8 up
sudo ip addr add 10.0.0.2/24 dev enp0s8

This does not survive a reboot, which is acceptable for now. To make it persistent on Ubuntu Server:

sudo tee /etc/netplan/99-rdma.yaml > /dev/null <<'EOF'
network:
  version: 2
  ethernets:
    enp0s8:
      dhcp4: no
      addresses: [10.0.0.1/24]
EOF
sudo chmod 600 /etc/netplan/99-rdma.yaml
sudo netplan apply

The chmod 600 is required — netplan on 24.04 refuses world-readable configuration files. Change the interface name and address per node.

If the address vanishes after a reboot anyway, cloud-init is rewriting the configuration:

echo 'network: {config: disabled}' | sudo tee /etc/cloud/cloud.cfg.d/99-disable-network-config.cfg

On Ubuntu Desktop, which uses NetworkManager instead:

sudo nmcli con add type ethernet ifname enp0s8 con-name rdma \
     ipv4.method manual ipv4.addresses 10.0.0.1/24
sudo nmcli con up rdma

S4 — Confirm connectivity, both directions

ip -br addr show enp0s8      # UP, with your 10.0.0.x address
# on node A
ping -c2 10.0.0.2
# on node B
ping -c2 10.0.0.1
Gate

Do not continue until both directions answer. If one works and the other does not, the silent node’s firewall is dropping traffic — do S7 on that node now, then retest. Everything after this point assumes S4 passes, and a failure here presents later as an RDMA problem that is not one.

S5 — Packages

sudo apt update
sudo apt install -y rdma-core ibverbs-utils rdmacm-utils perftest \
                    libibverbs-dev librdmacm-dev \
                    build-essential cmake git tcpdump iperf3

Confirm the tools resolve:

command -v ibv_devinfo ibv_rc_pingpong rping ib_send_bw rdma tcpdump iperf3

Seven paths should print. If one is missing, find its package with apt-file search bin/<name>.

S6 — Kernel modules

sudo modprobe rdma_rxe
sudo modprobe rdma_ucm
lsmod | grep -E 'rdma_rxe|rdma_ucm'

If modprobe reports the module is not found, your kernel image omits it:

sudo apt install -y linux-modules-extra-$(uname -r)
sudo modprobe rdma_rxe

The $(uname -r) matters — the unversioned package pulls modules for a kernel you are not running. If it installs a newer kernel as a dependency, reboot into it before continuing.

Persist across reboots:

printf 'rdma_rxe\nrdma_ucm\n' | sudo tee /etc/modules-load.d/rdma.conf

S7 — Firewall

RoCEv2 rides UDP port 4791.[3] On a disposable lab VM:

sudo ufw disable

Or permit the port specifically:

sudo ufw allow 4791/udp

Note which you did; R7 asks you to record it.

S8 — Create the software RDMA device

On the interface identified in S2 — not the NAT one:

sudo rdma link add rxe0 type rxe netdev enp0s8
rdma link show

Use the same device name rxe0 on both nodes so commands transfer between them.

Wrong interface? sudo rdma link delete rxe0 and repeat. This is the most common single mistake in this setup, and it produces a device that looks healthy and carries nothing.

Ignore any guide instructing you to build or run rxe_cfg, or to patch a kernel. That method predates the driver going in-tree in kernel 4.8 and is obsolete.[2] If a tutorial mentions it, the rest of that tutorial is stale too.

The link does not survive a reboot. Re-run the command, or write a one-line systemd unit — do not spend an hour on the unit.

S9 — Confirm the device is live

ibv_devices
ibv_devinfo -d rxe0 | grep -E 'state:|link_layer:|transport:'

Required:

  • state: PORT_ACTIVE (4)
  • link_layer: Ethernet

transport: InfiniBand (0) also appears and is correct — RoCE is the InfiniBand transport carried over Ethernet, and section 8 of the Prior Knowledge document explains why.

PORT_DOWN means the underlying interface is down or you bound the wrong one. Return to S8.

Technical Requirements

Everything below produces knowledge or an artifact. Setup produced a working machine; these produce the reason it was worth building.

R1 — Determine the Correct GID Index, and Say Why

A RoCE port has several entries in its GID table. Enumerate them, identify which is correct for this fabric, and record both the index and the reasoning.

Record in docs/fabric.md: every populated index with its type and GID value, which index you selected, and one sentence on why the others are wrong.

This is the rung’s first real decision. Section 8 of the Prior Knowledge document explains what a GID is and why the table has more than one entry. The index you find here is an argument you will type on every command for the rest of the ladder, and arriving at it by trial and error means meeting the same confusion again in TRD-02 with no idea why.

Stuck? → Hints H1

R2 — Move Bytes Over Raw Verbs

Complete an ibv_rc_pingpong exchange between the two nodes using the index from R1. Both processes must report a byte count and a throughput figure and exit 0.

Record the full command line and output from both sides in docs/fabric.md.

This is the raw-verbs path: the two processes exchange queue-pair parameters over a side TCP channel and drive the state transitions by hand. You will write this yourself in TRD-02 and TRD-03.

Stuck? → Hints H2

R3 — Move Bytes Over the Connection Manager, and Note the Difference

Complete an rping exchange of at least 10 verified iterations.

Then record, in one short paragraph in docs/fabric.md, what differed about how you invoked it compared to R2 — specifically what R2 required you to supply that R3 did not, and what that implies about which component determined it instead.

Both paths must work. A failure in exactly one isolates the fault precisely, which is why both are required rather than either.

Stuck? → Hints H3

R4 — See RoCEv2 on the Wire

Capture the traffic during an ib_send_bw run and confirm what the encapsulation actually is.

Record in docs/fabric.md: the capture command, the packet count observed, and confirmation that the traffic is UDP with destination port 4791.[3]

Why this capture is itself the lesson

You can capture this traffic because the software provider is the kernel — the packets traverse the ordinary network stack, so an ordinary packet sniffer sees them. On a hardware RDMA adapter the same capture typically shows nothing, because the adapter transmits directly and the host stack is never involved. Practitioners resort to vendor tools such as ibdump, or to a switch mirror port, precisely because the traffic does not pass through the host.

So this capture succeeding is direct evidence of what section 7 calls kernel bypass — by demonstrating its absence. Record one sentence in docs/fabric.md on why the same capture would be expected to fail on hardware.

Stuck? → Hints H4

R5 — Measure the Fabric

Run ib_send_bw and ib_send_lat between the nodes and record in docs/baseline-rxe.md:

  • Average bandwidth, with the message size it was measured at
  • Median and 99th-percentile latency, with its message size
  • Distribution, kernel release, hypervisor, vCPU count and memory per node
  • The MTU on both the network interface and the RDMA port
  • The date

The figures will be poor. That is the correct result, and section 9 of the Prior Knowledge document explains why. Record them as measured; do not investigate.

This file is the control for a comparison that has not happened yet. It costs ten minutes now and cannot be reconstructed later.

Stuck? → Hints H5

R6 — Compare Against TCP, and Explain the Result

Measure ordinary TCP throughput over the same link with iperf3, and record it in docs/baseline-rxe.md beside the R5 figures.

Then write two to four sentences explaining the comparison. Do not assume RDMA wins. Report what you actually measured and account for it using section 9’s explanation of what the software provider does and does not do.

This requirement exists because a number with nothing to compare it against teaches nothing. Whichever way the comparison falls, explaining it correctly requires understanding what is actually executing — which is the point of the rung.

Stuck? → Hints H6

R7 — Capture the Device Attributes

Record the full output of ibv_devinfo -v -d rxe0 in docs/baseline-rxe.md, and extract these fields explicitly: max_qp, max_qp_wr, max_cq, max_cqe, max_mr, max_sge, max_qp_rd_atom, active_mtu, and gid_tbl_len.

Also record in docs/fabric.md: the interface rxe0 is bound to, the two node addresses, whether you disabled the firewall or opened the port, and the exact commands to recreate the fabric after a reboot.

TRD-01 reads these attributes rather than assuming them, and TRD-02 sizes its queues against them. Code that hardcodes a queue depth learned from the software provider fails on a real adapter for reasons that look unrelated.

Stuck? → Hints H7

R8 — Repository and Build System

Initialise a Git repository with an initial commit and this layout:

limen/
├── CMakeLists.txt
├── README.md
├── .gitignore
├── docs/
│   ├── fabric.md
│   └── baseline-rxe.md
├── include/limen/
├── src/
├── scripts/
└── tests/

The CMakeLists.txt must require CMake 3.16 or later, declare a C++20 project, locate libibverbs and librdmacm and their headers as required, export a compilation database, configure cleanly, and define no build targets.

A required lookup that fails is an environment problem — the class of problem this entire rung exists to eliminate before TRD-01 begins.

What Comes Next

TRD-01 opens the device you verified here and writes the project’s first verbs code: enumerating adapters, opening a context, allocating a protection domain, and registering memory. It reads the attributes recorded in R7 rather than assuming them, and uses the build system from R8 to produce the first compiled target.

The two tools from R2 and R3 reappear as source rather than as instruments — rc_pingpong.c is the direct skeleton for TRD-02 and TRD-03, and rping.c is the structural model for TRD-05.
