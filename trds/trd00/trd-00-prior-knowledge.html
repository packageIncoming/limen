TRD-00: Fabric Up

Prior Knowledge — Limen RDMA Transport Project
Depends on: None  |  Difficulty: Low  |  Setup: ~1 session  |  Requirements: 1–2 sessions

1   The Project

Limen is a small RDMA transport library and the benchmark harness that measures it. When it is finished it exposes a C++ interface for moving bytes directly between two machines' memory, and a measurement tool that reports how long that takes and how much bandwidth it sustains.

The distinguishing property of Remote Direct Memory Access is that the remote CPU is not involved. On an ordinary network, sending data means the sender copies a buffer into the kernel, the kernel hands it to a network card, the receiving card raises an interrupt, the receiving kernel copies the data into a socket buffer, and eventually a process calls read() and copies it once more into user memory. Every one of those steps costs cycles and cache. RDMA removes almost all of them: the network adapter reads directly out of one machine's user memory and writes directly into another machine's user memory, with no kernel involvement on the data path and, for one-sided operations, no participation from the remote process at all.

That is the property Limen exists to expose and to measure. By the end of the ladder Limen can perform two-sided SEND/RECV transfers, one-sided RDMA_WRITE and RDMA_READ into and out of a peer's registered memory, and report calibrated latency and bandwidth numbers for each.

Figure 1 — The same byte, two paths. The left path crosses the kernel boundary four times and copies three. The right path crosses it zero times on the data path.

The name is Latin for threshold — the boundary between two spaces. That is what a transport is.

2   What You Will Learn

By the end of the ladder you will be able to:

  • Explain what an RDMA adapter does between the moment a work request is posted and the moment a completion appears, and name every structure involved.
  • Describe the difference between a two-sided and a one-sided operation, and explain why the one-sided case requires no CPU participation on the far side.
  • Register a memory region and explain what physically happens to those pages, why the registration can fail, and what the local and remote keys protect against.
  • Walk a queue pair through its full state machine and explain what each transition establishes and why the order cannot be changed.
  • Post send and receive work requests with scatter-gather lists, poll a completion queue, and correctly interpret every completion status you are likely to see.
  • Diagnose a receiver-not-ready condition and explain why it is a design problem rather than a transient error.
  • Write C++ RAII wrappers for resources with mandatory destruction ordering, including correct move semantics and a destructor that cannot throw.
  • Establish connections with the RDMA connection manager, drive its asynchronous event channel, and explain why its ownership model differs from every other resource in the API.
  • Perform RDMA_WRITE and RDMA_READ against a peer's memory, including the key exchange that makes it possible and the trust boundary that key represents.
  • Explain and apply the four principal completion-side optimizations — inline data, unsignaled completions, completion-queue moderation, and event-driven versus polled reaping — and say what each trades away.
  • Build a benchmark harness that produces defensible numbers: warm-up, repetition, percentile reporting rather than means, and validation against a reference implementation.
  • Read the verbs API's manual pages and the reference implementation's source without needing a tutorial in between.

4   Environment

Two Linux nodes that can reach each other directly at layer 2 — normally two virtual machines on a shared private network. Ubuntu 24.04 LTS is the reference; 22.04 works identically. Two virtual CPUs and 2 GB of memory per node is ample.

The complete configuration procedure — hypervisor adapters, addresses, packages, kernel modules, firewall, and creating the software RDMA device — is the Setup section of this TRD’s Requirements document, written as nine numbered steps with exact commands and a troubleshooting table. Work through it there.

Setup is deliberately not part of the requirements. Installing a package has one correct outcome and no judgment in it; it produces a working machine rather than knowledge. The requirements begin once the machine works.

If your host runs Windows, use real virtual machines. The Windows Subsystem for Linux kernel does not ship the software RDMA module, and discovering this after an hour of debugging is a poor use of an evening.

Toolchain: a C++20 compiler (GCC 12 or Clang 15 and later), CMake 3.16 or later, Git, the RDMA userspace stack, plus tcpdump and iperf3 for the observation and comparison requirements.

TRD-00 — Fabric Up

Builds: A verified two-node software RDMA fabric, a recorded performance baseline measured against a TCP control, a packet capture proving what the encapsulation is, and a repository skeleton whose build system locates the RDMA libraries.

Depends on: Nothing.

Unlocks: Everything. Until stock reference tools move bytes between the two nodes, no failure in TRD-01 can be attributed with confidence, because the environment is still a suspect.

Central idea: Verify the substrate with instruments you did not write, before writing anything that depends on it. This is the only rung with no code of your own in it, and it exists precisely so that every later rung's bugs are yours rather than the environment's.

TRD-01 — Context, Protection Domain, Memory Registration

Builds: A program that enumerates RDMA devices, opens a context on one, allocates a protection domain, registers a buffer, and prints the resulting keys and device limits.

Depends on: TRD-00's verified device and working build system.

Unlocks: Queue pairs, which cannot be created without a protection domain, and data transfer, which cannot address memory that has not been registered.

Central idea: Before an adapter can read your memory it must be told which memory, and the operating system must guarantee those pages will not move. Registration is where that bargain is struck, and it is why RDMA memory behaves unlike ordinary memory.

TRD-02 — Queue Pairs and the State Machine

Builds: A completion queue, a reliable-connected queue pair, and a hand-rolled exchange over TCP that carries the parameters each side needs to reach the other. The queue pair is driven from RESET through INIT and RTR to RTS.

Depends on: TRD-01's context, protection domain, and registered memory.

Unlocks: All data transfer. A queue pair in any state below RTS cannot send.

Central idea: A queue pair is a connection whose endpoint state you manage explicitly rather than delegating to the kernel. Each transition supplies information the adapter needs, and supplying it in the wrong order fails in ways whose error messages do not identify the cause. This is the hardest rung in the ladder.

TRD-03 — Two-Sided Transfer

Builds: A working ping-pong. Work requests posted with scatter-gather lists, receives posted in advance, completions polled and interpreted, and a loop that survives being run repeatedly.

Depends on: TRD-02's connected queue pair.

Unlocks: The RAII refactor, which needs enough distinct resource types to be worth doing, and one-sided operations, which reuse this posting machinery with different opcodes.

Central idea: Two-sided transfer requires the receiver to have posted a receive buffer before the sender's data arrives. Nothing in the API enforces this, and violating it produces a receiver-not-ready condition that reveals the deeper truth: RDMA gives you no flow control you did not build yourself.

TRD-04 — The RAII Layer

Builds: C++ wrapper types owning the context, protection domain, memory region, completion queue, and queue pair, with correct move semantics, deleted copies, non-throwing destructors, and enforced destruction order. Every earlier program is refactored onto them.

Depends on: TRD-03, which by now has accumulated enough manual cleanup to make the case for itself.

Unlocks: Every later rung, which would otherwise drown in cleanup paths.

Central idea: Verbs resources must be destroyed in the reverse of creation order, and destroying one out of turn either fails silently or corrupts the adapter's state. This is the textbook case for RAII, and building it here is what makes the rest of the ladder tractable.

TRD-05 — Connection Management

Builds: Connection establishment by IP address using the RDMA connection manager: an event channel, an identifier, an asynchronous event loop, and clean connect, accept, and disconnect paths. TRD-02's hand-rolled TCP exchange is deleted.

Depends on: TRD-04's ownership model, which is now extended to a resource that does not obey it.

Unlocks: Any program you would let another person run, since manual parameter exchange is not a usable interface.

Central idea: The connection manager hides the parameter exchange you built by hand, which is why you built it by hand first. Its identifier has different lifetime rules than every other resource in the API — a genuine test of whether the abstraction from TRD-04 generalizes or merely fit the first five cases.

TRD-06 — One-Sided Operations

Builds: RDMA_WRITE and RDMA_READ against a peer's registered memory, with the remote address and key exchanged during connection setup.

Depends on: TRD-05's connection setup, which is where the keys are exchanged.

Unlocks: The optimizations in TRD-07, whose effects are clearest on one-sided operations, and the measurements in TRD-08 that make the point of the project.

Central idea: This is the operation the technology exists for. The remote CPU is not merely idle during the transfer — it is not informed that it happened. Understanding what the remote key permits, and what it therefore risks, is understanding RDMA's actual trust model.

TRD-07 — Completion Efficiency

Builds: Inline data for small payloads, unsignaled completions with periodic signalling, completion-queue moderation, and a selectable polled or event-driven reaping mode.

Depends on: TRD-06, since there is nothing to optimize until transfers work.

Unlocks: Measurements worth taking. Without these, TRD-08 reports the cost of a naive implementation rather than the cost of the transport.

Central idea: Every one of these trades something. Inline copies to save a memory reference. Unsignaled saves completion processing at the cost of knowing when a buffer is reusable. Event-driven trades latency for CPU. Naming the trade is the skill; applying the technique is mechanical.

TRD-08 — Benchmark Harness

Builds: A measurement tool reporting latency percentiles and sustained bandwidth across a payload sweep, with warm-up, repetition, and validation against the reference implementation.

Depends on: All prior rungs.

Unlocks: Nothing — this is the final rung. It converts the library into a result.

Central idea: A number without a methodology is not a measurement. Reporting a mean latency hides the tail that actually matters, and a benchmark that has not been validated against a known-good implementation measures your harness rather than your transport.

Tools, and the boundary

RDMA failures are unusually opaque. A misconfigured queue pair does not report a useful error code; it reports a completion status you must look up, or it hangs. The tools that resolve this are ibv_devinfo for adapter state, strace for the syscall sequence, tcpdump or wireshark for what actually left the machine, gdb for crashes, and valgrind for the leaks that RDMA's manual resource management invites. Reading the reference implementations in the rdma-core source tree resolves more questions than any other single habit.[2]

Reach for those before reaching for a chat window. An AI assistant is appropriate for reviewing code once it works, clarifying a concept this document left unclear, and grading comprehension answers. It is not appropriate for writing or debugging the implementation — that is the part that constitutes the learning, and delegating it produces a repository you cannot defend.

7   What RDMA Actually Is

Ordinary networking is built on the assumption that the CPU mediates every transfer. The kernel owns the network device, applications ask the kernel to move data, and the data is copied at each boundary because no layer trusts another layer's memory. That assumption is correct for a general-purpose operating system on a hostile network, and it costs microseconds and cache lines on every message.

RDMA discards the assumption. Three properties follow, and together they define the technology:

Kernel bypass

After a connection is established, data transfer does not enter the kernel. The application writes a work request into a queue that the adapter reads directly, and the adapter writes completions into a queue that the application reads directly. Both queues live in memory mapped into the process. There is no system call on the data path. The kernel is still involved in setup — opening the device, registering memory, creating queues — but once those are done it steps aside.

Zero copy

The adapter transfers directly out of and into application buffers. There is no intermediate socket buffer, because the adapter has been told where the application's memory physically resides and is permitted to reach it by direct memory access. This is why memory must be registered before use: the adapter needs a physical address, and the operating system must promise that address will remain valid.

Remote CPU bypass

This is the property with no analogue in sockets. In a one-sided operation the initiating adapter carries both the data and the destination address. The remote adapter writes the data into the remote machine's memory and generates no completion, no interrupt, and no notification. The remote process is not merely uninvolved; it does not know the transfer occurred. Discovering that it happened requires the application to build its own signalling on top.

The contrast with two-sided operations matters throughout the ladder:

The verbs API

The programming interface is called verbs. It is not a socket API with different function names; the model is different in kind. You do not call a function that sends. You construct a work request describing a transfer, post it to a queue, and later reap a completion telling you the transfer finished. Posting and completion are separate events, potentially far apart in time, and everything about the API's shape follows from that asynchrony.

The principal objects, all built across TRD-01 through TRD-03:

ObjectWhat it is
Device contextAn open handle to one adapter. Everything else is created from it.
Protection domainAn isolation boundary. Memory regions and queue pairs in different domains cannot address each other, which is what stops one connection from reading another's memory.
Memory regionA registered buffer. Registration yields a local key and, if remote access is granted, a remote key.
Completion queueWhere the adapter deposits notice that a work request finished, successfully or otherwise.
Queue pairA send queue and a receive queue together. This is the connection endpoint — the closest analogue to a socket, though the analogy breaks quickly.
Work requestOne unit of work: an opcode, one or more buffer descriptors, and for one-sided operations a remote address and key.
CompletionOne finished work request: an identifier, a status, and a byte count.

8   RoCE: RDMA Over Ethernet

RDMA was specified for InfiniBand, a purpose-built fabric with its own physical layer, switches, and addressing. RDMA over Converged Ethernet carries the same transport over ordinary Ethernet, which is what makes it reachable without specialized hardware.[1]

Two versions exist. RoCEv1 encapsulates the InfiniBand transport directly in an Ethernet frame with its own EtherType, which confines it to a single layer-2 broadcast domain — it cannot be routed. RoCEv2 encapsulates the same transport inside UDP inside IP, making it routable across ordinary networks. RoCEv2 is what Limen uses and what essentially all current deployments use.[1]

+----------------+-------------+---------------+-------------------+-------+
| Ethernet hdr   |   IP hdr    | UDP hdr       | InfiniBand        | ICRC  |
|                |             | dst port 4791 | transport headers |       |
+----------------+-------------+---------------+-------------------+-------+
                                                | + payload        |
                                                +------------------+

The destination UDP port is 4791, registered with IANA for this purpose.[3] Three consequences follow immediately and all of them will bite you:

  • A firewall that does not permit UDP 4791 breaks everything, and does so by timing out rather than by reporting an error.
  • Packet capture works. RoCEv2 traffic is visible to tcpdump and decodable by Wireshark, which makes it far more debuggable than InfiniBand.
  • UDP is unreliable, yet reliable-connected queue pairs guarantee ordered, reliable delivery. The reliability is implemented in the InfiniBand transport headers inside the UDP payload — acknowledgements, sequence numbers, and retransmission — not by UDP. UDP is used purely as an encapsulation with routable addressing and a port number for demultiplexing.[1]

Addressing and GIDs

InfiniBand addresses endpoints by Global Identifier, a 128-bit value. In RoCEv2 the GID is derived from the interface's IP address: an IPv4 address appears as an IPv4-mapped IPv6 address in the GID table. A single port therefore has several GID table entries — typically a RoCEv1 entry and a RoCEv2 entry for each address family — and the raw verbs API requires you to say which index you mean.[6]

This is why the reference tool ibv_rc_pingpong takes a -g argument and why the wrong value produces a connection that fails without explaining itself. The connection manager introduced in TRD-05 selects the index for you, which is one of the reasons to prefer it once you understand what it is hiding.

Lossless fabrics

Production RoCEv2 deployments configure the Ethernet fabric to be lossless, using Priority Flow Control and Explicit Congestion Notification, because the InfiniBand transport's retransmission behaves poorly under loss. This matters greatly in a data centre and not at all here: on a direct link or a virtual bridge there is no congestion to manage. It is worth knowing that the requirement exists, because it is the first thing a practitioner will ask about.

9   Soft-RoCE: What rxe Is And Is Not

The Linux kernel includes a software implementation of RoCEv2 called rdma_rxe, usually shortened to Soft-RoCE or simply rxe. It presents a fully functional RDMA device that any verbs program can open, and implements the transport in software over an ordinary Ethernet interface.[4][5]

It has been in the mainline kernel since 4.8, which matters because most material found by searching predates that and describes an out-of-tree package configured with a tool called rxe_cfg. That method is obsolete. The current interface is the rdma link management command.[5][7] If a guide mentions rxe_cfg, the rest of that guide is also stale.

What transfers to hardware

Every line of verbs code you write against rxe compiles and runs unchanged against a hardware adapter. The device name changes and nothing else. The API surface is identical because rxe implements the same specification.

What does not transfer is performance, and the reason is structural. Soft-RoCE's "adapter" is the kernel. A posted work request is processed by kernel threads, encapsulated in software, and handed to the ordinary network stack for transmission. Consequently:

PropertyHardware adapterSoft-RoCE
Kernel bypass on data pathRealNone — the kernel is the implementation
Zero copyReal DMA from user pagesSoftware copies through the network stack
Round-trip latencyRoughly 1–3 microsecondsTens of microseconds
BandwidthLine rateCPU-bound, typically a small fraction
CPU cost per transferNear zero after postingSubstantial on both sides
Memory registrationPins pages, maps them for device DMA, consumes locked memoryPins pages and accounts locked memory identically, through the same kernel path; no DMA mapping, because there is no device
Verbs API and semanticsIdentical
Expect ordinary TCP to be faster

Because soft-RoCE runs the entire InfiniBand transport in software and then hands the result to the same kernel network stack that TCP uses, it performs strictly more work over the same wire. Measured against iperf3 on the same link, it usually loses — often decisively.

That is not a defect and it is not an argument against RDMA. It is the cleanest available demonstration of what the hardware contributes: remove the adapter and you retain every byte of protocol cost and none of the benefit. R6 makes you measure this rather than take it on faith.

Two implications shape the whole ladder. First, every concept, every state transition, every failure mode, and every line of code in TRD-01 through TRD-07 is fully learnable on rxe. Second, no performance number produced on rxe means anything about RDMA — it measures the kernel's software implementation. TRD-08 is explicit about this, and the baseline you record in this TRD exists so that a future comparison against real hardware has a control.

10   The Software Stack

The userspace side is one project, rdma-core, which most distributions split into several packages.[2]

ComponentProvides
libibverbsThe verbs API itself. Everything in TRD-01 through TRD-04 and TRD-06 through TRD-08 is this library.
librdmacmThe connection manager: connection setup by IP address, an event channel, and address resolution. TRD-05.
Provider driversPer-device userspace drivers loaded automatically. rxe and each hardware vendor have one. You never call into these directly.
ibverbs-utilsDiagnostic programs: ibv_devices, ibv_devinfo, ibv_rc_pingpong.

perftestThe standard RDMA benchmark suite: ib_send_bw, ib_send_lat, ib_write_bw, ib_read_lat. TRD-08 validates against these.[8]

On the kernel side, ib_core provides the RDMA subsystem, rdma_rxe the software provider, rdma_ucm the connection manager's userspace interface, and ib_uverbs the verbs userspace interface. The last two are loaded on demand; if rping fails while ibv_rc_pingpong succeeds, a missing rdma_ucm is the first thing to check.

Device state is visible in sysfs under /sys/class/infiniband/, including the GID table at /sys/class/infiniband/<dev>/ports/1/gids/. Reading these files directly is often faster than finding the tool that prints them.

11   The Verification Tools

This TRD is built entirely out of these four. Each answers a different question, and the order is deliberate: each one that passes eliminates a class of cause for the next one's failure.

ibv_devinfo

Prints adapter attributes and port state. Answers: does a device exist and is its port up? Three fields decide whether anything else can work — the port state must read PORT_ACTIVE, the link layer must read Ethernet, and the transport will read InfiniBand, which is correct and not a contradiction: RoCE is the InfiniBand transport carried over Ethernet.

The same output reports device limits — maximum queue pairs, maximum work requests per queue, maximum scatter-gather entries per request, and the active maximum transfer unit. These are not the same on rxe as on hardware, which is why TRD-01 requires you to query them rather than assume them.

ibv_rc_pingpong

A minimal reliable-connected ping-pong using raw verbs. It exchanges queue-pair parameters over a side TCP channel, transitions both queue pairs by hand, and moves data. Answers: can two nodes complete a raw verbs transfer?

Its source is the single most valuable file you will read in this project. It is the skeleton of TRD-02 and TRD-03, written by the people who wrote the library, in under a thousand lines.[2]

rping

The same idea via the connection manager: connect by IP address, no hand-rolled exchange. Answers: does the connection-manager path work? A failure here with ibv_rc_pingpong succeeding isolates the fault to rdma_ucm or the CM's addressing.

This is the structural model for TRD-05 and beyond.

perftest

ib_send_bw and ib_send_lat produce bandwidth and latency figures. Answers: how fast is this fabric, measured by an implementation known to be correct? These are the reference numbers TRD-08 validates against, and the baseline recorded here.[8]

12   Failure Modes

Nearly every failure in this TRD is one of the following. Consult before searching.

SymptomCauseResolution
Nodes cannot reach each other at all Network address translation. A translated guest cannot accept an inbound connection. Change the adapter to bridged or host-only.
modprobe reports the module is not found The distribution's base kernel image omits rdma_rxe. Install the extra modules package matching the running kernel exactly.
Every transfer times out with no error text A firewall is dropping UDP 4791. Permit 4791/udp, or disable the firewall on a lab machine.
ibv_devinfo reports PORT_DOWN The underlying interface is down, or the rxe link was attached to the wrong interface — commonly the translated one rather than the bridged one. Confirm the interface is up and carries the expected address, then remove and recreate the link.
The device disappears after reboot Expected. rxe links are not persistent. Recreate it, or arrange for the command to run at boot.

rping fails, ibv_rc_pingpong succeeds rdma_ucm is not loaded. Load it, and add it to the boot-time module list.

13   What Is Deliberately Left Out

This TRD verifies an environment. It contains no verbs code, and that is intentional — its entire value is that when TRD-01 fails, the fabric is already eliminated as a suspect.

Also absent by design across the early ladder: this fabric is not lossless, has no congestion control, and is not tuned. None of that matters on a virtual bridge with two nodes, and all of it matters in a data centre. Memory registration on rxe does not pin pages the way hardware does, so the locked-memory limits that cause hardware registration to fail will not appear until TRD-01 discusses them. Connection setup here is performed by reference tools; you build it by hand in TRD-02 and replace that with the connection manager in TRD-05.

The baseline recorded in this TRD is the control for a comparison that has not happened yet — and the TCP figure beside it is the control for the baseline itself. If the project is later moved to hardware, this file is what makes the difference measurable. Capturing it costs ten minutes now and cannot be reconstructed later.
