TRD-04: The RAII Layer

Requirements — Limen RDMA Transport Project
Depends on: TRD-03  |  Difficulty: Medium  |  Estimated: 3–5 sessions

Objective

Build limen:: wrapper types owning the device context, protection domain, memory region, completion queue, and queue pair. Each is move-only, releases in a non-throwing destructor, and exposes an explicit release returning the underlying status. Assemble them into a type whose member declaration order produces the required destruction order. Then refactor all three existing programs onto the layer and confirm every earlier gate still passes.

What This Is Not

No new RDMA. Not one new verb, not one new fabric concept. If you find yourself learning something about queue pairs during this rung, you have wandered.

No new behaviour in the three programs. Their output must be identical and their test suites must pass unmodified. A refactor that changes what the programs do is not a refactor and cannot be verified.

No reference counting, no thread safety, no virtual destructors, no allocator customisation. These are concrete, single-owner, non-polymorphic types.

No solution to transfer-time buffer ownership. Section 9 of the Prior Knowledge document explains why that hazard is a different problem; it survives this rung and is addressed in TRD-07.

Interface

Headers under include/limen/. Namespace limen. The suite compiles against these declarations, so the names and signatures are part of the contract.

namespace limen {

class VerbsError : public std::runtime_error {
public:
    VerbsError(const char *op, int err);
    int error() const noexcept;
};

class Context {
public:
    Context() noexcept = default;
    explicit Context(const char *device_name);        /* throws VerbsError */
    ~Context() noexcept;
    Context(const Context&)            = delete;
    Context& operator=(const Context&) = delete;
    Context(Context&&) noexcept;
    Context& operator=(Context&&) noexcept;

    ibv_context *get()   const noexcept;              /* nullptr when empty */
    explicit operator bool() const noexcept;
    int close() noexcept;                             /* idempotent */
};

class ProtectionDomain { /* same shape; ibv_pd *get() */ };
class CompletionQueue  { /* same shape; ibv_cq *get() */ };
class QueuePair        { /* same shape; ibv_qp *get() */ };

class MemoryRegion {
public:
    MemoryRegion() noexcept = default;
    MemoryRegion(ProtectionDomain& pd, std::size_t bytes, int access);
    /* ... five special members as above ... */
    ibv_mr     *get()    const noexcept;
    void       *data()   const noexcept;              /* the owned buffer */
    std::size_t size()   const noexcept;
    std::uint32_t lkey() const noexcept;
    std::uint32_t rkey() const noexcept;
};

} /* namespace limen */

Technical Requirements

R1 — The Ownership Contract

Every wrapper type satisfies all of the following, verifiable at compile time:

static_assert(!std::is_copy_constructible_v<T>);
static_assert(!std::is_copy_assignable_v<T>);
static_assert(std::is_nothrow_move_constructible_v<T>);
static_assert(std::is_nothrow_move_assignable_v<T>);
static_assert(std::is_nothrow_destructible_v<T>);
static_assert(std::is_nothrow_default_constructible_v<T>);

Place these assertions in tests/static_contract.cpp, instantiated for all five types. That file compiling is the verification; no runtime check is needed or sufficient.

Whether you write five hand-rolled classes or one template instantiated five times is your decision. Both satisfy this requirement and the comprehension questions ask you to defend the choice.

Stuck? → Hints H1

R2 — Context

Acquires by device name: enumerate, match, open, and free the device list. Throws VerbsError if the device is absent or the open fails.

Releases with ibv_close_device, whose convention is 0 or -1 — normalise it so close() returns 0 on success and a non-zero value otherwise, matching every other wrapper.

Stuck? → Hints H2

R3 — ProtectionDomain

Constructed from a Context. Releases with ibv_dealloc_pd, which returns 0 or an errno value.

An EBUSY from this release means a child outlived it. R8 requires that to be reported rather than swallowed, because it is the signal that the layer has a hole.

Stuck? → Hints H3

R4 — MemoryRegion

Allocates a buffer of the requested size, registers it with the given access flags, and owns both. Releases by deregistering first, then freeing the buffer — an ordering that must be internal and unreachable from outside the type.

Exposes data(), size(), lkey(), and rkey(). On an empty or moved-from region these return null, zero, and zero respectively rather than dereferencing.

Zero the buffer on construction. TRD-03 relied on that and the behaviour must not change.

Stuck? → Hints H4

R5 — CompletionQueue and QueuePair

The completion queue is constructed from a Context with a requested capacity; expose the granted cqe, which may exceed the request.

The queue pair is constructed from a ProtectionDomain and an ibv_qp_init_attr; expose qp_num and the granted capabilities the call wrote back. Both must survive being moved without the queue pair losing its reference to the completion queue.

The queue pair holds a raw ibv_cq * inside the provider, so the completion queue must outlive it. This wrapper cannot enforce that on its own; R7 is where it becomes structural.
Stuck? → Hints H5

R6 — Move Semantics

Move construction takes the source's handle and leaves the source empty. Move assignment releases the destination's existing resource before adopting, and is a no-op on self-assignment.

A moved-from object must be destructible, and its accessors must return the empty values from R4 rather than dereferencing. Moved-from is a valid state of the type.

Copy construction and copy assignment are deleted, not merely private or unimplemented — the suite compiles a program that attempts a copy and requires the compilation to fail.

Stuck? → Hints H6

R7 — Destruction Order by Declaration

Provide limen::Endpoint holding all five wrappers as members, declared in creation order so that reverse-declaration-order destruction yields queue pair, completion queue, memory region, protection domain, context.[1]

Endpoint declares no destructor. Its implicit destructor is correct, and writing one would be a place for the order to be got wrong.

Build with a diagnostic mode — a compile-time flag or an environment variable — under which each wrapper prints its type name as it releases. The suite runs an Endpoint under that mode and checks the order.

Stuck? → Hints H7

R8 — Non-Throwing Release With a Reportable Status

Every destructor is noexcept and never throws under any circumstance.[2] Every type also exposes close() returning the underlying status, callable explicitly by anyone who wants to check, and idempotent — a second call is a no-op returning 0.

The destructor calls close() and, on a non-zero result, writes a diagnostic to stderr naming the verb and the symbolic errno. It does not throw, does not abort, and does not silently discard.

Do not reach for uncaught_exceptions

The technique of inspecting std::uncaught_exceptions() to throw only when it is "safe" is explicitly rejected: circumventing normal destructor processing this way can leave the destructor failing to release the resource at all.[2] Report and continue.

Stuck? → Hints H8

R9 — Constructors Throw, Callers Do Not Clean Up

A constructor that cannot produce a valid object throws VerbsError carrying the operation name and the errno value. There are no half-constructed wrappers and no two-phase initialisation.

Correspondingly, calling code contains no cleanup for wrapper-owned resources on any path. Any wrapper already constructed when a later one throws is destroyed by unwinding.

Stuck? → Hints H9

R10 — Refactor All Three Programs

limen_devinfo, limen_connect, and limen_pingpong are ported onto the layer. Every goto cleanup block, every manual destroy call, and every conditional teardown is removed from them.

Observable behaviour is unchanged: identical output lines, identical exit codes. The TRD-01, TRD-02, and TRD-03 test suites must pass unmodified. The suite for this rung runs all three.

Half-refactored is worse than either state. A surviving goto cleanup block alongside a throwing constructor is a leak on the exception path that neither the old code nor the new code would have had. Port each program completely or not at all.

The teardown: line each program prints must survive. Its stages are now reported by close() called explicitly before the wrappers go out of scope, which is exactly the case that explicit release exists for.

Stuck? → Hints H10

R11 — No Raw Handles Outside the Layer

After R10, the only translation units that name ibv_destroy_qp, ibv_destroy_cq, ibv_dereg_mr, ibv_dealloc_pd, or ibv_close_device are the wrapper implementations themselves. The suite greps for this.

Programs may still call get() to pass a raw handle to a verb that needs one — posting and polling both require it, and hiding those behind further abstraction is TRD-07's business, not this rung's. What must not survive is any release call outside the layer.

Leak checks: valgrind --leak-check=full reports zero bytes definitely lost for all three refactored programs, on their success paths and on at least one failure path each.

Stuck? → Hints H11

What Comes Next

TRD-05 replaces the hand-rolled TCP parameter exchange with the RDMA connection manager. Its identifier does not obey the ownership model you just built — it is created through an event channel, can be destroyed by events rather than by you, and has a lifetime relationship to the channel that is not simple containment. That is the real test of whether this layer generalises or merely fitted the five cases in front of it.

Expect to change something here. A design that survives the sixth resource unmodified was either unusually good or not yet under pressure.
