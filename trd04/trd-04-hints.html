TRD-04: The RAII Layer

Hints — Limen RDMA Transport Project
Level 1 = nudge  |  Level 2 = stronger push  |  Try Level 1 for 15+ minutes before escalating

Level 1 points at the right place. Level 2 names the mechanism.

The failure character here is different again. TRD-02 failed at one call with one uninformative error; TRD-03 failed by hanging. This rung mostly fails silently — a wrapper that copies instead of moving compiles cleanly, runs correctly on the happy path, and double-frees on exit. The defence is compile-time: R1's static assertions and R6's compile-fail test catch these before anything runs, which is why the suite is mostly compilation rather than execution. Write those first.

H1 — The Ownership Contract (R1)

Level 1

Start by writing the assertion file, before any wrapper exists. It will not compile, and the errors are your specification — each one names a property you have not yet provided.

Then write one wrapper completely and get it passing. The protection domain is the right first choice: no arguments to speak of, one handle, one release call. Do not start with the memory region, which owns two things, or the context, which enumerates.

On the template question: write the first one by hand. You cannot design a good abstraction over a shape you have not yet written once, and after two or three you will know whether the shapes are actually the same. They are less identical than they look — the release conventions differ, and one wrapper owns an extra resource.

Level 2
/* tests/static_contract.cpp */
#include <limen/verbs.hpp>
#include <type_traits>

template <typename T>
constexpr void check() {
    static_assert(!std::is_copy_constructible_v<T>,        "must not be copyable");
    static_assert(!std::is_copy_assignable_v<T>,           "must not be copy-assignable");
    static_assert(std::is_nothrow_move_constructible_v<T>, "move ctor must be noexcept");
    static_assert(std::is_nothrow_move_assignable_v<T>,    "move assign must be noexcept");
    static_assert(std::is_nothrow_destructible_v<T>,       "dtor must be noexcept");
    static_assert(std::is_nothrow_default_constructible_v<T>, "empty state must exist");
}

int main() {
    check<limen::Context>();
    check<limen::ProtectionDomain>();
    check<limen::MemoryRegion>();
    check<limen::CompletionQueue>();
    check<limen::QueuePair>();
}

If is_nothrow_move_constructible_v fails while you believe you wrote a move constructor, the usual cause is that you declared a destructor and did not declare the moves — the implicit ones were suppressed, and what you are testing is the deleted copy.[4]

H2 — Context (R2)

Level 1

The body is TRD-01's R2 and R3 moved into a constructor. The list must be freed on every path out, including the throwing ones — which is exactly the kind of thing this layer exists to stop you hand-writing, so consider whether a tiny local guard type is worth it for the list, or whether the function is short enough to be obviously correct.

The release convention here is the odd one out: it returns -1 rather than an errno value. Normalise it, so that callers of close() never have to know which of the three conventions a given wrapper wraps. That normalisation is a quiet benefit of this layer worth noticing.

Level 2
Context::Context(const char *name) {
    int n = 0;
    ibv_device **list = ibv_get_device_list(&n);
    if (!list) throw VerbsError("ibv_get_device_list", errno);

    ibv_device *dev = nullptr;
    for (int i = 0; i < n; ++i)
        if (std::strcmp(ibv_get_device_name(list[i]), name) == 0) { dev = list[i]; break; }

    if (!dev) { ibv_free_device_list(list); throw VerbsError("device not found", ENODEV); }

    ctx_ = ibv_open_device(dev);
    int saved = errno;
    ibv_free_device_list(list);                    /* before the throw, on both paths */
    if (!ctx_) throw VerbsError("ibv_open_device", saved);
}

int Context::close() noexcept {
    if (!ctx_) return 0;                           /* idempotent */
    int rc = ibv_close_device(ctx_) ? EIO : 0;     /* -1 convention normalised */
    ctx_ = nullptr;
    return rc;
}

Save errno before ibv_free_device_list. Any intervening call may overwrite it, and reporting the wrong cause is worse than reporting none.

H3 — ProtectionDomain (R3)

Level 1

The simplest of the five and the one to get completely right before writing any others — every remaining wrapper is this shape with a different acquire and release call.

Once it passes the assertions, copy it four times and change the two calls. Then decide whether the duplication bothers you enough to template it. Deciding after you can see all five is the point; deciding before is guessing.

Level 2
ProtectionDomain::ProtectionDomain(Context &ctx) {
    pd_ = ibv_alloc_pd(ctx.get());
    if (!pd_) throw VerbsError("ibv_alloc_pd", errno);
}

ProtectionDomain::ProtectionDomain(ProtectionDomain &&o) noexcept
    : pd_(std::exchange(o.pd_, nullptr)) {}

ProtectionDomain &ProtectionDomain::operator=(ProtectionDomain &&o) noexcept {
    if (this != &o) { close(); pd_ = std::exchange(o.pd_, nullptr); }
    return *this;
}

int ProtectionDomain::close() noexcept {
    if (!pd_) return 0;
    int rc = ibv_dealloc_pd(pd_);                  /* 0 or an errno value */
    pd_ = nullptr;                                 /* clear regardless    */
    return rc;
}

ProtectionDomain::~ProtectionDomain() noexcept {
    if (int e = close(); e != 0)
        report_release_failure("ibv_dealloc_pd", e);
}

Clear the handle even when the release reports failure. Retaining it invites a second attempt on the next destruction, and there is nothing useful to retry.

H4 — MemoryRegion (R4)

Level 1

Two resources, one object, and a mandatory order between them: deregister before freeing. Getting that backwards hands the adapter a pointer into freed memory, which is the exact hazard making this a single type rather than two is meant to eliminate.

Moving must transfer both. A move that takes the registration and leaves the buffer behind produces a source that frees memory the destination is still registered against — a bug that will not appear until something is moved, which may be much later.

The accessors need to work on an empty region. Every one of them dereferences a handle in the obvious implementation, so each needs a guard.

Level 2
class MemoryRegion {
    ibv_mr     *mr_   = nullptr;
    void       *buf_  = nullptr;
    std::size_t size_ = 0;
};

MemoryRegion::MemoryRegion(ProtectionDomain &pd, std::size_t bytes, int access) {
    buf_ = std::aligned_alloc(4096, (bytes + 4095) & ~std::size_t{4095});
    if (!buf_) throw VerbsError("aligned_alloc", ENOMEM);
    std::memset(buf_, 0, bytes);

    mr_ = ibv_reg_mr(pd.get(), buf_, bytes, access);
    if (!mr_) { int e = errno; std::free(buf_); buf_ = nullptr;
                throw VerbsError("ibv_reg_mr", e); }
    size_ = bytes;
}

int MemoryRegion::close() noexcept {
    int rc = 0;
    if (mr_)  { rc = ibv_dereg_mr(mr_); mr_ = nullptr; }   /* deregister FIRST */
    if (buf_) { std::free(buf_); buf_ = nullptr; }         /* then free        */
    size_ = 0;
    return rc;
}

std::uint32_t MemoryRegion::lkey() const noexcept { return mr_ ? mr_->lkey : 0; }
std::uint32_t MemoryRegion::rkey() const noexcept { return mr_ ? mr_->rkey : 0; }
void         *MemoryRegion::data() const noexcept { return buf_; }
std::size_t   MemoryRegion::size() const noexcept { return size_; }

The constructor's failure path frees the buffer by hand, because the object does not exist yet and its destructor will not run. That is the one place in this layer where manual cleanup is correct and unavoidable — a constructor that throws leaves nothing behind for the language to clean up.

std::aligned_alloc requires the size to be a multiple of the alignment, hence the rounding. It pairs with plain std::free.

H5 — CompletionQueue and QueuePair (R5)

Level 1

Same shape again. The only new work is capturing what the provider granted, which for the completion queue is a field on the created object and for the queue pair is written back into the structure you passed.

Store the granted values as members at construction. Reading them back later through get() works for the completion queue and does not for the queue pair, since the structure you passed was a local that is gone.

The warning in R5 is worth sitting with for a moment: the queue pair holds a reference to the completion queue that neither wrapper knows about. Think about where that could be made structural, then read R7.

Level 2
CompletionQueue::CompletionQueue(Context &ctx, int want) {
    cq_ = ibv_create_cq(ctx.get(), want, nullptr, nullptr, 0);
    if (!cq_) throw VerbsError("ibv_create_cq", errno);
    requested_ = want;
    granted_   = cq_->cqe;                 /* may exceed the request */
}

QueuePair::QueuePair(ProtectionDomain &pd, ibv_qp_init_attr &init) {
    qp_ = ibv_create_qp(pd.get(), &init);
    if (!qp_) throw VerbsError("ibv_create_qp", errno);
    qp_num_ = qp_->qp_num;
    cap_    = init.cap;                    /* written back by the call */
}

Take the init structure by non-const reference precisely because the call modifies it — a const reference would not compile, and a by-value parameter would discard the granted capabilities. The signature documents the behaviour.

H6 — Move Semantics (R6)

Level 1

Three obligations for a correct move, listed in section 5 of the Prior Knowledge document. Most people get the first two and miss the third, and the third only fails when you assign over a live object — which the test suite does deliberately.

For the compile-fail test: a test that requires compilation to fail is unusual and worth thinking about before writing. The file must be excluded from the normal build, or the project will not compile at all.

The self-assignment guard looks like paranoia and is not. Without it, a = std::move(a) releases the resource and then adopts the null you just left behind, silently destroying the object.

Level 2
/* tests/copy_must_not_compile.cpp — NOT in the default build */
#include <limen/verbs.hpp>
int main() {
    limen::ProtectionDomain a;
    limen::ProtectionDomain b = a;      /* must be rejected: copy ctor deleted */
    (void)b;
}

Exclude it with EXCLUDE_FROM_ALL so the suite can invoke the compiler on it directly and require a non-zero exit:

add_executable(copy_must_not_compile EXCLUDE_FROM_ALL tests/copy_must_not_compile.cpp)

For the move-assign test, instrument the release path in diagnostic mode and count the reports. Assigning a live object over another live object must produce exactly one release at the assignment and one at scope exit — two in total, not three and not one.

H7 — Destruction Order by Declaration (R7)

Level 1

This requirement is mostly a matter of writing five member declarations in the right sequence and then not writing a destructor. The temptation to add one and release things explicitly is exactly the mistake — a hand-written destructor is a place the order can be wrong, and the implicit one cannot be.

The diagnostic mode needs each wrapper to know its own name. A string passed to the reporting function is the least clever option and the one that will not surprise you later.

Think about construction. Members are initialised in declaration order, and each one needs the previous — so the constructor's initialiser list has a natural shape that mirrors the declarations. If you find yourself wanting to initialise them out of order, the declaration order is wrong.

Level 2
class Endpoint {
public:
    Endpoint(const char *dev, std::size_t bytes, int access,
             int cq_depth, ibv_qp_init_attr &init)
        : ctx_(dev)
        , pd_(ctx_)
        , mr_(pd_, bytes, access)
        , cq_(ctx_, cq_depth)
        , qp_(pd_, (init.send_cq = init.recv_cq = cq_.get(), init))
    {}
    /* No destructor. The implicit one is correct. */

    Context          &context() noexcept { return ctx_; }
    /* ... accessors ... */

private:
    Context          ctx_;   /* destroyed 5th */
    ProtectionDomain pd_;    /* destroyed 4th */
    MemoryRegion     mr_;    /* destroyed 3rd */
    CompletionQueue  cq_;    /* destroyed 2nd */
    QueuePair        qp_;    /* destroyed 1st */
};

Members are initialised in declaration order regardless of the order they appear in the initialiser list, so writing the list in the same order keeps the two aligned and avoids a warning. Compile with -Wreorder — enabled by -Wall — and the compiler will tell you if they diverge.

For the diagnostic mode:

void limen::report_release(const char *what) noexcept {
    if (std::getenv("LIMEN_TRACE_RELEASE"))
        std::fprintf(stderr, "release: %s\n", what);
}

Call it from each close(). Running an Endpoint with that variable set produces the five lines the suite checks, in order.

H8 — Non-Throwing Release (R8)

Level 1

The design is in section 6 of the Prior Knowledge document and it is short: an explicit release that returns the status, and a destructor that calls it and reports. The work is in making close() genuinely idempotent, which means it must be safe to call from the destructor after a caller has already called it.

The pattern that makes idempotence fall out is clearing the handle inside close() and returning early when it is already null. Every wrapper then gets the property for free.

Resist any design where the destructor decides whether it is safe to throw. Section 6 explains why that particular cleverness is rejected by name.

Level 2
void limen::report_release_failure(const char *op, int err) noexcept {
    std::fprintf(stderr, "limen: %s failed during release: %s (%d)\n",
                 op, std::strerror(err), err);
}

Every destructor is the same three lines:

~QueuePair() noexcept {
    if (int e = close(); e != 0) report_release_failure("ibv_destroy_qp", e);
}

Mark close() and the reporting function noexcept explicitly. The destructor is implicitly noexcept[2] but a function it calls is not, and a throw escaping through the destructor terminates the program just the same.

To confirm the assertion in static_contract.cpp is testing what you think, temporarily add a throw to one destructor and check that the file fails to compile. Then remove it.

H9 — Constructors Throw (R9)

Level 1

One exception type carrying an operation name and an errno value is enough; resist a hierarchy.

The interesting part is what happens in Endpoint's constructor when the fourth member throws. Three members are fully constructed and one is not. Work out what the language does, and confirm you believe it before writing the test — the answer is what makes R9 true and it is worth deriving rather than being told.

Note the one place manual cleanup is still correct: inside a constructor, before the object exists. H4's memory region shows it.

Level 2
VerbsError::VerbsError(const char *op, int err)
    : std::runtime_error(std::string(op) + ": " + std::strerror(err))
    , err_(err) {}

When a member's constructor throws, the members already fully constructed are destroyed in reverse order, and the object under construction never existed, so its destructor does not run. That is exactly the behaviour R9 wants: a failure at the completion queue leaves the region, domain, and context released correctly with no code written to do it.

Test it by pointing at a device that exists and requesting a completion queue larger than max_cqe:

try {
    limen::Endpoint ep("rxe0", 4096, acc, 1 << 30, init);   /* cq too large */
} catch (const limen::VerbsError &e) {
    /* three members were constructed and released; valgrind must be clean */
}

H10 — Refactor All Three Programs (R10)

Level 1

Do them one at a time, smallest first, and run that program's own suite after each. Refactoring all three before testing any produces a failure you cannot localise.

The method that works: delete the cleanup block first, then fix every compile error it causes. Deleting it forces the issue and stops you from leaving half of it behind, which R10's warning identifies as the worst outcome.

The teardown: line is the one thing that needs thought. It reports per-stage status, and destructors run after your last statement — so you need the status before scope exit. Section 6 of the Prior Knowledge document explains what explicit release is for, and this is the case.

Level 2

Call close() explicitly in the order the line reports, then let the destructors run as no-ops:

int e;
const char *qp_s  = (e = ep.qp().close())  ? errno_name(e) : "ok";
const char *cq_s  = (e = ep.cq().close())  ? errno_name(e) : "ok";
const char *mr_s  = (e = ep.mr().close())  ? errno_name(e) : "ok";
const char *pd_s  = (e = ep.pd().close())  ? errno_name(e) : "ok";
const char *ctx_s = (e = ep.context().close()) ? errno_name(e) : "ok";
std::printf("teardown: qp=%s cq=%s mr=%s pd=%s context=%s\n",
            qp_s, cq_s, mr_s, pd_s, ctx_s);

Because close() is idempotent, the destructors that follow release nothing and report nothing. And because the explicit calls are in the same order the destructors would have used, an exception thrown before reaching this block still produces correct cleanup — the reporting is skipped, the release is not.

Order the port: limen_devinfo first (smallest, three wrappers), then limen_connect, then limen_pingpong. Run scripts/trd-01-tests.sh, then trd-02, then trd-03 after each respective port. Every one must pass unmodified — if you find yourself editing an old test, the refactor changed behaviour and has gone wrong.

H11 — No Raw Handles Outside the Layer (R11)

Level 1

Mostly a verification requirement rather than a construction one: if R10 is complete, this passes. Run the grep yourself before running the suite.

Expect to find one or two survivors — a stray destroy in an error path that the compiler had no reason to complain about. That is the requirement doing its job.

For the leak checks, remember to exercise a failure path for each program, not just the success path. Cleanup on the happy path is the part that was already working.

Level 2
grep -rn -E 'ibv_(destroy_qp|destroy_cq|dereg_mr|dealloc_pd|close_device)' \
     src/ include/ --include='*.c' --include='*.cpp' --include='*.hpp' \
  | grep -v 'src/verbs.cpp' | grep -v 'include/limen/verbs.hpp'

Empty output is the passing condition. Similarly for surviving manual cleanup:

grep -rn 'goto cleanup' src/ | grep -v verbs.cpp

The failure paths worth leak-checking are the ones each program already has: an unknown device for limen_devinfo, a forced RTR failure for limen_connect, and the finite-retry RNR run for limen_pingpong. All three now exit by unwinding rather than by jumping, which is precisely the change that could have introduced a leak.

The most useful habit on this rung

Compile early and often. Nearly every defect available here is a compile-time defect, and the assertion file plus the compile-fail test catch most of them before anything executes. A wrapper that passes static_contract.cpp and the three regression suites is very likely correct, which is not something that could be said of any previous rung.

The Tool Boundary

This is the one rung where the compiler is the primary diagnostic instrument. Read the error messages properly — a deleted-function error names the function and the call site, and a failed static_assert names the property. Both are more precise than anything a debugger would tell you afterwards.

An AI assistant is appropriate for reviewing code once it works, clarifying a concept a document left unclear, and grading comprehension answers. It is not appropriate for writing or debugging the implementation — and on this rung in particular, wrapper types are exactly the sort of boilerplate it is tempting to delegate, which would skip the entire lesson.
