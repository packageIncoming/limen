TRD-04: The RAII Layer

Prior Knowledge — Limen RDMA Transport Project
Depends on: TRD-03  |  Difficulty: Medium  |  Estimated: 3–5 sessions

1   Where This Fits

TRD-03 left you with a working transfer and a cleanup block containing six conditional destructions in a fixed order, reached by a jump from nine places, with correctness resting entirely on the sequence of lines. It also left you with a comment somewhere near the send buffer saying not to touch it until the completion arrives.

Both of those are rules the compiler is not enforcing. This rung makes it enforce them.

You will build C++ types that own verbs resources, release them in their destructors, refuse to be copied, move correctly, and cannot throw while destructing. Then you will refactor all three existing programs onto them and confirm that each still passes its own gate unchanged.

Nothing about RDMA changes here. Not one new verb, not one new concept about the fabric. What changes is that a class of bug you have been avoiding by remembering becomes a class of bug that will not compile.

This is also the rung that makes the rest of the ladder tractable. TRD-05 adds an event channel and a connection identifier with unusual lifetime rules. TRD-06 adds remote keys that must not outlive their regions. TRD-07 adds buffer pools. Every one of those is a resource, and hand-written cleanup does not survive that many.

2   The Problem, Stated Precisely

Verbs resources have three properties that together make manual management unreliable:

  1. Ordered destruction. A queue pair must be destroyed before the completion queue it references; both before the protection domain; the protection domain before the context. Violating the order produces EBUSY from a function whose return value nobody checks.
  2. Exclusive ownership. A handle is a pointer to a kernel object. Copying it produces two names for one resource and therefore two destructions of it. The second is a use-after-free inside a driver.
  3. Fallible release. ibv_destroy_qp(), ibv_destroy_cq(), ibv_dereg_mr(), and ibv_dealloc_pd() all return an error code.[5] Something can go wrong while you are cleaning up, and you may want to know.

C++ has an exact answer for the first two and an awkward one for the third. Sections 4 and 5 cover the exact answers; section 6 covers the awkwardness honestly, because pretending it is not there produces the most common defect in wrapper types.

3   What RAII Actually Guarantees

Resource acquisition is initialization: a resource's lifetime is tied to an object's lifetime, so that the resource is released whenever the object goes out of scope — normally, by early return, or by an exception unwinding the stack.

The last of those three is the one hand-written cleanup gets wrong most often, and the one that matters most as the program grows. A goto cleanup block handles normal exit and early return. It does not run if an exception passes through, and the moment any part of the program throws — a std::vector reallocation, a std::string construction, anything — the cleanup is skipped and the resources leak. In a C program that risk does not exist. In the C++ program this rung produces, it does.

What RAII buys, precisely:

GuaranteeMechanism
Release happens on every exit pathDestructors run during stack unwinding as well as normal scope exit
Release happens exactly onceOne owner; copying is forbidden and moving transfers
Release happens in the right orderMembers are destroyed in reverse declaration order — section 4
Forgetting is impossibleThere is no call to omit

4   The Ordering Guarantee

This is the fact the whole rung is built on, and it is worth stating in the language of the standard rather than as a rule of thumb.

Reverse declaration order

After a destructor body executes, the compiler calls the destructors of all non-static data members in reverse order of declaration, then the destructors of direct non-virtual base classes in reverse order of construction.[1] This is a guarantee of the language, not a convention or an optimisation.

So if a class declares its members in the order the resources must be created, the language destroys them in exactly the order they must be released. The ordering stops being something you maintain in a cleanup block and becomes something you express once, in a declaration list, that the compiler then honours on every exit path including ones you did not write.

class Endpoint {
    Context          ctx_;   /* created 1st  → destroyed 5th */
    ProtectionDomain pd_;    /* created 2nd  → destroyed 4th */
    MemoryRegion     mr_;    /* created 3rd  → destroyed 3rd */
    CompletionQueue  cq_;    /* created 4th  → destroyed 2nd */
    QueuePair        qp_;    /* created 5th  → destroyed 1st */
};

That produces queue pair, completion queue, memory region, protection domain, context — the exact order TRD-01 through TRD-03 required you to write by hand. Getting it wrong now requires reordering declarations, which is a visible structural edit rather than a line quietly moved inside a cleanup block during an unrelated change.

5   Move-Only Ownership

A verbs handle is a pointer to a kernel object. Two objects holding the same pointer will both destroy it, and the second destruction passes a dangling pointer into a driver. The type must therefore make copying impossible and moving correct.

The five special members

Declaring a destructor suppresses the implicit move operations, so a class with a user-declared destructor gets copy operations it should not have and loses move operations it needs. Every wrapper must therefore declare all five explicitly — this is the rule of five, and the correct form for a resource handle is:

class ProtectionDomain {
public:
    ProtectionDomain() = default;                                  /* empty state */
    explicit ProtectionDomain(ibv_context *ctx);                   /* acquires    */

    ~ProtectionDomain() noexcept;                                  /* releases    */

    ProtectionDomain(const ProtectionDomain&)            = delete; /* no sharing  */
    ProtectionDomain& operator=(const ProtectionDomain&) = delete;

    ProtectionDomain(ProtectionDomain&&) noexcept;                 /* transfers   */
    ProtectionDomain& operator=(ProtectionDomain&&) noexcept;

private:
    ibv_pd *pd_ = nullptr;
};

What a move must do

Three obligations, and the third is the one people forget:

  1. Take the source's handle.
  2. Leave the source holding null, so its eventual destructor releases nothing.
  3. In move assignment, release whatever the destination was already holding — otherwise assigning over a live object leaks it.

std::exchange expresses the first two in one line:[7]

ProtectionDomain::ProtectionDomain(ProtectionDomain &&o) noexcept
    : pd_(std::exchange(o.pd_, nullptr)) {}

ProtectionDomain &ProtectionDomain::operator=(ProtectionDomain &&o) noexcept {
    if (this != &o) {              /* self-assignment would release then adopt null */
        reset();                   /* obligation 3 */
        pd_ = std::exchange(o.pd_, nullptr);
    }
    return *this;
}
The moved-from state must be valid

A moved-from object is still destroyed. It must therefore be in a state where destruction is well defined — which for a handle means null, and means the destructor must check. An "empty" wrapper holding null is a legitimate state of the type, not an error, and every operation must behave sensibly in it.

Why the moves must be noexcept

Beyond being true, it is load-bearing: standard containers only use a type's move operations during reallocation if they are declared noexcept, falling back to copying otherwise. For a move-only type there is no copy to fall back to, so a non-noexcept move makes the type awkward to store in a std::vector — which TRD-07's buffer pool will want to do.

6   Destructors That Cannot Throw

Here is the awkward part, stated honestly.

A destructor with no exception specification is implicitly noexcept(true).[2] If an exception escapes one during stack unwinding, std::terminate() is called, which by default calls std::abort(); no further objects are destroyed and the program is in an indeterminate state.[1][2]

But ibv_destroy_qp() can fail. So a destructor has a failure it cannot report through the normal channel.

What not to do

ApproachWhy it is wrong
Throw from the destructorTerminates the program if anything else was already unwinding. The CERT rule is explicit: do not terminate a destructor by throwing.[2]
Declare it noexcept(false) and throwSame outcome during unwinding, plus it poisons every containing type's implicit destructor.[2]
Check std::uncaught_exceptions() and throw only when safeNamed as noncompliant. Circumventing normal destructor processing this way can leave the destructor failing to release the resource at all[2] — the workaround is worse than the problem.
Ignore the return value silentlyCompiles, never terminates, and discards the one signal that would have told you the ordering was wrong. This is the common defect.

What to do

Separate the two concerns. Provide an explicit release function that returns the status for callers who want it, and have the destructor call that function and report failure to a diagnostic sink without throwing.

class QueuePair {
public:
    /* Explicit release. Returns 0, or the errno value from ibv_destroy_qp.
       Safe to call more than once; a second call is a no-op returning 0. */
    int close() noexcept;

    ~QueuePair() noexcept {
        if (int e = close(); e != 0)
            limen::report_release_failure("ibv_destroy_qp", e);
    }
};

This gives callers who care a checkable error, gives everyone else automatic release, and never throws. report_release_failure writes to stderr — a real library would take a configurable sink, and this ladder does not need one.

The information is genuinely valuable. An EBUSY from a destructor means an ordering violation, and that is precisely the bug this layer exists to prevent. Printing it is how you find out the layer has a hole.

7   What Each Wrapper Owns

TypeOwnsReleases with

MemoryRegionibv_mr * and its bufferibv_dereg_mr, then free the buffer

Note that three different release conventions appear in one table, exactly as they did in TRD-01. Wrapping them is also how you stop having to remember which is which: each wrapper normalises its own, once, and no caller ever asks again. That is a second benefit of this layer and a reason to write the wrappers even for resources whose ordering is not delicate.

Why the memory region owns its buffer

A registration and the memory it registers have exactly the same required lifetime: the buffer must outlive the registration, and keeping it alive longer serves no purpose. Two objects with identical lifetimes and a mandatory ordering between them are better as one object.

It also closes a real hole. In TRD-03 the buffer was a separate free() in the cleanup block, and freeing it before deregistering — a two-line reordering — would hand the adapter a pointer into freed memory. Making the region own the buffer makes that ordering internal and unreachable from outside.

8   Construction and Failure

A constructor that cannot produce a valid object must throw; there is no return value. So a wrapper that acquires in its constructor throws when acquisition fails.

explicit ProtectionDomain(ibv_context *ctx) {
    pd_ = ibv_alloc_pd(ctx);
    if (!pd_) throw VerbsError("ibv_alloc_pd", errno);
}

This is a real change from the previous three rungs, where every failure was a return code and a jump. Two things follow and both matter.

First, the calling code gets simpler: failures propagate on their own and there is no cleanup to write, because any wrapper already constructed will be destroyed by unwinding. This is the payoff, and it is larger than it looks.

Second, the program can now throw, which means the goto cleanup blocks in the three existing programs are no longer merely verbose — they are incorrect, because an exception would skip them entirely. R10's refactor is therefore not optional tidying; leaving the old cleanup in place alongside throwing constructors is worse than either alone.

A single exception type carrying the operation name and the errno value is enough:

class VerbsError : public std::runtime_error {
public:
    VerbsError(const char *op, int err);
    int error() const noexcept { return err_; }
private:
    int err_;
};

The alternative — a factory function returning std::optional or std::expected and a private constructor — is defensible, avoids exceptions entirely, and is what some systems codebases require. It costs more boilerplate per type and is worth choosing deliberately rather than by default.

9   What This Layer Does Not Solve

Ownership of the buffer during a transfer is a different problem from ownership of the buffer's memory, and this layer does not address it.

Between posting a work request and reaping its completion, the adapter is reading or writing the buffer.[6] No destructor can help: the object is alive, the memory is valid, and the hazard is concurrent access rather than lifetime. Expressing it in the type system requires a different mechanism — a handle type returned by post() that must be consumed by wait() before the buffer is reachable again, so that the unsafe access has no expression rather than merely being discouraged.

That is a real design and this rung does not require it. What it does require, in the comprehension questions, is that you can describe why the two problems are different and what shape the second solution takes. Recognising which hazards RAII addresses and which it does not is the actual skill; applying RAII to everything is a way of believing you are safe.

11   What Is Deliberately Left Out

No reference counting. Verbs resources have exactly one owner in this design, and shared ownership would reintroduce the question of when release happens — which is the question this layer exists to answer definitively.

No thread safety. The wrappers are as thread-safe as a raw pointer: safe to use from one thread, unsafe to move from two. Nothing in this ladder is multithreaded.

No allocator customisation, no polymorphism, no virtual destructors. These are concrete types with no inheritance, which is why none of them needs a virtual destructor and why all of them can be trivially movable.

And, per section 9, no expression of transfer-time buffer ownership. That hazard survives this rung intact.

12   Further Reading

Read before starting:

  • cppreference, "Destructors"[1] — specifically the paragraphs on reverse-declaration-order member destruction and on the implicit exception specification. Two paragraphs, and the whole rung rests on them.
  • CERT DCL57-CPP[2] — why destructors must not throw, and why the std::uncaught_exceptions workaround is rejected. Short and unusually well argued.

Read while implementing:

  • A Tour of C++, ch. 5–6[4] — resource management, the rule of five, and move semantics, at exactly the depth this rung needs.
  • cppreference on std::exchange[7] — one page; it is the idiom the move operations are written in.

Reference as needed:

  • ISO C++ FAQ, destructors section[3] — good on the edge cases, particularly explicit destructor invocation and why you should not.
  • The verbs manual pages for the destroy functions[5] — the three return conventions your wrappers are normalising.
